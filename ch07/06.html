六、定时任务 ​

6.1 @EnableScheduling 与单线程默认值 ​

java
@Configuration(proxyBeanMethods = false)
@EnableScheduling
public class SchedulingConfig {
}

和 @EnableCaching 一样单独放一个类，理由在 2.3 说过：避免测试套件被动带上定时任务。

任务本身就是一个方法加注解：

java
@Scheduled(fixedDelayString = "${activity-server.cache-warmup.interval:30m}",
           initialDelayString = "${activity-server.cache-warmup.initial-delay:1m}")
public void refreshVenueCache() { ... }

默认只有一个线程。 官方原文：

The ThreadPoolTaskScheduler uses one thread by default and its settings can be fine-tuned using the spring.task.scheduling namespace.

只有一个线程意味着：任何任务执行慢，后面的任务全部排队等待。表现出来是“到点了但没执行”，而且日志里没有任何异常——因为它只是还没轮到。任务多于一个就必须调大：

yaml
spring:
  task:
    scheduling:
      pool:
        size: 4
      thread-name-prefix: hub-sched-

thread-name-prefix 顺手设一下，排查时在日志里能一眼看出是哪个执行器打的。

6.2 fixedDelay 还是 fixedRate ​

这两个参数的差别不在字面，而在计时起点：

参数计时起点任务执行时间超过间隔时
fixedRate上一次的开始时间下一次会被立即触发，多个执行可能叠在一起
fixedDelay上一次的结束时间天然不会重叠，跑完才重新计时
cron按日历规则与上次执行无关，可能重叠

案例项目用 fixedDelay：这个任务的语义是“隔一段时间做一次”，跑完再歇是符合直觉的。如果这里用 fixedRate 而任务某次执行卡了三分钟，之后会连续触发几次把队列塞满。

用 fixedDelayString 而不是 fixedDelay，是为了能从配置读值——测试时可以临时调短，不用改代码。

cron 表达式适合“每天凌晨 3 点”这种跟日历绑定的场景，写法是六段：

java
@Scheduled(cron = "0 0 3 * * *")        // 每天 03:00:00
@Scheduled(cron = "0 0/15 * * * *")     // 每 15 分钟
@Scheduled(cron = "0 0 9 * * MON-FRI")  // 工作日 09:00

要注意 cron 和 fixedRate/fixedDelay 不能在同一个 @Scheduled 上混用，只能选一种。

6.3 线程池参数怎么调 ​

@Scheduled 用的是 TaskScheduler（不是 TaskExecutor），可调的参数少，主要就是 pool.size 和线程名前缀。相比之下 @Async 用的 TaskExecutor 参数多得多：

yaml
spring:
  task:
    execution:
      pool:
        core-size: 8       # 默认 8
        max-size: 16
        queue-capacity: 100
        keep-alive: 10s
参数作用什么时候调
core-size常驻线程数默认 8。CPU 密集型别超过核数太多
max-size峰值线程数只在队列满时才扩到这么多
queue-capacity队列容量不设就是无界队列，此时 max-size 永远不会生效
keep-alive空闲线程回收时间默认 60s，调小让峰值后尽快缩容

queue-capacity 这一项要重点理解：队列无界时，任务会一直往队列里堆而不去创建新线程，max-size 形同虚设。官方示例里特意配了 queue-capacity=100，就是这个原因。

6.4 集群下的重复执行 ​

@Scheduled 是每个实例各跑一份。集群部署三个实例，任务是执行三次。这个行为本身不算 bug，但如果任务会写数据（比如“每天凌晨把过期活动标记为失效”），三次执行就可能出问题。

三种应对方式：

方式做法适合
加分布式锁抢到锁的实例执行中小规模，实现简单
用 Quartz 的集群模式见第八节，由数据库协调任务多、需要持久化和错过补偿
任务本身做成幂等重复执行结果不变最优，但设计成本高

最后一种是根本解。比如“标记过期活动”改成按条件更新（WHERE expire_at < now AND status = 'ACTIVE'），重复执行第二次影响行数是 0，自然幂等。

6.5 自调用：定时任务里的缓存注解不生效 ​

前面 2.10 提过，这里补上案例项目的完整写法。CacheWarmupJob 刻意没有用 @Scheduled + @Cacheable 的组合：

java
@Scheduled(fixedDelayString = "${activity-server.cache-warmup.interval:30m}", ...)
public void refreshVenueCache() {
    Cache cache = cacheManager.getCache(CACHE_CATEGORIES);
    if (cache == null) {
        log.warn("缓存 {} 不存在，请检查 spring.cache.cache-names 配置", CACHE_CATEGORIES);
        return;
    }
    cache.clear();
    log.debug("场地缓存已清理，下次访问将重新加载");
}

三点说明：

直接用 CacheManager，绕开注解。 注解要靠代理，而 @Scheduled 调的是同一个对象的方法，走不到代理。手写不仅行为确定，还能在缓存不存在时给出提示。

cache == null 的判断必须有。 声明 cache-names 之后，CacheManager 就不再按需创建缓存，getCache(未声明的名字) 会返回 null。不判断就是一次 NPE，而 NPE 在定时任务里只会打一行日志——没人盯着日志的话，你只会觉得“任务没生效”。

（simple provider 的表现略有不同：配了 cache-names 而用到未列出的缓存时，它会在运行期直接抛 IllegalArgumentException。官方对此的说明是“运行时会失败，而不是启动时”，也就是说这类拼写错误一定会在某个时刻暴露，只是不一定是启动时。）

用 log.debug 而不是 log.info。 这个任务默认 30 分钟跑一次，一年的 info 日志有 17520 行，全是“清理完成”。真正出问题时这些噪音会把有用的记录淹掉。定时任务里用 info 只留两种：启动、以及失败。

6.6 怎么确认任务真的跑了 ​

“任务没执行”是最难查的一类问题，因为成功的执行不留痕迹。三个办法：

办法做法说明
日志执行时打一条 debug排查时临时把该类的日志级别开到 debug，logging.level.com.example.activity=debug
Actuator查 /actuator/scheduledtasks能看到已注册的全部任务、cron 表达式和下次执行时间（第 10 篇讲）
测试直接调用任务方法断言副作用案例项目 CacheWarmupJobTest 用的就是这种，见下

测试的做法是直接调方法，然后断言缓存真的被清了：

java
venueService.listAll();                       // 填充缓存
assertThat(entriesOf(CACHE_CATEGORIES)).hasSize(1);

cacheWarmupJob.refreshVenueCache();            // 直接调用，不等待调度

assertThat(entriesOf(CACHE_CATEGORIES)).isEmpty();

这里顺手演示了怎么把缓存里的东西掏出来看。Cache 接口只有 get/put/evict 改不了遍历，要看全部条目得拿 getNativeCache()：

java
com.github.benmanes.caffeine.cache.Cache<Object, Object> nativeCache =
        (com.github.benmanes.caffeine.cache.Cache<Object, Object>) cache.getNativeCache();
return nativeCache.asMap();

这个技巧在排查“缓存到底有没有生效”时很有用。断言“第二次查询没发 SQL”能证明命中了缓存，但证明不了缓存里存的是不是你想要的那份数据。
