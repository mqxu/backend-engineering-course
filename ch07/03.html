三、参数校验：从 DTO 到配置项 ​

3.1 依赖与自动配置 ​

xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

引入它之后，Bean Validation 的实现（Hibernate Validator）就在类路径上了，Spring Boot 自动完成两件配置：

  • 装配一个 Validator bean，供 @Valid 使用；
  • 注册 MethodValidationPostProcessor，让标注了 @Validated 的类具备方法级校验能力。

官方对这一点的原话是：

The method validation feature supported by Bean Validation 1.1 is automatically enabled as long as a JSR-303 implementation (such as Hibernate Validator, typically provided by spring-boot-starter-validation) is on the classpath.

3.2 @Valid 与 @Validated 的分工 ​

这两个注解经常被混着用，它们其实管的是两条不同的路径：

注解位置管什么失败时抛什么
@Valid@RequestBody 参数上对请求体做一次校验，级联到字段MethodArgumentNotValidException
@Validated类上开启方法级校验，让 @Min、@Size 这类注解在方法参数上生效ConstraintViolationException

案例项目正好两条都用上了：

java
@RestController
@RequestMapping("/api/activities")
@Validated                                  // 开方法级校验
public class ActivityController {

    @PostMapping
    public ApiResponse<ActivityResponse> create(
            @Valid @RequestBody ActivityCreateRequest request) { ... }   // 校验请求体

    @GetMapping
    public ApiResponse<PageResult<ActivityResponse>> list(
            @RequestParam(defaultValue = "0")
            @Min(value = 0, message = "页码不能小于 0") int page, ...) { ... }  // 校验请求参数
}

关键点：类上不加 @Validated，@RequestParam 上的 @Min 就是一个装饰品——不报错，也不生效。这是最容易踩的一个坑，因为代码看起来完全正常。

3.3 案例项目的校验注解清单 ​

请求 DTO 上的约束写得很密，逐个看一遍就知道常用的几个够用了：

java
public record ActivityCreateRequest(
        @NotBlank(message = "标题不能为空")
        @Size(max = 128, message = "标题长度不能超过 128 个字符")
        String title,

        @Size(max = 512, message = "描述长度不能超过 512 个字符")
        String description,

        @NotNull(message = "必须指定所属场地")
        Long venueId,

        @NotNull(message = "必须指定活动类型")
        ActivityType type, ...) { }
注解语义常见误用
@NotNull不能为 null，空串可以通过想校验“必填字符串”时用错，应该用 @NotBlank
@NotEmpty不能为 null 且长度大于 0，纯空格可以通过用于字符串时不严格，同上
@NotBlank不能为 null，且去掉首尾空白后长度大于 0只能用于字符串，用在数值类型上会报错
@Size长度范围，可用于字符串、集合、数组@Min/@Max 用于数值，别混
@Pattern正则匹配正则里带 \ 时要写成 \\
@Min / @Max数值边界记不清是包含还是不包含——两者都包含边界值
@Email邮箱格式它不校验“域名真实存在”，只校验格式

注册接口的密码规则用的是 @Pattern，一次把复杂度讲清楚：

java
@Pattern(regexp = "^(?=.*[A-Za-z])(?=.*\\d).+$", message = "密码必须同时包含字母和数字")

而登录接口刻意没有这套规则，只留了长度上限：

注意这里只有 @NotBlank/@Size 这类格式校验，没有“密码必须 8 位以上”的规则。

原因是安全上的惯例：登录接口不应该校验密码复杂度。如果登录时告诉你“密码不符合复杂度要求”，就等于向外泄露了“系统里没有这种格式的密码”，属于信息泄漏。复杂度只在注册和改密时校验。

3.4 实测：四种错误的实际响应体 ​

校验失败要返回什么，光看代码不够直观，实测一遍。用 MockMvc 发四种有问题的请求，把响应体打出来：

场景HTTP响应体
字段全空400{"code":40001,"message":"venueId: 必须指定所属场地; organizer: 主办方不能为空; type: 必须指定活动类型; title: 标题不能为空"}
JSON 语法错400{"code":40002,"message":"请求体格式错误，请检查 JSON 结构与枚举取值"}
枚举值非法400{"code":40002,"message":"请求体格式错误，请检查 JSON 结构与枚举取值"}
分页参数非法400{"code":40001,"message":"页码不能小于 0"}

从这四行能读出几个设计决定：

一、错误信息是拼接返回的，不是只报第一个。 全局异常处理器把 getFieldErrors() 全部收集起来拼成一行：

java
String detail = ex.getBindingResult().getFieldErrors().stream()
        .map(error -> error.getField() + ": " + error.getDefaultMessage())
        .collect(Collectors.joining("; "));

让前端一次拿到所有问题，可以一次把所有出错字段标红，而不是用户改一个提交一次、来回五次。

二、字段顺序是不固定的。 上面那行里 venueId 在 title 前面，换个 JDK 版本或者改个字段可能就变了——底层是 LinkedHashMap 但校验器遍历顺序并不保证。所以不要写依赖顺序的测试断言，前端也不要按位置取值。要精确断言的话应该用 contains 而不是 isEqualTo。

三、枚举传错值归到“格式错误”而不是“字段错误”。 因为 Jackson 反序列化阶段就失败了，压根没走到 Bean Validation。日志里能看到具体原因：

text
Cannot deserialize value of type `com.example.activity.domain.ActivityType`
from String "NOT_A_TYPE": not one of the values accepted for Enum class: [LINK, COMPETITION, CODE, LECTURE]

这个日志有用（排查时能直接看到合法取值），但不能返回给前端——错误消息里带上内部枚举的完整类名属于信息泄漏。所以异常处理器只回一句通用提示，细节留在服务端日志里：

java
@ExceptionHandler(HttpMessageNotReadableException.class)
public ResponseEntity<ApiResponse<Void>> handleNotReadable(HttpMessageNotReadableException ex) {
    log.warn("请求体解析失败: {}", ex.getMessage());     // 细节只进日志
    return ResponseEntity.badRequest()
            .body(ApiResponse.fail(40002, "请求体格式错误，请检查 JSON 结构与枚举取值"));
}

四、兜底处理必须有，但不能返回内部细节。 全局异常处理器最后一个分支是 @ExceptionHandler(Exception.class)，它记 error 级日志（带堆栈）但只回一句“服务器内部错误，请稍后重试”。少了这个分支，未预期的异常会直接变成 Spring 默认的白页错误响应，格式和其他接口完全不一致。

3.5 分组校验 ​

同一个 DTO 在新增和修改时校验规则不同的情况很常见。比如新增要求密码必填，修改时密码可选。用校验分组解决：

java
public interface Create {}
public interface Update {}

public record UserRequest(
        @NotNull(groups = Update.class, message = "修改时必须指定 id")
        Long id,

        @NotBlank(groups = Create.class, message = "新增时用户名必填")
        String username,

        @NotBlank(groups = Create.class, message = "新增时密码必填")
        @Size(min = 8, max = 64, groups = {Create.class, Update.class})
        String password) { }

控制器的调用方式：

java
@PostMapping
public ApiResponse<?> create(@Validated(Create.class) @RequestBody UserRequest req) { ... }

@PutMapping("/{id}")
public ApiResponse<?> update(@Validated(Update.class) @RequestBody UserRequest req) { ... }

两个注意点：这里用的是 @Validated(Create.class) 而不是 @Valid（@Valid 不支持指定分组）；以及没有声明分组的约束属于 Default 组，指定了分组就不会执行——上例中 @Size 显式归到了两个分组，如果不写 groups，它会因为只属于 Default 组而被跳过。

3.6 自定义约束 ​

内置注解不够用时写一个。以“必须是合法活动链接”为例，先写注解：

java
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = HttpUrlValidator.class)
public @interface HttpUrl {
    String message() default "必须是合法的 http/https 链接";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

三样东西不能少：message、groups、payload。前两个是给框架用的，payload 看着没用但 Bean Validation 规范要求必须有。

再写校验器：

java
public class HttpUrlValidator implements ConstraintValidator<HttpUrl, String> {

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        // 约定：null 一律放行，是否允许为空交给 @NotNull 决定。
        // 这是 Bean Validation 的惯例，自定义约束也必须遵守，
        // 否则一个"格式"约束会顺带变成"必填"约束。
        if (value == null) {
            return true;
        }
        return value.startsWith("http://") || value.startsWith("https://");
    }
}

“null 一律返回 true”是自定义约束最容易写错的地方。 校验注解的职责是校验格式，不是校验存在性。把两个职责混在一起，之后就没法单独关掉其中一个了。

3.7 方法级校验：Service 层也要防 ​

DTO 校验只能挡住来自 HTTP 的请求。同一套业务逻辑如果被定时任务、消息消费者、内部其他服务调用，就绕过了整个校验层。所以 Service 上也应该有个兜底：

java
@Service
@Validated
public class ActivityService {

    public ActivityResponse getById(@NotNull(message = "id 不能为空") Long id) { ... }

    public List<ActivityResponse> batchDelete(
            @NotEmpty(message = "id 列表不能为空")
            @Size(max = 100, message = "单次最多删除 100 条") List<Long> ids) { ... }
}

约束失败时抛 ConstraintViolationException。案例项目在全局异常处理器里已经接了它：

java
@ExceptionHandler(ConstraintViolationException.class)
public ResponseEntity<ApiResponse<Void>> handleConstraintViolation(ConstraintViolationException ex) {
    String detail = ex.getConstraintViolations().stream()
            .map(ConstraintViolation::getMessage)
            .collect(Collectors.joining("; "));
    return ResponseEntity.badRequest().body(ApiResponse.fail(40001, detail));
}

为什么它和 MethodArgumentNotValidException 要分开处理：两个异常的信息结构不同。前者有 getBindingResult().getFieldErrors()，能拿到字段名；后者只有 getConstraintViolations()，字段名藏在 getPropertyPath() 里，格式是 methodName.argN，直接返回给用户没意义。所以后者只回消息文本。

3.8 配置项校验：让配错在启动时就炸 ​

这是最容易被忽略的一处校验场景。配置类同样可以校验，而且收益比 DTO 校验更大——DTO 配错影响一个接口，配置配错影响整个应用。

案例项目的做法是加 @Validated 和约束注解：

java
@Validated
@ConfigurationProperties(prefix = "activity-server.external-api")
public record ExternalApiProperties(
        @NotBlank(message = "activity-server.external-api.base-url 不能为空")
        @DefaultValue("https://catalog.example.com/api") String baseUrl,

        @NotNull @DefaultValue("2s") Duration connectTimeout,

        @NotNull @DefaultValue("3s") Duration readTimeout,

        @DefaultValue("false") boolean enabled
) { }

@Validated 必须加。 光在字段上写约束注解不生效——配置绑定走的是自己的流程，不会自动触发 Bean Validation。

实测把它配成一个空串：

yaml
activity-server:
  external-api:
    base-url:      # 故意留空

应用启动直接失败。这一点很重要：配错 base-url 如果是运行到调用外部接口时才失败，那么故障要等到那个功能被触发才暴露，可能是上线几天后。启动期失败虽然“看起来更凶”，但把问题挡在了部署环节。

不过有个细节值得知道：启动失败的报错信息本身很笼统，只说找不到某个 bean 或配置绑定失败，真正说明哪个属性不合规的消息藏在根因里，要顺着 getCause() 一层层往下钻才看得到。真遇到时不要只看第一行。

3.9 消息国际化 ​

约束消息可以抽到 messages.properties 里，走 Spring 的 MessageSource 解析。官方明确说明会先用应用的 MessageSource 解析消息里的 {参数}，之后才交给 Bean Validation 的标准插值器。

做法是把消息写成占位符：

java
@Size(max = 128, message = "{activity.title.max}")
String title;
properties
# src/main/resources/messages.properties
activity.title.max=标题长度不能超过 {max} 个字符
properties
# src/main/resources/messages_en.properties
activity.title.max=Title must not exceed {max} characters

{max} 是被自动填入的——它来自约束本身的属性。这样多语言和文案调整都不用改 Java 代码，业务同事也能改。

⚠ 注意消息 key 不要用 . 结尾或者写成路径形式，也要避免和 messages.properties 里已有的 key 撞名。找不到 key 时，Hibernate Validator 会把 {xxx} 原样输出在错误消息里返回给用户——这类泄漏偶尔会在线上看到。
