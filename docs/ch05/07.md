# 七、授权：两种配置方式

### 7.1 URL 规则（过滤链里）

适合“按接口路径划分权限”的粗粒度控制，优点是一眼能看全所有接口的权限规则。

```java
.requestMatchers(HttpMethod.POST, "/api/resources").hasRole("ADMIN")
.requestMatchers(HttpMethod.PUT, "/api/resources/**").hasRole("ADMIN")
.requestMatchers(HttpMethod.DELETE, "/api/resources/**").hasRole("ADMIN")
```

### 7.2 方法注解（`@PreAuthorize`）

适合“权限条件带业务含义”的场景。需要类或配置上的 `@EnableMethodSecurity` 才会生效。

```java
@PostMapping("/{id}/download")
@PreAuthorize("isAuthenticated()")
public ApiResponse<ResourceResponse> download(@PathVariable Long id) {
    return ApiResponse.ok(resourceService.download(id));
}
```

`@PreAuthorize` 支持 SpEL，能写更复杂的条件：

```java
@PreAuthorize("hasRole('ADMIN') or #userId == authentication.principal.id")
public UserResponse getUser(Long userId) { ... }

@PreAuthorize("hasAuthority('resource:delete')")
public void delete(Long id) { ... }
```

| | URL 规则 | `@PreAuthorize` |
| --- | --- | --- |
| 配置位置 | 集中在一处 | 分散在方法上 |
| 能否按方法参数判断 | 不能 | 能（用 SpEL 引用参数） |
| 新增接口时的默认行为 | 由 `anyRequest` 兜底 | 不写注解就没有额外限制 |
| 适用 | 路径与权限一一对应 | 权限条件复杂、与业务相关 |

**两种方式同时存在不会重复拦截**——只要有一条不通过就拒绝。本项目两者都用：URL 规则做主干，`@PreAuthorize` 补充带业务语义的规则。
