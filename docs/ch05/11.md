# 十一、实测抓到的真实 bug：`ROLE_` 前缀

这一节是整篇最值得看的部分——**测试全绿但线上坏掉**的典型案例。

### 现象

42 个测试全部通过后，我启动应用用 curl 真实调用：

```
管理员带令牌新增资源 → HTTP 403 "没有权限执行该操作"
```

管理员是 `hasRole("ADMIN")` 允许的角色，令牌也校验通过了，却拿到 403。

### 根因

问题出在 `AuthUser` 的权限构造：

```java
// 错的
@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    return List.of(new SimpleGrantedAuthority(role));   // role = "ADMIN"
}
```

Spring Security 的 `hasRole("ADMIN")` 内部比对的是 **`ROLE_ADMIN`**，而这里放进去的权限名是裸的 `ADMIN`，匹配不上。

### 为什么测试没发现

MockMvc 测试里写的是：

```java
user("admin").roles("ADMIN")
```

`roles("ADMIN")` 这个 API **会自动补上 `ROLE_` 前缀**，产生的权限名是 `ROLE_ADMIN`——正好匹配。

而真实请求走的是 JWT 解析路径：

```
令牌 claim: role = "ADMIN"
  → AuthUser.fromToken(uid, subject, "ADMIN")
  → getAuthorities() 返回 "ADMIN"        ← 少了前缀
  → hasRole("ADMIN") 去找 "ROLE_ADMIN"   ← 匹配失败
  → 403
```

**两条路径构造权限的方式不同，测试用了一条，线上走的是另一条。**

### 修复

```java
private static final String ROLE_PREFIX = "ROLE_";

@Override
public Collection<? extends GrantedAuthority> getAuthorities() {
    // 角色名可能来自数据库（"ADMIN"），也可能来自测试代码（"ROLE_ADMIN"），
    // 这里统一补前缀，避免拼出 ROLE_ROLE_ADMIN
    String authority = role.startsWith(ROLE_PREFIX) ? role : ROLE_PREFIX + role;
    return List.of(new SimpleGrantedAuthority(authority));
}
```

修复后：

```
管理员带令牌新增 → HTTP 201
普通用户新增     → HTTP 403
```

### 教训

| 结论 | 说明 |
| --- | --- |
| **测试通过 ≠ 功能正确** | 尤其是测试框架提供的便捷 API（`roles()`、`hasRole()`）会自动补全一些东西，掩盖真实路径的差异 |
| **关键链路必须用真实 HTTP 验证** | 认证、授权、序列化这三类问题最容易被测试的“便利层”掩盖 |
| **`hasRole` 与 `hasAuthority` 别混用** | `hasRole("ADMIN")` 找 `ROLE_ADMIN`；`hasAuthority("ADMIN")` 找 `ADMIN`。数据库里存哪种，就统一用对应的那个 |
