# 9.10 Testcontainers 2.0：一次比 Boot 4 更彻底的模块拆分

Boot 4.1.1 管理的 Testcontainers 版本是 **2.0.5**。这是一个大版本跨越（1.21.x 直接跳到 2.0），变化集中在模块与包名上，而且**有些地方跟直觉相反**。

### 变化一：数据库容器全部移出了 core

1.x 时代，`org.testcontainers:testcontainers` 这一个 jar 里什么都有：`GenericContainer` 和 `MySQLContainer`、`PostgreSQLContainer` 是邻居。2.0 之后，core 里只剩与具体中间件无关的东西：

| 还在 core 里的 | 已经搬走的 |
| --- | --- |
| `GenericContainer`、`Network`、`Container`、`ContainerState` | `MySQLContainer` → `testcontainers-mysql` |
| `DockerComposeContainer`、`ComposeContainer` | `JdbcDatabaseContainer` → `testcontainers-jdbc` |
| `ImageNameSubstitutor`、`DockerImageName` 等工具类 | `@Testcontainers` / `@Container` → `testcontainers-junit-jupiter` |

核实方式很直接——把 `testcontainers-2.0.5.jar` 拉下来列一遍类名，`JdbcDatabaseContainer`、`MySQLContainer`、`PostgreSQLContainer` 一个都搜不到：

```bash
unzip -l testcontainers-2.0.5.jar | grep -E "JdbcDatabaseContainer|MySQLContainer"
# 没有输出
```

所以**引了 core 不等于有 `MySQLContainer`**。缺 `testcontainers-mysql` 会在编译期直接报“找不到符号”，不会拖到运行期。

### 变化二：坐标名加了前缀（和 1.x 相反）

这一条最反直觉，因为它是**反着改**的：

| 模块 | 1.x 坐标 | 2.0 坐标 |
| --- | --- | --- |
| MySQL 容器 | `org.testcontainers:mysql`（1.21.4） | `org.testcontainers:testcontainers-mysql`（2.0.5） |
| JUnit 5 支持 | `org.testcontainers:junit-jupiter`（1.21.4） | `org.testcontainers:testcontainers-junit-jupiter`（2.0.5） |
| JDBC 基类 | `org.testcontainers:jdbc`（1.21.4） | `org.testcontainers:testcontainers-jdbc`（2.0.5） |

注意两个 metadata 的版本线，它们是**两条并行的线**、互不覆盖：

```
org.testcontainers:mysql                  → <release> 1.21.4
org.testcontainers:testcontainers-mysql    → <release> 2.0.5
```

这意味着**旧的 `org.testcontainers:mysql` 不会自动跳到 2.0**。如果你的 `pom.xml` 里写的是老坐标，版本会一直停在 1.21.4，看起来“升级了 Boot 但 Testcontainers 没动”。

### 变化三：包名从 `containers` 搬到了各自的技术栈下

| 类 | 1.x 包名 | 2.0 包名 |
| --- | --- | --- |
| `MySQLContainer` | `org.testcontainers.containers` | `org.testcontainers.mysql` |
| `JdbcDatabaseContainer` | `org.testcontainers.containers` | `org.testcontainers.containers`（未变，但在 `testcontainers-jdbc` 模块里） |
| `@Testcontainers` / `@Container` | `org.testcontainers.junit.jupiter` | `org.testcontainers.junit.jupiter`（未变，但换了模块） |

跟 Boot 4 自己的做法一样：**技术栈专属的类挪进技术栈命名空间**。

这里有个细节要注意——`org.testcontainers.containers.MySQLContainer` **在 2.0 里仍然存在**，能 import、能编译，只是类的内部已经变成对新的 `org.testcontainers.mysql.MySQLContainer` 的包装。所以**“能编译过”不能作为“用的是新写法”的证据**。反编译对比一下两个包的类声明能看出区别：

```
新：public class org.testcontainers.mysql.MySQLContainer
        extends org.testcontainers.containers.JdbcDatabaseContainer<org.testcontainers.mysql.MySQLContainer>

旧：public class org.testcontainers.containers.MySQLContainer<SELF extends ...MySQLContainer<SELF>>
        extends org.testcontainers.containers.JdbcDatabaseContainer<SELF>
```

### 变化四：去掉了自引用的泛型参数

旧写法是 `MySQLContainer<SELF extends MySQLContainer<SELF>>` 这种自引用泛型，用来让链式调用返回子类型。2.0 把它去掉了，`MySQLContainer` 不再有类型参数：

```java
// 1.x 的写法
MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8");

// 2.0 的写法，不需要钻石操作符
MySQLContainer mysql = new MySQLContainer("mysql:8");
```

### 怎么快速判断一个坐标/包名到底改没改

结合第 7 篇和第 8 篇用过的办法，这类“升级后编译不过”的问题都可以按下面的顺序查，比翻文档快：

```bash
# 1. 查坐标的最新版本线，看有没有并行的新旧两条
curl -s https://repo1.maven.org/maven2/org/testcontainers/mysql/maven-metadata.xml | grep release

# 2. 把 jar 拉下来，直接看到底有哪些类
unzip -l testcontainers-mysql-2.0.5.jar | grep "\.class"

# 3. 类名没变却报"找不到包"，基本就是包名迁移
unzip -l xxx.jar | grep 关键词
```
