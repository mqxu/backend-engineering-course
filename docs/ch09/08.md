# 9.8 条件装配怎么测：`ApplicationContextRunner`

前面所有测试都在验证“应用能不能干活”，有一类东西却一直没有覆盖到：**容器该不该装上某个 Bean**。

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(name = "activity.feature.signup-tracking",
        havingValue = "true", matchIfMissing = true)
public class SignupTrackingConfig {

    @Bean
    public SignupTracker downloadTracker() {
        return new SignupTracker();
    }
}
```

这类开关用 `@SpringBootTest` 也能测，代价是为了确认一个 `@ConditionalOnProperty` 生效没生效，得把数据库、Web 服务器全启动一遍。`ApplicationContextRunner` 给的是另一条路：

```java
class SignupTrackingConfigTest {

    private final ApplicationContextRunner runner = new ApplicationContextRunner()
            .withUserConfiguration(TestConfig.class);

    @Configuration(proxyBeanMethods = false)
    @Import(SignupTrackingConfig.class)
    static class TestConfig {
    }

    @Test
    void disabledWhenFalse() {
        runner.withPropertyValues("activity.feature.signup-tracking=false")
                .run(context -> assertThat(context).doesNotHaveBean(SignupTracker.class));
    }
}
```

它搭的是一个只装了两三个类的小上下文，启动成本几乎为零——4 个用例跑了 **0.02 秒**。而且它**不读 `application.yml`**（除非你主动告诉它读），每个属性都是测试自己写的，条件分支能被一条条穷举干净。

### 一条实测验证过的语义细节

`havingValue` 比对的是**字符串**，不是布尔的松散解析：

```java
@Test
void anyOtherValueMeansDisabled() {
    // 写 on / yes / 1 都不会生效
    runner.withPropertyValues("activity.feature.signup-tracking=on")
            .run(context -> assertThat(context).doesNotHaveBean(SignupTracker.class));
}
```

`on`、`yes`、`1` 这些写法看起来很合理，但都不会让开关打开。把它钉成测试，下次谁改了配置写法，这里会先提醒他确认语义。

`matchIfMissing = true` 同样值得测。它表示“属性完全没写时按开启处理”，漏写这个属性时容器里会悄悄少一个 Bean——这种失败往往要等到线上报 `NullPointerException` 才被发现。
