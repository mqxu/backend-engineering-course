# 9.1 四层测试：先划线，再动手写

测试分层的意义不是“显得专业”，是**省时间**。下面这张表的耗时是实测值，同一个工程、同一台机器：

| 层次 | 启动的东西 | 用例数 | 实测耗时 | 适合测什么 |
| --- | --- | --- | --- | --- |
| 纯单元测试 | 什么都不起 | 5 | **0.68 s** | 业务规则、分支、异常路径 |
| Web 切片 | 只有 MVC 那半边容器 | 4 | **0.31 s** | 路由、入参校验、响应体格式、异常映射 |
| 数据访问切片 | JPA + 内嵌数据库 | 5 | **0.56 s** | 仓储方法名解析出的 SQL 行为 |
| 整体测试（Mock 环境） | 完整容器，不起服务器 | 4 | **2.43 s** | 一次请求穿透所有层，但不走网络 |
| 整体测试（真实端口） | 完整容器 + 内嵌 Tomcat | 3 | **0.66 s** | 序列化、HTTP 状态码、真实网络栈 |
| 条件装配 | 极小的手工上下文 | 4 | **0.02 s** | 开关、`@ConditionalOn*` 是否按预期生效 |
| 测试工具 | 什么都不起 | 2 | **0.01 s** | 输出捕获、临时属性注入 |
| Testcontainers | 完整容器 + 真实 MySQL | 4 | **9.28 s** | 方言、字符集、真实约束行为 |

几个从这张表里能直接读出来的结论：

1. **纯单元测试比 Web 切片快一倍，Web 切片比整体测试快一个数量级。** 一个断言逻辑分支的测试如果写在 `@SpringBootTest` 里，你付出的代价是它的几百倍，换来的可信度却完全一样。
2. **“真实端口”没有比“Mock 环境”慢很多**。这一点常被误解——2.43 s 那个数字看着更大，是因为它包含了整个容器首次启动的开销（数据库初始化、JPA 元模型构建），后面几个整体测试类复用了同一个上下文，所以轮到真实端口那个类时只剩 0.66 s。稳定跑起来之后，两者的差距主要在 Tomcat 启动和 TCP 往返上，通常几十毫秒量级。
3. **条件装配那一层的成本几乎为零。** 用 `ApplicationContextRunner` 搭一个只装两三个类的小上下文，4 个用例 17 毫秒。需要验证“开关打开时有没有这个 Bean”，不该去启动整个应用。
4. **Testcontainers 一层比其余所有层加起来还贵。** 9.28 s 里绝大部分是容器启动与 MySQL 初始化，跟用例写了几个关系不大。所以它的定位是**补充**而不是**替代**：日常迭代跑前面几层，涉及方言与字符集的用例放到这一层，在 CI 上完整跑。

### 划线的两条问题

每写一个测试前，问两句话就够：

- **被测的这段逻辑里，有没有 Spring 特有的行为？**（事务代理、条件装配、AOP、参数解析）——没有的话，别起容器。
- **有没有真实的外部依赖？**（数据库、HTTP、消息队列）——没有的话，用假对象就够，别连真的。

两个问题都是“否”，写在最底层。任一为“是”，往上走一层，并且**只走必要的那些层**。
