# 9.3 第一层：纯单元测试，不启动任何容器

```java
@ExtendWith(MockitoExtension.class)
class ResourceServiceUnitTest {

    @Mock
    private ResourceItemRepository repository;

    private ResourceService service;

    @BeforeEach
    void setUp() {
        // 手工 new 出被测对象，依赖从构造器塞进去。
        // 能手工 new，恰恰说明 Service 没有把自己绑死在容器上。
        service = new ResourceService(repository);
    }

    @Test
    void findByIdThrowsWhenMissing() {
        given(repository.findById(99L)).willReturn(Optional.empty());

        ResourceNotFoundException ex = catchThrowableOfType(
                () -> service.findById(99L), ResourceNotFoundException.class);

        assertThat(ex).isNotNull();
        assertThat(ex.getMessage()).contains("99");
        assertThat(ex.getResourceId()).isEqualTo(99L);
    }
}
```

这段代码里没有一行 Spring 的东西，这本身就是结论：**`ResourceService` 的构造器注入写得对**。如果它内部用 `@Autowired` 字段注入，或者直接 `new` 了仓储，这个测试就写不成，只能去起容器。

### 为什么用 `MockitoExtension` 而不是 `Mockito.mock()`

两者都能造出假对象，区别在两件事：

**一是无用的 stub 会被揪出来。** 需求改动之后，某个 `given(...)` 可能再也不会被走到。用 `MockitoExtension`，测试会直接失败并提示“这个 stub 没被使用”；用 `mock()` 手工创建，它会一直躺在那儿，测试照样绿，而你已经在断言一段不存在的行为了。

```java
// 定义了却用不到，MockitoExtension 会让这个测试失败
given(repository.save(any(ResourceItem.class))).willReturn(item);
```

**二是 `@Mock` 的注入与生命周期由扩展管理**，不用每个测试方法里写一遍 `mock(...)`。

### 断言“对象长什么样”，而不是“方法被调用过”

`verify(...)` 能表达的信息很少。想知道传给下游的对象是否组装正确，用 `ArgumentCaptor` 把参数抓出来看：

```java
given(repository.save(any(ResourceItem.class)))
        .willAnswer(invocation -> invocation.getArgument(0));

service.create("新资源", "描述", "生活", ResourceType.LINK, "https://x.com", "陶然然");

ArgumentCaptor<ResourceItem> captor = ArgumentCaptor.forClass(ResourceItem.class);
then(repository).should().save(captor.capture());

assertThat(captor.getValue().getTitle()).isEqualTo("新资源");
assertThat(captor.getValue().getType()).isEqualTo(ResourceType.LINK);
```

`then(repository).should()` 是 BDD 写法，和 `verify(repository)` 等价，但读起来更像一句话：“然后，仓储应该被保存调用了一次”。

### 这一层容易写歪的两个地方

**避免为了凑覆盖率去测 getter。** 一个只有 getter/setter 的类不需要测试，测它只是在重复编译器的活儿。

**别在单元测试里验证事务。** 下面这行代码在纯单元测试里是**完全没有效果**的——没有容器，就没有代理，注解只是一段元数据：

```java
@Transactional
public ResourceItem download(Long id) { ... }
```

第 8 篇的类里也吃这个亏。想验证“事务真的生效了”，得往上走一层，放到切片或整体测试里。
