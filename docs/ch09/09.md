# 9.9 第四层：Testcontainers，让测试跑在真实数据库上

前面所有数据库测试用的都是 H2。H2 很好用，但它不是 MySQL：

- **方言不同**：`ON DUPLICATE KEY UPDATE`、`LIMIT ? OFFSET ?` 的边界行为、`GROUP BY` 的宽松程度都不一样
- **隔离级别与锁行为不同**：MySQL 默认 `REPEATABLE READ`，H2 默认 `READ COMMITTED`
- **约束的报错时机不同**：有些约束 H2 立刻报，MySQL 等到语句结束才报
- **字符集与排序规则不同**：容器默认字符集不对时，中文会变成问号，而且**只在真实库上才暴露**

“本地全绿，一上真实库就挂”，根因多半就在这几条里。Testcontainers 解决的是这件事：让测试跑在真实的 MySQL 上，同时不要求开发机装数据库。

### 用起来只有三行

```java
@SpringBootTest
@Testcontainers
class MySqlContainerIntegrationTest {

    @Container
    @ServiceConnection
    static MySQLContainer mysql = new MySQLContainer("mysql:8");

    @Autowired
    private DataSource dataSource;
}
```

三个注解各管一件事：

| 注解 | 作用 |
| --- | --- |
| `@Testcontainers` | 把容器生命周期交给 Testcontainers 的 JUnit 扩展 |
| `@Container` | 标记这是一个受管容器；**`static` 是必须的**，否则每个测试方法都会起一个新容器 |
| `@ServiceConnection` | 把容器的连接信息喂给 Spring Boot，覆盖配置里的数据源设置 |

`@ServiceConnection` 是 Spring Boot 提供的那一半。它读容器的连接信息，反过来覆盖 `spring.datasource.*`——**所以这里一个字的数据源配置都不用写，写了的反而会被它盖掉**。

这段逻辑真的生效了吗？用测试确认，不要靠猜：

```java
@Test
void serviceConnectionOverridesConfiguration() throws Exception {
    try (Connection connection = dataSource.getConnection()) {
        String url = connection.getMetaData().getURL();

        // application.yml 里写的是 jdbc:h2:mem:testing
        assertThat(url).doesNotContain("h2");
        assertThat(url).contains("mysql");
        assertThat(url).isEqualTo(mysql.getJdbcUrl());
    }
}
```

**实测结果**（本机 Docker 为 OrbStack 29.4.0，镜像 `mysql:8`）：

```
[Testcontainers] MySQL 版本 = 8.4.9
[Testcontainers] 实际连接 = jdbc:mysql://localhost:32768/test
[Testcontainers] 容器地址 = jdbc:mysql://localhost:32768/test
```

两个地址完全一致，说明 `@ServiceConnection` 认出了 `org.testcontainers.mysql.MySQLContainer`。这一点值得单独验证——**Testcontainers 2.0 把 `MySQLContainer` 换了包，Boot 侧的连接工厂要能跟上才行**（关于这个包名变化，见下一节）。

这一层的代价也很明确：4 个用例 **9.28 秒**，比前面所有层加起来还多。容器启动、MySQL 初始化、健康检查，每一步都要真实的时间（如果本机还没有 `mysql:8` 镜像，首次运行还要再加上拉取的时间）。

### 两个容易忽略的点

**容器 Bean 与容器字段，生命周期不一样。** 官方文档专门讲了这件事：

- **容器作为 Spring Bean**：容器 Bean 会在所有其他 Bean 之前创建并启动，在所有其他 Bean 销毁之后停止
- **容器由 Testcontainers 管理**（就是上面 `@Container` 的写法）：不保证顺序，**可能出现容器先于依赖它的 Bean 关闭**

官方给的建议是：**应用 Bean 依赖容器功能时，优先把容器配成 Spring Bean**。写法是把容器声明在 `@TestConfiguration` 里：

```java
@TestConfiguration(proxyBeanMethods = false)
class MyTestConfiguration {

    @Bean
    @ServiceConnection
    MySQLContainer mysqlContainer() {
        return new MySQLContainer("mysql:8");
    }
}
```

**用 `@Bean` 方法时，`GenericContainer` 需要显式的名字提示。** `@ServiceConnection` 判断用哪个连接工厂，靠的是容器的镜像名或容器类型。用 `@Bean` 方法时 Spring Boot **不会调用该方法**去拿镜像名（那会导致过早初始化），只能用方法返回类型判断。所以 `GenericContainer` 这种看不出中间件类型的，必须手写名字：

```java
@Bean
@ServiceConnection(name = "mysql")
public GenericContainer<?> mysqlContainer() {
    return new GenericContainer<>("mysql:8");
}
```

这种“配错了也不报错、只是连不上”的地方，最值得写一条测试固定下来。

### 在多个测试类之间复用容器配置

容器常常要在好几个测试类里用同一套配置。官方给的方案是把容器声明在接口的静态字段上，然后用 `@ImportTestcontainers` 导入：

```java
interface MyContainers {

    @Container
    MySQLContainer mysqlContainer = new MySQLContainer("mysql:8");
}

@TestConfiguration(proxyBeanMethods = false)
@ImportTestcontainers(MyContainers.class)
class MyTestConfiguration {
}
```

注意注解的拼写：`@ImportTestcontainers`（小写 t）在 `org.springframework.boot.testcontainers.context` 包下，而 `@Testcontainers` 是 Testcontainers 自己的注解、在 `org.testcontainers.junit.jupiter` 下。两者长得像，来源完全不同。
