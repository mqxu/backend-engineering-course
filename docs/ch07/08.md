# 八、Quartz：需要持久化的定时任务

`@Scheduled` 有三个做不到的事：任务需要持久化（重启后不丢）、需要集群协调（多实例只执行一次）、需要错过补偿（服务器停机期间该执行的任务在恢复后补上）。Quartz 就是为这三个场景准备的。

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-quartz</artifactId>
</dependency>
```

引入了就自动配置一个 `Scheduler`。默认用内存 JobStore：

```yaml
spring:
  quartz:
    job-store-type: jdbc            # 持久化到数据库
    jdbc:
      initialize-schema: always     # 启动时建 Quartz 的表
```

一个有风险的默认行为要知道：**`initialize-schema` 用的标准脚本会删掉已存在的表**，也就是说每次重启都会清空所有触发器。官方原文：

> By default, the database is detected and initialized by using the standard scripts provided with the Quartz library. These scripts drop existing tables, deleting all triggers on every restart.

生产环境不能这么用——应该是配一次 `always` 建表，之后改成 `never`，或者用自定义脚本（`spring.quartz.jdbc.schema`）。

任务写法是继承 `QuartzJobBean`：

```java
public class StatisticJob extends QuartzJobBean {

    private StatisticService statisticService;   // 通过 setter 注入

    public void setStatisticService(StatisticService statisticService) {
        this.statisticService = statisticService;
    }

    @Override
    protected void executeInternal(JobExecutionContext context) throws JobExecutionException {
        statisticService.rebuild(context.getFireTime());
    }
}
```

注意是 **setter 注入**而不是构造器——Quartz 自己实例化 Job，它需要无参构造器，字段只能靠 setter 带进来。

两个容器相关的细节：

| 需求 | 做法 |
| --- | --- |
| Quartz 用独立的数据库 | 声明 `DataSource` bean 并加 `@QuartzDataSource` |
| Quartz 用独立的事务管理器 | 声明 `TransactionManager` bean 并加 `@QuartzTransactionManager` |

**什么时候真的需要 Quartz**：任务数量多、每个任务要能单独启停和查执行历史、集群环境必须只跑一次、需要持久化。只有一两个简单定时任务的话，`@Scheduled` 加上分布式锁足够，不必引入 Quartz 和它那套数据库表。
