# 二、缓存：把热点查询挡在数据库前面

### 2.1 一行注解带来的变化

先看效果。给 `CategoryService.listAll()` 加上 `@Cacheable`，然后连续调两次：

```text
分类首次 SQL: 1 条，二次 SQL: 0 条
```

第二次一条 SQL 都没发。这个方法的返回值被存进了缓存，第二次调用直接返回缓存里的对象，方法体根本没执行。

再看详情接口 `ResourceService.getById(1L)`：

```text
首次 getById(1) 发出 SQL: 1 条
二次 getById(1) 发出 SQL: 0 条
```

同样是第二次零 SQL。这就是缓存抽象的价值：业务代码里没有一行 `if (cache.containsKey(...))`，只是一个注解。

**但这个“零”是有前提的**。第 6 篇讲过的 `open-in-view: false` 如果没关，Hibernate 的 Session 会一直开到响应渲染完，缓存命中也照样可能触发一次延迟加载——那统计出来的就不是 0 了。

### 2.2 依赖：starter 和实现，两个都要

缓存需要两样东西，缺一不可：

```xml
<!-- 提供 CacheManager 的自动配置与 spring.cache.* 属性 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-cache</artifactId>
</dependency>

<!-- 具体的缓存实现。这里是 Caffeine -->
<dependency>
    <groupId>com.github.ben-manes.caffeine</groupId>
    <artifactId>caffeine</artifactId>
</dependency>
```

只引 `starter-cache` 也能跑，但会退化到 `ConcurrentHashMap` 实现的 simple provider。官方对这一点的原话是：

> The simple provider is not really recommended for production usage, but it is great for getting started and making sure that you understand the features.

（simple 实现其实并不推荐用于生产，但它很适合入门，以及用来确认你理解了各项功能。）

它的问题在于**没有容量上限、没有过期策略**。缓存条目只增不减，长期运行就是一条内存泄漏路径，而且你完全感觉不到——直到某天 OOM。

### 2.3 `@EnableCaching` 不要放主类上

这是官方明确提醒的一条，原文：

> Avoid adding `@EnableCaching` to the main method's application class. Doing so makes caching a mandatory feature, including when running a test suite.

（不要把 `@EnableCaching` 加到 main 方法所在的应用类上。这样做会让缓存成为强制特性，包括在运行测试套件时。）

原因是写测试时踩出来的：缓存是**跨测试共享的全局状态**。如果缓存跟着主类一起被加载，那么测试 A 写完数据、测试 B 读同一个 key，读到的可能是 A 留下的缓存值而不是数据库里的值。断言失败时你盯着 B 的代码看半天，也想不出问题在哪。

所以案例项目把它放进独立的配置类：

```java
@Configuration
@EnableCaching
public class CacheConfig {
}
```

这个类里一行方法都没有。看起来多此一举，但它让切片测试可以绕开缓存，也让“哪些测试带缓存”变成显式的选择。

> **同一个原则适用于 `@EnableScheduling`**。一个每 30 秒执行的任务，在测试套件里可能被触发几十次，轻则刷满日志，重则因为并发写数据让断言随机失败。案例项目同样把它单独放进 `SchedulingConfig`。

### 2.4 自动配置怎么挑缓存实现

如果没有自己声明 `CacheManager`，Spring Boot 会**按固定顺序**探测可用实现。官方给的顺序是：

| 顺序 | 实现 | 触发条件 |
| --- | --- | --- |
| 1 | Generic | 上下文里存在至少一个 `Cache` bean |
| 2 | JCache (JSR-107) | 类路径上有 `CachingProvider`（EhCache 3、Hazelcast 等） |
| 3 | Hazelcast | 有 `HazelcastInstance` 且类路径有 `hazelcast-spring` |
| 4 | Infinispan | 存在 Infinispan 的 Spring 集成 |
| 5 | Couchbase | Spring Data Couchbase 可用且已配置 |
| 6 | Redis | Spring Data Redis 可用且已配置 |
| 7 | Caffeine | 类路径上有 Caffeine |
| 8 | Simple | 以上都没有时的兜底 |

顺序本身有个值得注意的后果：**同时引了 Caffeine 和 Redis 时，Redis 胜出**，因为 6 在 7 前面。想反过来就用 `spring.cache.type` 强制指定：

```yaml
spring:
  cache:
    type: caffeine   # 可选值：generic / jcache / hazelcast / infinispan / couchbase / redis / caffeine / cache2k / simple / none
```

`none` 这个值比它看起来有用。怀疑“数据改了但页面没变”是缓存引起的时，把它改成 `none` 重启，缓存立刻变成空操作。这比去代码里翻注解快得多。

### 2.5 Caffeine 的容量与过期策略

案例项目的配置：

```yaml
spring:
  cache:
    type: caffeine
    cache-names: resourceDetail,categories
    caffeine:
      spec: maximumSize=500,expireAfterWrite=10m
```

`spec` 的字符串格式直接来自 Caffeine 自己的 `CaffeineSpec`。几个常用的维度：

| 维度 | 写法 | 含义 |
| --- | --- | --- |
| 容量 | `maximumSize=500` | 最多 500 条，超出按 LRU 淘汰。**不写就是无上限** |
| 写入过期 | `expireAfterWrite=10m` | 写入后 10 分钟失效，适合“数据本身有保鲜期” |
| 访问过期 | `expireAfterAccess=10m` | 最后一次访问后 10 分钟失效，适合“冷数据可以走” |
| 弱引用 | `weakKeys` / `weakValues` | 允许 GC 回收，一般不需要 |

官方示例用的是 `expireAfterAccess=600s`，案例项目用 `expireAfterWrite=10m`。两者的差别在语义：`expireAfterWrite` 保证数据最多旧 10 分钟；`expireAfterAccess` 会把一直被访问的热数据永久留在缓存里，数据可能旧很久。**对“用户改完要能立刻看到变化”这种诉求，必须用 `expireAfterWrite`。**

`cache-names` 这一行也应该写。它的作用是启动时就建好这两个缓存。不写的话，Caffeine 会按需创建——这本身没问题，但当缓存名写错时，表现出来不是报错而是“缓存不起作用”。更麻烦的是 simple provider 配了 `cache-names` 之后，用到未声明的缓存名会**运行期抛异常**，而不是启动期。

### 2.6 案例项目：哪几个方法该缓存

不是所有查询都值得缓存。判断依据通常是三件事：读的频率、写（失效）的频率、以及结果集大小。

| 方法 | 是否缓存 | 理由 |
| --- | --- | --- |
| `CategoryService.listAll()` | 缓存 | 典型读多写极少，且结果集小（几个分类），变化频率以月计 |
| `ResourceService.getById(id)` | 缓存 | 详情页访问集中，key 是 id，失效容易精确定位 |
| `ResourceService.search(...)` | 不缓存 | 见下 |

`search` 不缓存的原因值得展开。它的方法是：

```java
public PageResult<ResourceResponse> search(Long categoryId, ResourceType type,
                                           String keyword, int page, int size)
```

四个可变参数（`page` 还一直在变），意味着缓存 key 的组合是发散的：同一个用户翻十页就是十个 key，不同关键词又各是一套。结果是**缓存命中率极低而内存占用极高**——命中的那点收益还不够抵消维护成本。

实测也印证了这一点，列表接口两条路径都回库：

```text
列表首次 SQL: 2 条，二次 SQL: 2 条（列表未加缓存）
```

（两条 SQL 分别是对应的 count 查询与主查询，第 6 篇的分页部分解释过。）

列表要提速，正确的方向是搜索引擎或者物化视图，而不是 `@Cacheable`。

### 2.7 写操作的驱逐

缓存最大的风险不是“没缓存上”，而是**改了数据忘了清缓存**。这种 bug 的表现是：用户提交成功、数据库确实改了，但页面上还是旧值，刷新也没用，看起来像“保存失败”。

案例项目的做法是在每个写方法上标注 `@CacheEvict`：

```java
@CacheEvict(cacheNames = CACHE_DETAIL, key = "#id")
@Transactional
public ResourceResponse update(Long id, ResourceUpdateRequest request) { ... }
```

三个参数的取舍：

| 参数 | 用法 | 说明 |
| --- | --- | --- |
| `cacheNames` | 缓存名 | 与 `@Cacheable` 上的名字必须一致，写错就是两个互不相干的缓存 |
| `key` | 定位要清的条目 | `#id` 是 SpEL，取名为 `id` 的方法参数。不写 key 则用默认 key 策略 |
| `allEntries` | 清空整个缓存 | 新增操作用它（新条目会影响哪些查询结果无法预知），改动单个条目时不用 |

新增操作用的是 `allEntries = true`：

```java
@CacheEvict(cacheNames = CACHE_DETAIL, allEntries = true)
@Transactional
public ResourceResponse create(ResourceCreateRequest request) { ... }
```

因为新增一条资源后，“哪些 id 的详情受影响”是说不清的（答案是不受影响，但缓存里可能已经存在同名资源的旧判断），全清最省心，代价只是接下来几次查询回库。

`@CacheEvict` 默认在方法**正常返回之后**执行。这个顺序是对的：万一方法抛异常导致事务回滚，缓存不会被误清。想改成方法执行前清可以用 `beforeInvocation = true`，但除非明确知道为什么，否则不要改。

### 2.8 实测：驱逐到底生效没有

“清了缓存”这件事光看代码看不出来，要实测。案例项目的 `CacheBehaviorTest` 用 Hibernate 的 `Statistics` 精确计数：

```java
private long statementCount() {
    return statistics().getPrepareStatementCount();
}
```

`hibernate.generate_statistics=true` 打开后，`getPrepareStatementCount()` 返回的就是累计发出的 JDBC 语句数。读差值比数日志可靠——日志里会混进连接池的探活语句，数着数着就乱了，而且没法写成断言。

实测输出：

```text
首次 getById(1) 发出 SQL: 1 条
二次 getById(1) 发出 SQL: 0 条
缓存中的值类: com.example.resourcehub.dto.ResourceResponse
update 之后缓存中该 key: null
驱逐后再查发出 SQL: 1 条
```

四行分别证明了四件事：

1. 第一次确实回库了（如果这里就是 0，说明缓存里本来有值，测试前提不成立）；
2. 第二次真的没回库；
3. 缓存里躺的是 `ResourceResponse` 而不是 JPA 实体；
4. `update` 之后 key 被清掉，再查必须回库。

第 3 点值得单独说。缓存里存的**不该是实体对象**。JPA 实体是“托管状态”的，放它进缓存有两个隐患：一是事务结束后它变成游离对象，不同缓存实现序列化它的行为不一致；二是有人从缓存里取出来改了字段，以为能通过脏检查写回数据库——实际不会，而且会让内存里的对象和库里的数据长期不一致。所以 `ResourceService` 里做缓存的是返回 DTO 的方法，缓存值类型就是那个不可变的 record。

### 2.9 缓存 key 是怎么生成的

默认策略是 `SimpleKeyGenerator`，规则只有两条：

| 方法签名 | 生成的 key |
| --- | --- |
| 无参数 | `SimpleKey.EMPTY`（一个全局单例） |
| 只有一个参数 | 参数本身 |
| 两个及以上参数 | `SimpleKey` 包装的多参数对象 |

`CategoryService.listAll()` 无参，所以缓存里只有一个条目。`getById(Long id)` 单参，key 就是 `id` 本身——这也是为什么测试里能直接 `cache.get(1L)` 取到值。

多参数时用 `SimpleKey` 有要求：**所有参与 key 的参数必须正确实现 `equals` 和 `hashCode`**。传进来的如果是没重写这两个方法的自定义对象，每次生成的 key 都不相等，缓存永远不命中，而且不报任何错。

要自己控制 key 就写 SpEL：

```java
@Cacheable(cacheNames = "resourceDetail", key = "#id")
@Cacheable(cacheNames = "resourceSearch", key = "#categoryId + '-' + #page")
@Cacheable(cacheNames = "byTitle", key = "#title.toLowerCase()")
```

> ⚠ **参数名不是一定拿得到的**。SpEL 里的 `#id` 依赖编译时保留参数名（`-parameters`）。Spring Boot 的父 POM 已经开好了这个编译选项，但如果你自己改了 `maven-compiler-plugin` 配置或换了构建工具，`#id` 会突然报“找不到变量”。稳妥的写法是用位置参数 `#p0` / `#a0`，或者直接在参数上加 `@Cacheable` 的 `keyGenerator`。

### 2.10 自调用陷阱：注解写了但不生效

这是 Spring 缓存最经典的一个坑，案例项目里也留了痕迹。看 `CacheWarmupJob` 的注释里提到的写法：

```java
// 这样写缓存注解是不会生效的
@Scheduled(fixedDelay = 60000)
public void warmup() {
    this.loadCategories();          // 自调用
}

@Cacheable("categories")
public List<CategoryResponse> loadCategories() { ... }
```

`warmup()` 里的 `this.loadCategories()` 是**同一个对象内部的直接方法调用**，不经过 Spring 的代理对象，所以 `@Cacheable` 那一层拦截根本没机会执行。方法照常跑，缓存什么都没做，也不报错。

问题出在机制上：Spring 的缓存（以及 `@Transactional`、`@Async`）都靠**代理**实现。外部调用者拿到的是代理，代理在转发前后做增强；而 `this` 指向的是原始对象，绕过代理就直接执行了真实方法。

三个解法：

| 解法 | 做法 | 适用 |
| --- | --- | --- |
| 拆类 | 把带注解的方法挪到另一个 bean | 最干净，首选 |
| 注入自己 | `@Autowired private XxxService self;` 然后 `self.loadCategories()` | 快速修补，注意别写出循环依赖 |
| 换实现 | 直接用 `CacheManager` 手写缓存逻辑 | 逻辑复杂或需要精确控制时 |

案例项目的 `CacheWarmupJob` 选的是第三种——它本来就要“清”缓存而不是“读”缓存，直接操作 `CacheManager` 反而更直白：

```java
Cache cache = cacheManager.getCache(CACHE_CATEGORIES);
cache.clear();
```

### 2.11 穿透、雪崩与一致性

这三个词经常一起出现，但它们描述的是三个不同的问题，解法也不一样：

| 问题 | 场景 | 应对 |
| --- | --- | --- |
| 缓存穿透 | 查询一个**不存在**的数据。缓存里没有 → 查库，库里也没有 → 不写缓存 → 下次还查库 | 缓存空值（`unless` 控制），或对不存在的 id 也写入一个短 TTL 的占位值 |
| 缓存击穿 | 某个**热点 key** 恰好过期，瞬间大量请求同时回库 | 加互斥锁只放一个请求回库，其余等待；或对热点数据不设过期、靠主动刷新 |
| 缓存雪崩 | **大批 key 同时过期**，或缓存服务整体挂掉 | 过期时间加随机扰动，避免同一秒集中失效；做好降级（直接回库但不至于全挂） |

关于一致性，需要先把预期放对：**本地缓存（Caffeine）在多个实例之间是不一致的**。实例 A 改了数据清了缓存，实例 B 的缓存里还是旧值，直到过期。这是本地缓存的固有限制，不是配置问题。

要跨实例一致就必须用集中式缓存（Redis），而且要注意官方专门提过的一点：

> By default, a key prefix is added so that, if two separate caches use the same key, Redis does not have overlapping keys and cannot return invalid values. We strongly recommend keeping this setting enabled if you create your own `RedisCacheManager`.

（默认会加 key 前缀，避免两个不同缓存用了相同 key 时互相覆盖、返回错误值。自建 `RedisCacheManager` 时强烈建议保留这个设置。）

普通业务的取舍是：**接受秒级不一致，用较短的 TTL 兜住**。真需要强一致的地方，就不该用缓存，直接查库。

### 2.12 缓存出问题时怎么定位

遇到“数据改了但页面没变”，按这个顺序查，能覆盖绝大多数情况：

| 步骤 | 操作 | 判断 |
| --- | --- | --- |
| 1 | 把 `spring.cache.type` 改成 `none` 重启 | 问题消失 → 确定是缓存，继续往下；没消失 → 问题在别处 |
| 2 | 检查写方法上有没有 `@CacheEvict` | 漏了就是根因，最常见 |
| 3 | 核对 `cacheNames` 是否两边一致 | 名字不同等于两个缓存，清了也没用 |
| 4 | 检查 `key` 表达式 | key 不匹配时清的是别的条目，同样等于没清 |
| 5 | 确认方法是不是被自调用 | 见 2.10 |
| 6 | 确认清缓存的代码走的是代理对象 | 通过注入的 bean 调用，不要用 `this` |
