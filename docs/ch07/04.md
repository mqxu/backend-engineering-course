# 四、调用外部服务：RestClient

### 4.1 三个客户端怎么选

官方给出的选型依据只有两句话：

> If you are developing a non-blocking reactive application and you're using Spring WebFlux, then you can use `WebClient`. If you prefer imperative APIs then you can use `RestClient` or `RestTemplate`.

| 客户端 | 定位（官方原文） | 什么时候用 |
| --- | --- | --- |
| `WebClient` | "provides a functional style API and is fully reactive" | 项目本身就是 WebFlux / Reactor |
| `RestClient` | "provides a similar functional API, but is imperative rather than reactive" | **命令式项目的默认选择** |
| `RestTemplate` | "predates `RestClient` and is the classic way that many applications use to call remote REST services" | 官方建议“仅在已有存量代码不想迁移时选用” |

案例项目是 Spring MVC，所以用 `RestClient`。

### 4.2 `RestTemplate` 到底废弃了没有

网上流传“`RestTemplate` 已在 Spring 7 中废弃”。这个说法**不准确**。直接反编译 Spring Framework 7.0.9 的 `spring-web` 看字节码：

```bash
unzip -l spring-web-7.0.9.jar | grep RestTemplate
javap -v org/springframework/web/client/RestTemplate.class | grep -i Deprecated
```

结果：`RestTemplate` 上**没有** `@Deprecated` 标记，仍然可以正常使用。官方文档里的措辞也是“经典的（classic）方式”，而不是“已废弃（deprecated）”，只是建议新代码用 `RestClient`。

这个区别有实际意义：如果你维护的项目里到处是 `RestTemplate`，不需要为了“避免编译警告”去做一遍迁移。真正该迁移的理由是代码可读性和统一的请求工厂配置，而不是“它要没了”。

### 4.3 Boot 4 把它拆成了独立模块

这是本篇最容易卡住的一处，实测踩过。4.x 把原来堆在 `spring-boot-autoconfigure` 里的自动配置按技术栈拆成了独立模块，REST 客户端这一块被拆成两个：

| 模块 | 提供什么 |
| --- | --- |
| `spring-boot-restclient` | `RestClient.Builder` / `RestTemplateBuilder` 这两个原型 bean、`RestClientCustomizer`、`RestClientSsl`、`RestTemplateAutoConfiguration` |
| `spring-boot-http-client` | `HttpClientSettings`、`ClientHttpRequestFactoryBuilder`、`spring.http.clients.*` 属性 |

而且**这两个模块都没有对应的 starter**，也不是 `starter-webmvc` 的传递依赖——`starter-webmvc` 只带来 `spring-boot-http-converter`（管 JSON 编解码）。所以要显式引：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-restclient</artifactId>
</dependency>
```

`spring-boot-restclient` 会传递引入 `spring-boot-http-client`，所以引一个就够。

不引的后果很难自己看出来——注入 `RestClient.Builder` 时报的是：

```text
Parameter 0 of method catalogRestClient in com.example.resourcehub.config.RestClientConfig
required a bean of type 'org.springframework.web.client.RestClient$Builder' that could not be found.
```

它只说找不到 bean，不会提示你“少了哪个模块”，也不会有任何关于自动配置被跳过的线索。而且**这个错误会让整个应用起不来**，不只是那个功能不可用。遇到时第一反应应该是查模块依赖，而不是去写一个 `RestClient.create()` 绕过去——绕过之后 `spring.http.clients.*` 那些配置也一并失效了。

### 4.4 底层 HTTP 库怎么选

`RestClient` 和 `RestTemplate` 本身不实现 HTTP，底下要有个真正的客户端。官方给的检测顺序（**命令式**这一侧）：

| 顺序 | 实现 |
| --- | --- |
| 1 | Apache HttpClient |
| 2 | Jetty HttpClient |
| 3 | Reactor Netty HttpClient |
| 4 | JDK client（`java.net.http.HttpClient`） |
| 5 | Simple JDK client（`java.net.HttpURLConnection`） |

规则是：类路径上有多个时，取最靠前的那个。**什么都不引也不会报错**——JDK 17 起自带的 `HttpClient` 会在第 4 位兜住，所以开箱即用。

要注意的是**响应式侧的顺序不一样**（Reactor Netty → Jetty → Apache → JDK），不要记混。案例项目没引任何额外的 HTTP 库，实际走的是 JDK HttpClient。

要指定实现用配置：

```yaml
spring:
  http:
    clients:
      imperative:
        factory: jetty     # 命令式客户端用 Jetty
      reactive:
        connector: jetty   # 响应式客户端用 Jetty
```

### 4.5 构建客户端与超时

案例项目的 `RestClientConfig`：

```java
@Configuration(proxyBeanMethods = false)
public class RestClientConfig {

    @Bean
    public RestClient catalogRestClient(RestClient.Builder builder, ExternalApiProperties properties) {
        HttpClientSettings settings = HttpClientSettings.defaults()
                .withConnectTimeout(properties.connectTimeout())
                .withReadTimeout(properties.readTimeout());

        ClientHttpRequestFactory requestFactory =
                ClientHttpRequestFactoryBuilder.detect().build(settings);

        return builder
                .baseUrl(properties.baseUrl())
                .requestFactory(requestFactory)
                .defaultHeader(HttpHeaders.ACCEPT, MediaType.APPLICATION_JSON_VALUE)
                .build();
    }
}
```

几个设计决定：

**注入 `RestClient.Builder`，不要自己 `RestClient.create()`。** 自动配置的那个 builder 已经预装了两样东西：从 classpath 探测出来的 `HttpMessageConverter` 集合（JSON 支持靠它），以及按 `spring.http.clients.*` 配好的请求工厂。自己 create 出来的什么都没有，还得手工配转换器。

**`ClientHttpRequestFactoryBuilder.detect()` 而不是写死实现。** 它按 4.4 的顺序自动挑。写死的话，将来换库要改代码。

**不声明一个共享的 `RestClient` bean。** 官方文档的示例都是“你自己构建客户端”，因为一个应用往往会调多个外部服务，各自的超时、鉴权头、基地址都不同。把不同服务的配置塞进一个共享 bean，早晚会缠在一起。

**超时必须设。** 底层 HTTP 库的默认值是“无限等待”。第三方服务挂起不响应时，你的线程会被逐个占满，最后表现成“本应用整体不可用”——故障从下游传导过来。官方在邮件那一章专门提醒过同样的问题（见 7.2）。

全局默认值可以在 yml 里兜底：

```yaml
spring:
  http:
    clients:
      connect-timeout: 2s
      read-timeout: 5s
      redirects: follow        # 可选 dont-follow / follow / normal
```

这一组属性作用于自动配置的 `RestClient.Builder`。单客户端需要不同的值时，像案例项目那样单独设 `requestFactory` 覆盖。

> ⚠ **`RestClient.Builder` 是有状态的**。官方原话：
>
> > `RestClient.Builder` instances are stateful: Any change on the builder is reflected in all clients subsequently created with it.
>
> 也就是说，注入进来的 builder 上做一次 `defaultHeader(...)`，之后从同一个 builder 建出来的客户端都会带上这个头。需要互不影响的多个客户端时，要 `builder.clone()`。这一点和 `RestTemplateBuilder` 的行为相反——后者每次调用返回新实例，定制只影响当次。

### 4.6 异常分类：三类失败，三种处理

这是调用外部接口最关键的部分，也是案例项目 `ExternalCatalogService` 的重点。失败分三类：

| 类型 | 触发条件 | 抛出的异常 | 该返回什么 |
| --- | --- | --- | --- |
| 对方明确报错 | 4xx / 5xx | `RestClientResponseException` | 按状态码分流，见下 |
| 连不上 | 超时、DNS 失败、连接被拒 | `ResourceAccessException` | 502 |
| 反序列化失败 | 对方返回的结构和预期不符 | `RestClientException` 子类 | 502 |

具体到业务语义的分流：

```java
try {
    return catalogRestClient.get()
            .uri("/items/{id}", id)
            .retrieve()
            .body(ExternalCatalogItem.class);
} catch (RestClientResponseException ex) {
    int status = ex.getStatusCode().value();
    if (status == 404) {
        throw BusinessException.notFound("外部目录中不存在 id=" + id);
    }
    if (status == 401 || status == 403) {
        throw BusinessException.badGateway("外部目录服务拒绝访问，请检查密钥配置");
    }
    throw BusinessException.badGateway("外部目录服务返回 " + status);
} catch (ResourceAccessException ex) {
    throw BusinessException.badGateway("外部目录服务不可达：" + ex.getMessage());
}
```

三个判断值得说明：

**为什么 404 要单独处理。** 404 是“这个数据确实不存在”，属于业务语义上的正常结果，返回给前端应该是 404。如果把它和 5xx 一起笼统处理成“调用失败”，前端就没法区分“没有这个资源”和“系统坏了”，只能给用户看一个通用错误页。

**为什么 401/403 要换成 502。** 密钥配置错误是**我们这边能修**的问题，不是对方的故障。但从调用方的角度看，它既不是“你的请求有错”（400），也不是“我的服务炸了”（500）。502 表达的是“我背后的第三方不给力”，语义准确。

**为什么超时不能用 500。** 这是最常见也最容易漏的。线程池被占满、参数配错、网络抖动，最后都落到 `ResourceAccessException`。如果不单独 catch，它会一直冒到兜底的 `Exception` 分支变成 500，运维看到的就是“服务端内部错误”，会去翻自己这边的日志和代码——而真正的根因在别人的服务上。案例项目为此专门在 `BusinessException` 里加了一个 502 的工厂方法：

```java
public static BusinessException badGateway(String message) {
    return new BusinessException(50200, HttpStatus.BAD_GATEWAY, message);
}
```

**另一个原则：外部响应对象不要直接当接口返回值往外传。** 案例项目里定义了自己的 record：

```java
public record ExternalCatalogItem(Long id, String title, String license) { }
```

外部字段改名、加字段、换类型时，改动被限制在这一个类里，不会顺着调用链扩散到 Controller 和前端。直接用对方的 DTO 当返回值，等于把对方的数据结构变成你自己的公开接口。

### 4.7 实测：六条路径逐条验证

外部服务的失败路径在真机上极难复现——你没法让第三方随时返回 500。案例项目用 `MockRestServiceServer` 解决这个问题：

```java
private final RestClient.Builder builder = RestClient.builder().baseUrl(BASE_URL);
private final MockRestServiceServer server = MockRestServiceServer.bindTo(builder).build();
```

它挂到 builder 上，把底层请求工厂替换成一个假的：请求照常构造、URI 和请求头照常参与断言，但不会真的连出去。所以**整套测试不启动 Spring 容器、不需要网络**，跑完只要 100 毫秒上下。

覆盖的六条路径：

| 测试 | 构造的响应 | 断言的重结果 |
| --- | --- | --- |
| 正常返回 | 200 + JSON | 三个字段逐个对上 |
| 对方 404 | 404 | `HTTP 404`，业务码 `40400` |
| 对方 500 | 500 | `HTTP 502`，业务码 `50200` |
| 对方 403 | 403 | 消息里含“密钥” |
| 开关关闭 | 不发请求 | 消息里含“未启用” |
| 传输层失败 | 抛 `SocketTimeoutException` | `HTTP 502` |

**最后一条本来是最想验证的**：超时这种“底层抛 IOException”的情况，Spring 会不会包成 `ResourceAccessException` 让我的 catch 接住？实测结果是会——测试通过，说明 `RestClient` 确实把传输层的 IO 异常包装成了 `ResourceAccessException`。这条如果只靠读文档是没法确认的，而一旦它没包装，超时就会漏到兜底分支变成 500，属于上线后才发现的类型。

还有一条值得注意的测试技巧：**“开关关闭”那条故意不注册任何 `server.expect`**。如果代码在开关关闭时仍然发出了请求，`MockRestServiceServer` 会因为收到未预期的请求而报错——这就把“提前返回”这个断言变成了“连请求都没发”，比只断言异常类型更有力。

### 4.8 重试

`RestClient` 本身不带重试，需要的话用 Spring Retry 或自己包一层。但**先想清楚哪些失败该重试**：

| 失败类型 | 该重试吗 | 理由 |
| --- | --- | --- |
| 连接超时 | 该 | 通常是瞬时网络问题 |
| 读超时 | **要谨慎** | 请求可能已经被对方执行了，重试会造成重复操作 |
| 429 限流 | 该，但要按 `Retry-After` 退避 | 立刻重试只会加剧限流 |
| 5xx | 该 | 对方瞬时故障 |
| 4xx（除 429） | **不该** | 请求本身有问题，重试多少次都一样，还白占线程 |
| 幂等写操作 | 可以 | 但要有幂等键 |

没有退避策略的重试比不重试更糟：三个服务互相调用、每个都重试三次，一次故障会被放大成 27 次请求，直接把下游打穿。

### 4.9 注解式 HTTP 接口

如果外部服务的接口很多，可以用声明式的方式，写接口不写实现：

```java
@HttpExchange("/items")
public interface CatalogClient {

    @GetExchange("/{id}")
    ExternalCatalogItem findById(@PathVariable Long id);

    @PostExchange
    ExternalCatalogItem create(@RequestBody ExternalCatalogItem item);
}
```

用 `@ImportHttpServices` 导入：

```java
@Configuration(proxyBeanMethods = false)
@ImportHttpServices(group = "catalog", types = CatalogClient.class)
public class CatalogClientConfig {
}
```

分组的意义在于配置可以按服务隔离，前缀是 `spring.http.serviceclient.<group>`：

```yaml
spring:
  http:
    serviceclient:
      catalog:
        base-url: https://catalog.example.com/api
        connect-timeout: 2s
        read-timeout: 3s
```

注意官方特别提醒：**服务端的 API 版本配置不会自动传给客户端**，客户端要显式配。

接口少、逻辑简单时没必要上这套——一个 `RestClient` 顶多几十行，加一层抽象反而多一处要理解的东西。
