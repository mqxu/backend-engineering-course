# 五、配置里的 Duration：一个不会报错的坑

超时这类配置用 `Duration` 类型接收，好处是能带单位：

```yaml
activity-server:
  external-api:
    connect-timeout: 500ms
    read-timeout: 90s
```

`500ms`、`90s`、`1m`、`1h`、`1d` 都能被正确解析，实测确认。`Duration` 甚至能接 ISO-8601 格式（`PT2S`）。

**但有个不会报错、只会静默出错的写法**：不带单位的裸数字。

实测：

```yaml
activity-server:
  external-api:
    read-timeout: 3000
```

这里 `3000` 被解释成 **3000 毫秒**，也就是 3 秒。能绑定成功，不报任何错。

于是灾难场景是这样的：有人想让读超时是 3 秒，写下 `read-timeout=3`。系统接受它，解释为 **3 毫秒**。然后所有外部调用都会超时，而配置本身完全合法——你会去查网络、查对方服务、查线程池，唯独不会怀疑那一行配置。

**结论：Duration 类型的配置永远带上单位。** 这条规则没有例外，因为“不加单位也能跑”恰恰是它危险的地方。如果要更保险，可以在配置类上关掉裸数字的支持，让这类写法直接启动失败——代价是它也挡住了合法的毫秒写法，取舍看团队习惯。

顺带记一下 `@DefaultValue` 的边界：它只在**属性完全缺席**时生效。配了但配成空值（`base-url:`）会走到校验那一层报错，而不是回退到默认值。这个行为是对的——把配置显式写空，意图通常是“关掉它”，静默回退到默认值反而更糟。
