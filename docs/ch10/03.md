# 10.3 健康检查：内置组件与自定义实现

### 一台真实运行的机器上有什么

不配任何自定义检查时，`/actuator/health` 已经会汇总一批内置组件。实测这台机器（写了 H2 数据源、`show-details: always`、打开探针）的输出是：

```json
{
  "components": {
    "db":            { "status": "UP", "details": { "database": "H2", "validationQuery": "isValid()" } },
    "diskSpace":     { "status": "UP", "details": { "total": 994662584320, "free": 429614133248, "threshold": 10485760, "exists": true } },
    "livenessState": { "status": "UP" },
    "ping":          { "status": "UP" },
    "readinessState":{ "status": "UP" },
    "ssl":           { "status": "UP", "details": { "expiringChains": [], "invalidChains": [], "validChains": [] } },
    "storage":       { "status": "UP", "details": { "endpoint": "https://storage.activity-server.local", "region": "cn-north", "latencyMs": 0 } }
  },
  "groups": ["liveness", "readiness"],
  "status": "UP"
}
```

其中 `storage` 是我们自己写的，其余都是内置的。**`ssl` 是 Boot 4.0 新增的组件** —— 核实依据是它的源码上写着 `@since 4.0.0`（`org.springframework.boot.health.application.SslHealthIndicator`）。它检查证书链是否即将过期或已失效，对做过 HTTPS 的服务挺有用，3.x 时代没有这个内置检查。

`ping` 是那个“进程还在跑”的最小检查，`livenessState` / `readinessState` 是下面 10.4 要讲的探针状态。

### 自定义检查：把细节带出来

```java
@Component
public class StorageHealthIndicator implements HealthIndicator {

    private final ObjectStorageClient client;
    private final StorageProperties properties;

    public StorageHealthIndicator(ObjectStorageClient client, StorageProperties properties) {
        this.client = client;
        this.properties = properties;
    }

    @Override
    public Health health() {
        ObjectStorageClient.Probe probe = client.probe();

        if (!probe.success()) {
            // down 时把原因带进详情。show-details 默认是 never，
            // 所以这段内容不会出现在匿名请求的响应里 —— 详见配置说明。
            return Health.down()
                    .withDetail("endpoint", properties.endpoint())
                    .withDetail("region", properties.region())
                    .withDetail("error", probe.error())
                    .build();
        }

        Health.Builder builder = Health.up()
                .withDetail("endpoint", properties.endpoint())
                .withDetail("region", properties.region())
                .withDetail("latencyMs", probe.elapsed().toMillis());

        // 慢但没坏：仍然是 UP，但额外标一个状态位，
        // 让看板能区分"正常"和"能撑住但已经吃力"。
        if (probe.elapsed().compareTo(properties.slowThreshold()) > 0) {
            builder.withDetail("slow", true)
                    .withDetail("slowThresholdMs", properties.slowThreshold().toMillis());
        }
        return builder.build();
    }
}
```

三个要点：

**组件名是 bean 名去掉 `HealthIndicator` 后缀。** 类是 `StorageHealthIndicator`，bean 名就是 `storageHealthIndicator`，在响应里这条记录叫 `storage`。这个规则决定了你在 `management.endpoint.health.group.*.include` 里写什么名字，也在 `$.components.storage.status` 这类断言路径里体现出来。实测断言的正是这个：

```java
json.extractingPath("$.components.storage.status").isEqualTo("UP");
json.extractingPath("$.components.db.status").isEqualTo("UP");
json.extractingPath("$.components.diskSpace.status").isEqualTo("UP");
```

**`withDetail` 里的东西默认看不见。** `management.endpoint.health.show-details` 默认是 `never`，所以匿名请求只看得到 `{"status":"UP"}`。这属于设计如此：健康检查的详情会告诉外部调用方你用了什么数据库、连的是哪个地址、证书什么时候过期。示例里为了能直接观察，开成了 `always`，**上线前必须改回去**：

```yaml
management:
  endpoint:
    health:
      # never（默认）不显示各组件详情；when-authorized 需要配合角色。
      # 这里用 always 是为了让示例输出可直接观察 —— 上线前必须改回 never
      # 或者 when-authorized。
      show-details: always
      show-components: always
```

`show-components` 与 `show-details` 是两件事：前者只控制“列出哪些组件及其状态”，后者控制“每个组件里有哪些细节”。想看组件列表但不想暴露细节，就只开 `show-components`。

**`Health.down()` 会让 HTTP 状态码变成 503。** 这一点是健康检查能接负载均衡的前提 —— 探测方大都只看状态码：

```java
@Test
@DisplayName("存储不可用时整体状态变 DOWN，HTTP 状态码跟着变成 503")
void healthGoesDownWithStorage() {
    storageClient.setAvailable(false);

    AbstractJsonContentAssert<?> json = assertThat(mvc.get().uri("/actuator/health").exchange())
            // 这一步是健康检查接负载均衡的关键：
            // 状态码必须是 5xx，否则探测方只看状态码时会以为一切正常
            .hasStatus(503)
            .bodyJson();

    json.extractingPath("$.status").isEqualTo("DOWN");
    json.extractingPath("$.components.storage.status").isEqualTo("DOWN");
    json.extractingPath("$.components.db.status").isEqualTo("UP");
}
```

顺带一个细节：健康状态是**上下文里的共享状态**。测试改了存储可用性，用例结束必须还原，否则后面的用例会因为“存储还是 down 的”而莫名其妙地失败：

```java
@AfterEach
void restoreStorage() {
    storageClient.setAvailable(true);
    storageClient.setArtificialLatency(null);
}
```

### 关掉不想要的检查

某些依赖的健康检查会带来噪音。比如引了 Redis 但并不关键，就不该让它的抖动把整个服务标成 DOWN：

```yaml
management:
  health:
    diskspace:
      enabled: true
    redis:
      enabled: false
```

每个内置检查都有一个 `management.health.<id>.enabled` 开关，自定义检查按同样的规则响应 —— 前提是它用 `@ConditionalOnEnabledHealthIndicator` 配合。
