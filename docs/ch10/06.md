# 10.6 指标：Micrometer 与自定义 Meter

### 注入注册表，别用静态方法

指标代码最要紧的一条约定，在构造函数签名里就体现出来了：

```java
@Component
public class ResourceMetrics {

    private static final String DOWNLOADS = "resourcehub.resource.downloads";
    private static final String UPLOADS = "resourcehub.resource.uploads";

    private final MeterRegistry registry;

    /** 按资源类型预建的下载计数器，标签在构造时就固定下来 */
    private final Map<ResourceType, Counter> downloadCounters;

    /** 同上，上传计数器 */
    private final Map<ResourceType, Counter> uploadCounters;

    /** 删除次数。不带 type 标签：删除动作的排查价值和类型关系不大 */
    private final Counter deleteCounter;

    /** 删除时目标不存在的次数。单列一条，因为它的含义是"调用方可能有问题" */
    private final Counter deleteMissingCounter;

    /** 下载接口的耗时分布 */
    private final Timer downloadTimer;

    public ResourceMetrics(MeterRegistry registry) {
        this.registry = registry;

        this.downloadCounters = new EnumMap<>(ResourceType.class);
        this.uploadCounters = new EnumMap<>(ResourceType.class);
        for (ResourceType type : ResourceType.values()) {
            downloadCounters.put(type, Counter.builder(DOWNLOADS)
                    .description("资源被下载的次数")
                    .tag("type", type.name())
                    .register(registry));
            uploadCounters.put(type, Counter.builder(UPLOADS)
                    .description("资源被上传的次数")
                    .tag("type", type.name())
                    .register(registry));
        }

        this.deleteCounter = Counter.builder("resourcehub.resource.deletes")
                .description("资源被删除的次数")
                .register(registry);

        this.deleteMissingCounter = Counter.builder("resourcehub.resource.deletes.missing")
                .description("删除时目标不存在的次数")
                .register(registry);

        this.downloadTimer = Timer.builder("resourcehub.resource.download.duration")
                .description("单个资源下载的处理耗时")
                // 打开直方图，导出端才算得出 P95 / P99
                .publishPercentileHistogram()
                .register(registry);
    }
```

**不要用 `Metrics.counter("x")` 这类静态方法。** 它们写的是全局注册表，Spring 的公共标签、`MeterFilter`、导出配置全都不生效，测试里也换不掉。这个代价在测试里立刻显现 —— 因为构造函数收的是 `MeterRegistry`，指标可以完全不启动 Spring 地测：

```java
class ResourceMetricsTest {

    private SimpleMeterRegistry registry;
    private ResourceMetrics metrics;

    @BeforeEach
    void setUp() {
        registry = new SimpleMeterRegistry();
        metrics = new ResourceMetrics(registry);
    }
```

`SimpleMeterRegistry` 是 Micrometer 自带的内存实现。4 个用例跑 **6 毫秒**，断言就是普通的 Java 断言。如果业务代码里写的是静态方法，这个测试根本没法写：全局注册表是进程级单例，用例之间互相污染，也没法在每个用例前清空。

### 指标名不要挂高基数标签

`type` 是 `ResourceType` 枚举，取值有限，这是最典型的低基数标签。**如果把 `resourceId` 当标签，每个资源一条时间线，几千个资源就能把监控系统打爆** —— 标签基数问题是监控系统最常见的事故原因，比指标写错更致命。

### 一个实测踩到的坑：同名 meter 多出一条空时间线

最初这个类是这样写的：构造器里注册一个不带标签的 `resourcehub.resource.downloads`，运行时再注册一个带 `type` 标签的同名 `Counter`。结果 `/actuator/prometheus` 里出现了**两条**时间线：一条没有任何标签、值恒为 0，另一条带 `type="DOCUMENT"`。

原因是 **Micrometer 的身份判定是“名字 + 标签”而不是只看名字** —— 标签不同就是不同的 meter。多出来的那条 0 值时间线会一直躺在监控里，看板上做聚合时还会把分子分母算错。

正确做法是**把标签组合在构造时一次性建全，运行时只取不建**。这个坑值得写成断言盯住：

```java
@Test
@DisplayName("同名 meter 配不同标签就是不同时间线，彼此独立；不会额外冒出一条无标签的")
void sameNameDifferentTagsAreSeparateMeters() {
    metrics.recordUpload(ResourceType.DOCUMENT);
    metrics.recordUpload(ResourceType.VIDEO);
    metrics.recordUpload(ResourceType.VIDEO);

    assertThat(registry.get("resourcehub.resource.uploads")
            .tag("type", "DOCUMENT").counter().count()).isEqualTo(1.0);
    assertThat(registry.get("resourcehub.resource.uploads")
            .tag("type", "VIDEO").counter().count()).isEqualTo(2.0);

    // 三个枚举值各一条时间线，恰好三条。
    // 这个数字是在盯一个具体的坑：如果顺手在构造器里多注册一个不带标签的同名
    // Counter，这里就会变成 4 —— 多出来的那条空时间线会一路进到 Prometheus，
    // 把看板上的聚合结果算歪。
    assertThat(registry.getMeters().stream()
            .filter(meter -> meter.getId().getName().equals("resourcehub.resource.uploads"))
            .count()).isEqualTo(3);
}
```

### `Timer` 与 `Counter` 的选择

两者语义不同，别混用：

| 类型 | 回答的问题 | 导出成什么 |
| --- | --- | --- |
| `Counter` | 发生了多少次？ | 只增不减的累计值 |
| `Timer` | 发生了多少次 + 每次多久？ | `_count` / `_sum` / `_max` / `_bucket` |
| `Gauge` | 现在是多少？ | 一个瞬时值 |

`Timer` 已经带了计数功能，所以**不要为同一个动作同时注册 `Counter` 和 `Timer`** —— 计数会重复。示例里 `resourcehub.resource.downloads`（Counter）与 `resourcehub.resource.download.duration`（Timer）并存是有意的：前者按类型拆分，用于看业务构成，后者看性能。真要合并的话，用 `Timer` 的 `tag` 也能表达。

`SimpleMeterRegistry` 下 `Timer` 的行为很好预测，所以单元测试可以直接断言总耗时：

```java
@Test
@DisplayName("Timer 记录了调用次数与总耗时")
void timerRecordsCountAndTotalTime() {
    metrics.recordDownload(ResourceType.LINK, Duration.ofMillis(20));
    metrics.recordDownload(ResourceType.LINK, Duration.ofMillis(30));

    var timer = registry.get("resourcehub.resource.download.duration").timer();

    assertThat(timer.count()).isEqualTo(2);
    // SimpleMeterRegistry 直接把 record 的时长累加起来，不做采样
    assertThat(timer.totalTime(java.util.concurrent.TimeUnit.MILLISECONDS))
            .isEqualTo(50.0);
}
```

### 观测别人的数据：`MeterBinder` 与公共标签

指标的定义可以集中在一处，被观测的对象完全不需要知道自己在被观测：

```java
/**
 * 用 {@code MeterBinder} 绑定"别人的数据"。
 *
 * <p>凡是"值的来源是另一个 bean、自己不需要在运行时改它"的指标，
 * 用 {@code MeterBinder} 比在业务类里注入 {@code MeterRegistry} 干净。
 *
 * <p>{@code Gauge} 的第一个参数是<em>取值函数</em>而不是当前值：
 * 注册只发生一次，之后每次抓取指标时都会重新调用它。
 * 所以千万不要写成 {@code Gauge.builder(name, queue.size())} ——
 * 那样记下来的是注册那一刻的常量。
 */
@Bean
public MeterBinder pendingUploads(PendingUploadQueue queue) {
    return registry -> Gauge.builder("resourcehub.upload.pending", queue, PendingUploadQueue::size)
            .description("排队等待上传的文件数")
            .register(registry);
}
```

**`Gauge` 传的是取值函数，不是当前值。** `Gauge.builder(name, obj, ToDoubleFunction)` 这个三参数重载收的是“怎么从对象里取值”，每次抓取时都会重新调用。如果写成 `Gauge.builder(name, queue.size())` 那种传当前值的写法，记下来的就是注册那一刻的常量，之后再也不会变 —— 这类 bug 在图上表现为一条水平直线，很不容易发现。

实测这条指标在 `/actuator/metrics/resourcehub.upload.pending` 里的输出：

```json
{
  "availableTags": [ { "tag": "application", "values": ["resource-hub"] },
                     { "tag": "region", "values": ["cn-north"] },
                     { "tag": "env", "values": ["local"] } ],
  "description": "排队等待上传的文件数",
  "measurements": [ { "statistic": "VALUE", "value": 0.0 } ],
  "name": "resourcehub.upload.pending"
}
```

注意 `measurements` 里的 `statistic` 是 `VALUE` —— 这是 `Gauge` 的特征。`Counter` 是 `COUNT`，`Timer` 会同时给出 `COUNT` 与 `TOTAL_TIME`。

### 公共标签与过滤器

公共标签加在注册表上，会出现在每一条时间线上：

```java
@Bean
public MeterRegistryCustomizer<MeterRegistry> commonTags(StorageProperties properties) {
    return registry -> registry.config()
            .commonTags("application", "resource-hub", "region", properties.region());
}
```

`MeterRegistryCustomizer` 的新包是 `org.springframework.boot.micrometer.metrics.autoconfigure`（见 10.2）。它的另一条路是配置属性：

```yaml
management:
  metrics:
    tags:
      # 静态公共标签。随运行时变化的标签请在 MeterRegistryCustomizer 里加
      env: local
    # 按名字前缀整体关掉某类 meter，比在导出端过滤更省资源
    enable:
      jvm: true
```

两者的分工是：**属性方式拿得到的东西都是常量**，而 `region` 来自 `StorageProperties`，是随配置变化的运行时值，所以放在 Java 里。实测这台机器上最终生效四条公共标签：`application=resource-hub`、`region=cn-north`、`env=local`，再加上导出端自动补的 `main_application_class`。

**公共标签要克制。** 每加一条，时间线数量就乘一次。三条公共标签加上一个 `type` 四值标签，就是 12 条时间线。

需要更复杂的过滤就写 `MeterFilter`：

```java
@Bean
public MeterFilter denyNoisyMeters() {
    return MeterFilter.deny(id -> id.getName().startsWith("resourcehub.internal.debug"));
}
```

这里演示的是按名字前缀丢弃。真实的过滤条件常常还需要按标签判断 —— `MeterFilter` 提供 `deny` / `accept` / `maximumAllowableTags` 等一串工厂方法，其中 `maximumAllowableTags` 可以给某条指标设一个标签数量上限，超过的部分会被归并掉，是防高基数最后一道闸。
