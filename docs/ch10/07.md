# 10.7 Prometheus 端点：实测输出与命名转换

`/actuator/prometheus` 是给抓取端用的，格式与 `/actuator/metrics` 的 JSON 完全不同。实测：

```text
HTTP 200  content-type=text/plain;version=0.0.4;charset=utf-8
总行数: 913
# TYPE 行数: 81
```

前几行长这样：

```text
# HELP application_ready_time_seconds Time taken for the application to be ready to service requests
# TYPE application_ready_time_seconds gauge
application_ready_time_seconds{application="activity-server",env="local",main_application_class="com.example.activity.ObservabilityApplication",region="cn-north"} 2.635
# HELP application_started_time_seconds Time taken for the application to start
# TYPE application_started_time_seconds gauge
application_started_time_seconds{application="activity-server",env="local",main_application_class="com.example.activity.ObservabilityApplication",region="cn-north"} 2.597
```

### 指标名会被改写

这是看板对不上时最先要想到的一件事。Micrometer 的命名规则（点分隔）与 Prometheus 的命名规则（下划线 + 单位后缀）不一样，注册表在导出时会做转换：

| Micrometer 里的名字 | Prometheus 里的名字 |
| --- | --- |
| `activity.signups`（Counter） | `activity_signups_total` |
| `activity.deletes.missing`（Counter） | `activity_deletes_missing_total` |
| `activity.signup.pending`（Gauge） | `activity_upload_pending` |
| `activity.signup.duration`（Timer） | `activity_signup_duration_seconds`（外加 `_count` `_sum` `_max` `_bucket`） |
| `http.server.requests`（Timer） | `http_server_requests_seconds` |

三条规则：

1. **点换成下划线。** `activity.signups` → `activity_signups`
2. **`Counter` 补 `_total` 后缀。** 这是 Prometheus 的约定，`rate()` 之类的函数依赖它
3. **`Timer` 补 `_seconds` 后缀。** 单位被提升到名字里，因为 Prometheus 不记录单位

实测输出里可以看到这个转换后的完整形态：

```text
# HELP activity_signups_total 活动报名通过的次数
# TYPE activity_signups_total counter
activity_signups_total{application="activity-server",env="local",region="cn-north",type="LECTURE"} 0.0
activity_signups_total{application="activity-server",env="local",region="cn-north",type="LINK"} 0.0
activity_signups_total{application="activity-server",env="local",region="cn-north",type="COMPETITION"} 0.0
```

注意 `# HELP` 里的中文描述原样带了出来 —— 这是 `Counter.builder(...).description("活动报名通过的次数")` 那一行的作用。描述不是可选项：抓取端会把它渲染成图表的说明，没有 `HELP` 行的话运维只能靠猜。

### 直方图分桶：算 P95 / P99 的依据

`Timer` 默认只记总数与总耗时，算不出分位数。打开直方图之后才有 `_bucket`：

```text
activity_signup_duration_seconds_bucket{...,le="0.001"} 0
activity_signup_duration_seconds_bucket{...,le="0.001048576"} 0
...
activity_signup_duration_seconds_bucket{...,le="+Inf"} 0
activity_signup_duration_seconds_count{...} 0
activity_signup_duration_seconds_sum{...} 0.0
```

配置侧对应这一段：

```yaml
management:
  metrics:
    distribution:
      # 默认只记总次数与总耗时，算不出分位数。
      # 打开直方图之后导出端才有 _bucket 分位可用来算 P95 / P99 ——
      # 代价是时间线数量变多，所以只给真正关心的指标开。
      percentiles-histogram:
        "http.server.requests": true
```

代价很直接：**每多一个分桶边界，就多一条时间线**。上面那段输出的 `le` 从 `0.001` 一路排到 `+Inf`，一共 77 个分桶 —— 只这一条指标就贡献了 77 条时间线。所以只给真正关心的指标开，别全局打开。

### 测试这个端点

```java
@Test
@DisplayName("抓取端点按 Prometheus 文本格式输出，指标名被规范化，公共标签带在每条时间线上")
void rendersScrapeFormat() {
    assertThat(mvc.post().uri("/api/activities/1/download").exchange()).hasStatusOk();

    assertThat(mvc.get().uri("/actuator/prometheus").exchange())
            .hasStatusOk()
            // 指标名里的点被换成下划线，Counter 补上 _total 后缀
            .bodyText()
            .contains("activity_signups_total")
            .contains("# TYPE activity_signups_total counter")
            // MeterRegistryCustomizer 里加的公共标签会出现在每一条时间线上
            .contains("application=\"activity-server\"")
            .contains("region=\"cn-north\"");
}
```

这里用的是 `bodyText()` 而不是 `bodyJson()` —— `bodyText()` 返回 `StringAssert`，可以直接链式写 `contains`；`bodyJson()` 返回内容断言，要先存成变量再逐条提取（第 9 篇讲过这个差异）。
