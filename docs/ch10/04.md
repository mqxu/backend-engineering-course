# 10.4 存活与就绪：接 K8s 探针

这是健康检查里最容易被配错的一块。两个探针回答的问题完全不同：

| 探针 | 问题 | 挂了以后平台怎么做 |
| --- | --- | --- |
| liveness | 进程还活着吗？ | **重启容器** |
| readiness | 现在能接流量吗？ | 从负载均衡里摘掉，不重启 |

先把探针打开：

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
      group:
        # 存活探针只回答"进程还活着吗"。绝不能把数据库、下游服务塞进来：
        # 外部系统一抖动，K8s 会把所有实例一起重启，故障被放大。
        liveness:
          include: livenessState
        # 就绪探针回答"现在能接流量吗"，可以带上关键依赖。
        # 这里把对象存储加进来，表示"存储不可用时不接新流量"。
        readiness:
          include: readinessState,storage
```

实测两个探针的响应：

```text
GET /actuator/health/liveness
{"components":{"livenessState":{"status":"UP"}},"status":"UP"}

GET /actuator/health/readiness
{"components":{"readinessState":{"status":"UP"},"storage":{...,"status":"UP"}},"status":"UP"}
```

注意 **liveness 组里只有 `livenessState`**，没有任何外部依赖。这就是它与 readiness 的核心区别，也是这条用例要断言的东西：

```java
@Test
@DisplayName("存活探针不包含外部依赖，存储挂了它也照样 UP")
void livenessIgnoresExternalDependencies() {
    storageClient.setAvailable(false);

    AbstractJsonContentAssert<?> json = assertThat(mvc.get().uri("/actuator/health/liveness").exchange())
            .hasStatusOk()
            .bodyJson();

    // 这正是 liveness 与 readiness 必须分开的原因：
    // 外部依赖不可用时，重启进程解决不了任何问题，只会让故障范围扩大
    json.extractingPath("$.status").isEqualTo("UP");
}
```

**把数据库写进 liveness 是线上事故的经典来源。** 数据库抖动 → 所有实例的 liveness 同时失败 → K8s 把所有实例一起重启 → 重启期间连接池重建、缓存清空 → 数据库压力更大。本该是“等 30 秒自动恢复”的问题，被放大成“全站不可用”。

### 组的状态是聚合出来的，不是写死的

这里有个与直觉不符的地方，实测确认过：

```java
@Test
@DisplayName("就绪探针带上了存储，存储挂了就不再接新流量")
void readinessIncludesStorage() {
    storageClient.setAvailable(false);

    AbstractJsonContentAssert<?> json = assertThat(mvc.get().uri("/actuator/health/readiness").exchange())
            .hasStatus(503)
            .bodyJson();

    // 组状态实测是 DOWN 而不是 OUT_OF_SERVICE —— 组是按包含的组件聚合出来的，
    // 里面有一个 DOWN，整个组就是 DOWN。想让它表达成 OUT_OF_SERVICE，
    // 得显式配 group.<name>.status.order 与 http-mapping。
    json.extractingPath("$.status").isEqualTo("DOWN");
    json.extractingPath("$.components.storage.status").isEqualTo("DOWN");
}
```

`readinessState` 本身是 `UP`，但因为组里带了 `storage` 而 `storage` 是 `DOWN`，整个组聚合出来就是 **`DOWN`**，HTTP 状态码 **503**。你可能会期待 `OUT_OF_SERVICE`，但组状态默认按“包含的组件里最差的”来定，不会自动翻译成“停止服务”。

想让 `DOWN` 映射成 `OUT_OF_SERVICE`，得显式配状态顺序与 HTTP 映射：

```yaml
management:
  endpoint:
    health:
      group:
        readiness:
          include: readinessState,storage
          # 让 DOWN 在 HTTP 上仍表示"不接流量"，而不是"服务坏了"
          status:
            http-mapping:
              DOWN: 503
              OUT_OF_SERVICE: 503
```

### 运行时的可用状态由 `ApplicationAvailability` 管

`livenessState` 与 `readinessState` 不是静态的，它们跟着应用生命周期走：容器启动完成前后、收到停止信号后，Spring 会把它们切成 `CORRECT` / `BROKEN`、`ACCEPTING_TRAFFIC` / `REFUSING_TRAFFIC`。所以平滑下线是自动生效的 —— 收到停机信号时，`readinessState` 先变成 `REFUSING_TRAFFIC`，流量被摘走，然后才开始关连接池。这也解释了为什么 readiness 组里的组件状态会在大约一个请求周期内从 200 变 503。
