# 10.8 测试环境里指标导出被换掉了

这一节是本篇最值得记住的一条实测结论，因为它会让一个本该 200 的端点变成 404。

现象：写了一个断言 `/actuator/prometheus` 返回 200 的测试，结果是 **404**。但把应用真的跑起来，同一个端点返回 200。差异不在代码，在测试环境。

根因通过探针拿到了：

```text
REGISTRY = io.micrometer.core.instrument.simple.SimpleMeterRegistry
/actuator/prometheus → 404
```

**`spring-boot-starter-actuator-test` 在 4.x 里传递引入了 `spring-boot-micrometer-metrics-test`。** 这个测试模块注册了一个 `MetricsContextCustomizerFactory`，默认会把真实的指标导出自动配置换掉，只留一个 `SimpleMeterRegistry`（纯内存、查询用）。

这个开关的元数据写得很清楚：

```text
spring.test.metrics.export | 默认 false
  Whether metrics export should be auto-configured in tests.
```

后果是：`MeterRegistry` 注入到的是 `SimpleMeterRegistry`，`PrometheusMeterRegistry` 根本不会被创建，`/actuator/prometheus` 直接 404。而生产运行时不是这样。

要验证导出格式，就必须显式打开：

```java
@SpringBootTest(properties = "spring.test.metrics.export=true")
@AutoConfigureMockMvc
class PrometheusEndpointTest {

    @Autowired
    private MeterRegistry registry;

    @Test
    @DisplayName("打开真实导出后，注入到的就是 Prometheus 自己的注册表")
    void realExportIsRestored() {
        assertThat(registry.getClass().getName())
                .isEqualTo("io.micrometer.prometheusmetrics.PrometheusMeterRegistry");
    }
```

**这个默认值其实是合理的。** 大多数测试并不需要真实导出 —— 断言计数用内存注册表更快也更稳，还省掉 Prometheus 客户端的一系列对象。只有在验证“导出格式对不对”这类事情时才需要把它打开。也就是说：**测试里指标端点的 404 不一定是配置错了**，先想想是不是被这个测试模块换掉了。

顺带一个排查技巧：这类问题看一眼 `registry.getClass().getName()` 就清楚了，比去读配置属性快。上面那条断言同时也是文档 —— 下一个人看到这个测试就知道默认值是什么。
