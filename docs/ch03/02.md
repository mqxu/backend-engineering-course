# 二、@ConfigurationProperties：类型安全的配置绑定

### 2.1 为什么不用 @Value 硬撑

项目刚起步时用 `@Value` 看着挺方便，配置项一多问题就来了：

| 问题 | 具体表现 |
| --- | --- |
| 散落各处 | 同一个配置项在五个类里各写一遍 `@Value("${app.name}")`，改个前缀要全局搜 |
| 无类型校验 | 配置成 `app.max-page-size=abc`，启动时不报错，第一次调用时才抛异常 |
| 无拼写提示 | IDE 无法提示配置项名称，写错了也没人拦着 |
| 无集中校验 | 想约束“这个值必须大于 0”，得在每个使用处各写一遍判断 |

### 2.2 本案例工程的写法：record 构造器绑定

`config/AppProperties.java`

```java
package com.example.resourcehub.config;

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;

/**
 * 自定义配置项。
 *
 * 用 record 做构造器绑定：字段一旦声明就是 final，绑定完成后不可变，
 * 不存在“忘了写 setter 导致配置读不进来”这类问题。
 */
@ConfigurationProperties(prefix = "resource-hub")
public record AppProperties(
        @DefaultValue("资源分享中心") String name,
        @DefaultValue("./storage") String storagePath,
        @DefaultValue("100") int maxPageSize,
        @DefaultValue("匿名用户") String defaultUploader
) {
}
```

对应的配置项：

`application.yml`

```yaml
resource-hub:
  name: 教学资源分享中心
  storage-path: ./storage
  max-page-size: 50
  default-uploader: 系统管理员
```

> **松散绑定：Java 的驼峰对应 yml 里的短横线**
>
> Java 字段 `storagePath` 在 yml 里写 `storage-path`。以下四种写法都能绑定成功，但**推荐统一用短横线**（kebab-case）—— 这是官方推荐风格，也和 `application.yml` 里其他配置项一致：
>
> | yml 里的写法 | 能否绑定 |
> | --- | --- |
> | `storage-path` | ✓ 推荐 |
> | `storagePath` | ✓ 可以 |
> | `storage_path` | ✓ 可以 |
> | `STORAGE_PATH` | ✓ 可以（环境变量常用这种形式） |

### 2.3 注册：为什么必须有 @ConfigurationPropertiesScan

`@ConfigurationProperties` 标注的类**不会被组件扫描发现**，它是另一套机制。三种注册方式：

**方式一：在启动类上扫描（本案例工程的做法）**

```java
@SpringBootApplication
@ConfigurationPropertiesScan        // 扫描主类所在包及子包下的 @ConfigurationProperties
public class ResourceHubApplication {
}
```

**方式二：精确指定**

```java
@SpringBootApplication
@EnableConfigurationProperties(AppProperties.class)
public class ResourceHubApplication {
}
```

**方式三：标注为组件（不推荐，原因见下）**

```java
@ConfigurationProperties(prefix = "resource-hub")
@Component                    // 能生效，但把配置类和组件扫描耦合在一起
public class AppProperties {
}
```

> **方式一为什么更合适**
>
> `@ConfigurationPropertiesScan` 让配置类保持“纯数据对象”，不依赖 Spring 的组件注解。好处是这个类可以直接 `new` 出来写单元测试，也可以被其他模块复用。这也是官方在文档里推荐的做法。

### 2.4 加校验

配置项写错却到运行时才炸，是最费时间的故障之一。加上校验可以让它在启动阶段就暴露：

**带校验的配置类**

```java
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;
import org.springframework.validation.annotation.Validated;

@Validated
@ConfigurationProperties(prefix = "resource-hub")
public record AppProperties(
        @NotBlank String name,
        @NotBlank String storagePath,
        @Min(1) @Max(1000) @DefaultValue("100") int maxPageSize,
        @DefaultValue("匿名用户") String defaultUploader
) {
}
```

需要 `spring-boot-starter-validation` 依赖。校验失败时应用**直接启动失败**，日志里会明确指出哪个属性不合法：

```text
APPLICATION FAILED TO START

Description:

Binding to target org.springframework.boot.context.properties.bind.BindException failed

Property: resource-hub.maxPageSize
    Value: 5000
    Reason: must be less than or equal to 1000
```

> **这与“配置错误晚发现”正好相反**
>
> 把校验放在配置类上，等于把配置错误从“运行期异常”提前成“启动期失败”。对本案例的 `maxPageSize` 尤其有意义 —— 它用来防止前端传 `size=100000` 把数据库拖死，配置错了必须在部署时就拦住。

### 2.5 让 IDE 有提示：配置元数据

引入注解处理器后，IDE 编辑 `application.yml` 时会自动补全自定义配置项，鼠标悬停还能看到 Javadoc：

`pom.xml`

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-configuration-processor</artifactId>
    <optional>true</optional>
</dependency>
```

原理是它在编译期生成 `META-INF/spring-configuration-metadata.json`。字段上的 Javadoc 会变成提示信息，所以**给配置字段写好注释，等于给同事写了配置文档**。
