# 8.1 先想清楚：什么时候真的需要消息队列

消息队列不是架构成熟度的标志，是要付账的。上之前先确认动机属于下面哪一类。

**解耦**：一个动作要触发好几件后续的事（建索引、发通知、记审计、刷缓存）。如果这些事写在同一个方法里，任何一件改动都要重新发版，任何一件变慢都会拖慢主流程。改成发一条事件出去，后续各自订阅。

判断标准很具体：**这些后续动作的失败，是否应该影响主流程？** 用户在页面上点了“上传”，资源已经存好了，此时索引服务挂了，你要让他看到上传失败吗？不该。那就该发事件。

**削峰**：真正的瓶颈是瞬时并发超出下游承受力。例如批量导入时要往检索服务写几万条，直接同步写会把检索服务打挂。用队列把流量摊平到下游能吃的速度。

判断标准：**下游能不能拒绝、能不能排队？** 如果下游是同步接口且必须立即返回结果（比如支付扣款），队列帮不上忙。

**异步**：主流程只需要确认“事情已经受理”，不需要等结果。典型是发邮件、生成报表、跑数据同步。

判断标准：**用户需要等多长时间？** 超过一两秒且他不需要立刻看到结果，就适合异步。

### 不该上消息队列的情况

- **只是想解耦两个类**，而不是解耦两个部署单元。同进程内的模块划分用接口就够了，引入 broker 只会多一个故障点。
- **数据量根本没起来**。QPS 几十、每天几千条记录的系统，数据库直接扛得住，加一个 Kafka 集群等于白送自己一份运维负担。
- **需要强一致**。消息队列的默认语义是最终一致。如果业务要求“扣了库存就必须立刻扣款成功”，那是一个分布式事务问题，不是消息队列能解决的——引入队列反而让它更难推理。

### 引入之后会多出来的四件事

这四件事在后面每一节都会具体碰到，先建立预期：

1. **重复消费**。无论 Kafka 还是 RabbitMQ，都只能保证“至少一次”。消费端必须自己做幂等——同一条消息处理两次，结果要和处理一次一样。
2. **顺序不保证**（RabbitMQ 多消费者场景尤其明显）。要靠分区 key 或单消费者来换顺序。
3. **失败处理要自己设计**。默认行为往往不是你想要的：Kafka 的默认行为是一条消息永远重试，把整个分区堵死。
4. **本地跑不起来**。这直接改变了测试怎么写，本篇最后会专门讲。
