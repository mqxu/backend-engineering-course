# 8.8 发布确认与退回：RabbitMQ 的“发出即忘”

`rabbitTemplate.convertAndSend(...)` 正常返回，只说明消息交给了客户端库。它不代表 broker 收到了，更不代表路由到了队列里。要拿到这两层信息得额外配：

```yaml
spring:
  rabbitmq:
    publisher-confirm-type: correlated
    publisher-returns: true
    template:
      mandatory: true
```

```java
@PostConstruct
void registerCallbacks() {
    rabbitTemplate.setConfirmCallback((correlation, ack, cause) -> {
        if (!ack) {
            log.error("broker 未确认消息 id={} 原因={}", correlation != null ? correlation.getId() : "?", cause);
        }
    });
    rabbitTemplate.setReturnsCallback(returned -> log.error(
            "消息无法路由，被退回：exchange={} routingKey={} replyCode={} replyText={}",
            returned.getExchange(), returned.getRoutingKey(),
            returned.getReplyCode(), returned.getReplyText()));
}
```

两个回调各管一件事，搞混了就排查不出问题：

- **ConfirmCallback**：broker 有没有收到这条消息。没收到说明是连接、权限或者 broker 内部的问题。
- **ReturnsCallback**：broker 收到了，但**路由不到任何队列**（路由键没人绑）。需要同时开 `publisher-returns` 和 `template.mandatory`，缺一个都不会触发。

`correlated` 这个确认类型的作用是让回调能拿到你传进去的 `CorrelationData`，从而知道是哪条消息出问题了。用 `new CorrelationData(String.valueOf(event.activityId()))` 带上业务 ID，日志才有排查价值。

**发送端配了确认，不等于消息一定不丢。** 确认只覆盖“到达 broker”这一段。broker 收到消息但还没落盘就宕机，消息照样丢。要抗这个得用 `publisher-confirm-type: correlated` + 持久化队列 + 持久化消息（`MessageDeliveryMode.PERSISTENT`）三者配合。教学场景不必展开，但要知道确认解决的是哪一段问题。
