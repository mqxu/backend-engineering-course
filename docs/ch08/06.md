# 8.6 RabbitMQ：和 Kafka 不是替代关系

两者的分工用一句话概括：**Kafka 是分布式的追加日志，RabbitMQ 是消息代理。**

| 关注点 | Kafka | RabbitMQ |
| --- | --- | --- |
| 消息消费后 | 保留（按时间或容量过期） | 通常被删除 |
| 想重读历史 | 改消费位点即可 | 做不到 |
| 吞吐量 | 十万级每秒 | 万级每秒 |
| 路由灵活度 | 只有主题 + 分区 | 交换机类型丰富（direct/topic/fanout/headers） |
| 单条消息的复杂路由 | 不擅长 | 擅长 |
| 顺序 | 分区内保证 | 队列内保证（多消费者会打乱） |
| 典型场景 | 事件流、日志、数据管道 | 任务分发、RPC、复杂路由 |

### 拓扑声明

```java
@Configuration(proxyBeanMethods = false)
public class RabbitConfig {

    public static final String EXCHANGE = "resource-hub.events";
    public static final String QUEUE = "resource-hub.events.index";
    public static final String ROUTING_KEY = "resource.event";

    public static final String DLX = "resource-hub.events.dlx";
    public static final String DLQ = "resource-hub.events.dead";
    public static final String DLQ_ROUTING_KEY = "resource.event.dead";

    @Bean
    public TopicExchange resourceEventExchange() {
        return new TopicExchange(EXCHANGE, true, false);
    }

    @Bean
    public Queue resourceEventQueue() {
        return QueueBuilder.durable(QUEUE)
                .deadLetterExchange(DLX)
                .deadLetterRoutingKey(DLQ_ROUTING_KEY)
                .build();
    }

    @Bean
    public Binding resourceEventBinding(@Qualifier("resourceEventQueue") Queue queue,
                                       @Qualifier("resourceEventExchange") TopicExchange exchange) {
        return BindingBuilder.bind(queue).to(exchange).with(ROUTING_KEY);
    }
}
```

`Queue` / `Exchange` / `Binding` 只要注册成 Bean，Boot 的 `RabbitAdmin` 就会在建立连接时去 broker 上声明它们（已存在则跳过）。

**这里有个必须知道的代价：参数一旦改动不会自动覆盖。** 比如给队列加了 `x-message-ttl`，broker 上已有同名队列不会重建，只报一条 `inequivalent arg` 的错误然后停止声明。改队列参数时要手工删掉旧队列，或者直接换个新名字。开发期遇到“配置明明改了却没生效”，先怀疑这个。

**`@Qualifier` 不是多余的**：容器里有两个 `Queue` Bean（业务队列和死信队列）、两个交换机 Bean，按类型注入会有多个候选。写清楚注入哪一个，比依赖参数名匹配稳妥。

### 死信参数为什么要配

死信队列不是可选项。消息被拒绝且不重回队列时，如果没有配 `x-dead-letter-exchange`，broker 就**直接把消息丢掉**——没有日志、没有痕迹。配了死信之后，这些消息落到 `resource-hub.events.dead` 队列里，事后可以人工取出重放。

注意这里的路由键：队列声明用的是 `DLQ_ROUTING_KEY`（`resource.event.dead`），而不是业务路由键。因为死信重新投递时用的是**队列上配的那个 routing key**，而不是原消息的 routing key。配错了消息就会在死信交换机上路由不到任何队列，同样丢掉。
