# 8.2 Kafka：依赖、配置与主题声明

### 一个容易忽略的变化：Boot 4 终于有了 Kafka starter

3.x 时代要用 Kafka，得自己引 `org.springframework.kafka:spring-kafka`，Spring Boot 并没有提供对应的 starter。**4.1.1 新增了 `spring-boot-starter-kafka`**：

```xml
<!--
  Boot 4 新增的 Kafka starter（3.x 时代没有这个坐标，那时要直接引 spring-kafka）。
  它只带来两个依赖：spring-boot-starter 与 spring-boot-kafka。
  KafkaProperties、@KafkaListener 的容器工厂自动配置都搬进了 spring-boot-kafka 模块。
-->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-kafka</artifactId>
</dependency>
```

配套的模块拆分同样是 4.x 的老套路，三个技术栈各拆出一个模块，starter 只是薄薄一层壳：

| starter | 引入的 Boot 模块 | 模块里的自动配置类包名 |
| --- | --- | --- |
| `spring-boot-starter-kafka` | `spring-boot-kafka` | `org.springframework.boot.kafka.autoconfigure` |
| `spring-boot-starter-amqp` | `spring-boot-amqp` | `org.springframework.boot.amqp.autoconfigure` |
| `spring-boot-starter-websocket` | `spring-boot-websocket` | `org.springframework.boot.websocket.autoconfigure.servlet` |

**这带来一个和前面几篇一样的坑**：`KafkaProperties` 的包名从 `org.springframework.boot.autoconfigure.kafka` 变成了 `org.springframework.boot.kafka.autoconfigure`，`RabbitProperties` 从 `org.springframework.boot.autoconfigure.amqp` 变成 `org.springframework.boot.amqp.autoconfigure`。老代码里的 import 会直接编译不过——报的是“找不到符号”，而类名本身没变，很容易查半天。

版本基线（取自官方 `spring-boot-dependencies:4.1.1` 的 BOM）：

| 组件 | 版本 |
| --- | --- |
| spring-kafka | 4.1.1 |
| spring-amqp | 4.1.1 |
| kafka-clients | 4.2.1 |
| spring-integration | 7.1.1 |

### 配置文件

```yaml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    consumer:
      group-id: resource-hub-messaging
      # 新消费组第一次启动时从头读。生产环境一般不这么配，
      # 但测试里必须——否则「消息先发了、消费组还没就位」就会漏掉数据
      auto-offset-reset: earliest
      key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
      value-deserializer: org.springframework.kafka.support.serializer.JacksonJsonDeserializer
      properties:
        "[spring.json.trusted.packages]": com.example.resourcehub.msg
        "[spring.json.value.default.type]": com.example.resourcehub.msg.kafka.ResourceEvent
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JacksonJsonSerializer
      properties:
        # 不随消息发送 Java 类型头，避免消费者被生产者的包名绑死
        "[spring.json.add.type.headers]": false
```

几个点值得说明。

**`properties` 下的键要用 `"[...]"` 包起来**。键里有点号和驼峰（`spring.json.trusted.packages`），YAML 的宽松绑定会把它拆成嵌套结构，必须用方括号转义成一个整体键名。

**`JacksonJsonDeserializer` 而不是 `JsonDeserializer`**。Spring Kafka 4.x 把面向 Jackson 2 的 `JsonSerializer`/`JsonDeserializer` 换成了面向 Jackson 3 的 `JacksonJsonSerializer`/`JacksonJsonDeserializer`/`JacksonJsonSerde`，和 Boot 4 用的 Jackson 3 对得上。

**关掉类型头**（`spring.json.add.type.headers: false`）。默认情况下生产者会把目标类的全限定名写进消息头，消费者据此反序列化。听起来方便，实际很脆：生产者的包名一旦重构，所有还没消费的旧消息就全部反序列化失败。显式关掉、让消费者用 `spring.json.value.default.type` 指定自己的类型，两边才能真正独立演进。

### 主题声明

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnProperty(name = "resource-hub.messaging.kafka-topics.enabled",
        havingValue = "true", matchIfMissing = true)
public class KafkaTopicsConfig {

    @Bean
    public NewTopic resourceEventsTopic() {
        return TopicBuilder.name(KafkaTopics.RESOURCE_EVENTS)
                .partitions(3)
                .replicas(1)
                .build();
    }
}
```

Boot 见到 `NewTopic` 类型的 Bean 就会去 broker 上建主题，已存在则忽略。

**为什么要显式声明，而不是靠 broker 自动创建**：自动创建出来的分区数和副本数取决于 broker 的 `auto.create.topics.enable` 与 `num.partitions` 默认值。生产环境这两个默认值通常是 1 分区 1 副本——分区数决定消费并行度上限，上线后才发现分区不够，就得做数据迁移。副本数更麻烦，1 副本意味着任意一台 broker 挂掉都可能丢数据。

**那个 `@ConditionalOnProperty` 是给测试用的**。不需要 Kafka 的测试（比如只测 WebSocket 的那个）如果还留着这些 Bean，每次启动都会去连一个不存在的 broker，白白等超时。加个开关，测试里关掉即可。开关默认值是 `matchIfMissing = true`，所以生产配置里什么都不用写。
