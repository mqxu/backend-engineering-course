# 8.5 消费失败：不配的话，一条坏消息能堵死整个分区

这是本篇最值得单独拎出来的一节。

**默认行为是“一直重试同一条消息”。** 一条永远处理不成功的消息，会让这个分区的消费位点停在那里不动，后面的消息全部消费不到。而应用看起来一切正常：不报错、不崩溃、日志里只有零星的重试记录，只是业务数据不再更新。等发现的时候，可能已经积压了几个小时。

正确的做法是给一个上限，超过就转入死信主题：

```java
@Configuration(proxyBeanMethods = false)
public class KafkaErrorConfig {

    @Bean
    public DefaultErrorHandler kafkaErrorHandler(KafkaTemplate<String, Object> kafkaTemplate) {
        // 目的地一定要显式指定。DeadLetterPublishingRecoverer 的默认后缀是 "-dlt"（连字符），
        // 而 Boot 的 @RetryableTopic 用的是 ".DLT" —— 两套约定不一致，靠默认值很容易
        // 出现「消息确实进了死信，但进的不是你以为的那个主题」。
        var recoverer = new DeadLetterPublishingRecoverer(kafkaTemplate,
                (record, ex) -> new TopicPartition(KafkaTopics.RESOURCE_EVENTS_DLT, record.partition()));
        var backOff = new FixedBackOff(1000L, 2L);
        var handler = new DefaultErrorHandler(recoverer, backOff);
        // 反序列化失败的消息不该重试——它永远也不会成功，直接进死信
        handler.addNotRetryableExceptions(DeserializationException.class);
        return handler;
    }
}
```

### 实测踩到的那个坑：死信主题的默认后缀

我先按 Spring Boot 的常见写法把死信主题命名成 `activity-server.activity-events.DLT`，配上 `new DeadLetterPublishingRecoverer(kafkaTemplate)`（用默认目的地），测试等了 60 秒也读不到记录：

```
java.lang.IllegalStateException: No records found for topic
```

翻 `DeadLetterPublishingRecoverer` 的常量池才看到默认后缀是 `-dlt`：

```
#939 = String  #940          // \u0001-dlt
```

**连字符，不是点。** 而 Boot 的 `@RetryableTopic` 那一套用的又是 `.DLT`。两套约定并存，靠默认值就很容易“消息确实进了死信，但进的不是你以为的那个主题”。所以我改成显式指定目的地——写清楚，比记住两套默认值可靠。

改完之后，死信内容能完整读出来：

```
@@@KAFKA-DLT@@@ 原消息 partition=0
@@@KAFKA-DLT@@@ 死信 key=99 originalTopic=activity-server.activity-events
  payload={"activityId":99,"title":"boom 触发失败","eventType":"CREATED","operator":"tester",
           "occurredAt":"2026-09-13T13:40:22.538483Z"}
```

三件事得到确认：**key 被保留了**（还是 `99`，说明分区算法对得上）、**原始主题记在头里**（`DLT_ORIGINAL_TOPIC`，事后重放时知道该回到哪里）、**消息体是 JSON 明文**（没变成二进制，能直接看）。

### 还有两个细节

**重试次数是 `retries + 1`**。`FixedBackOff(1000L, 2L)` 表示间隔 1 秒、重试 2 次，总共尝试 3 次。别按“2 次”去估算耗时。

**不可重试的异常要单独声明**。反序列化失败的消息重试一万次也不会成功，只会浪费时间。`addNotRetryableExceptions(DeserializationException.class)` 让这类消息第一次失败就进死信。
