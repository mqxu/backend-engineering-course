# 8.9 消费者确认、prefetch 与重投

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        acknowledge-mode: auto
        prefetch: 10
        retry:
          enabled: true
          max-attempts: 3
          initial-interval: 500ms
```

**`acknowledge-mode`**：默认 `auto`，方法正常返回就 ack、抛异常就 nack。改成 `manual` 才能由代码决定何时 ack——好处是可以“处理完再确认”，代价是漏掉 ack 会让消息一直是 unacked 状态，直到连接断开才重新入队，表现为“消息凭空消失了一段时间又回来了”。

**`prefetch`**：一次预取多少条。默认 250。设太大，消息全堆在消费者的内存里，这个消费者一挂要等连接断开才重新分配；设 1 则吞吐上不去。合理值取决于单条消息的处理耗时：越快，可以越大。

**抛异常后的行为**——这条最容易出事。默认情况下监听器抛异常会**无限重投**，业务上表现为同一条消息被反复处理，日志刷屏。两种改法：

1. 设 `spring.rabbitmq.listener.simple.default-requeue-rejected: false`，异常后不重回队列。
2. 抛 `AmqpRejectAndDontRequeueException`，明确表示“这条消息不要再给我了”。

配了 `listener.retry` 之后，框架在重试耗尽时用的正是第二种机制，消息于是转进死信队列（前提是队列上配了死信参数，见第 8.6 节）。所以这两处配置是一套的：**队列上的死信参数负责“丢到哪里”，监听器的重试配置负责“什么时候丢”**。
