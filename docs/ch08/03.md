# 8.3 生产者：key 决定分区，返回的 Future 默认不等确认

```java
@Component
public class ResourceEventPublisher {

    private final KafkaTemplate<String, ResourceEvent> kafkaTemplate;

    public CompletableFuture<SendResult<String, ResourceEvent>> publish(ResourceEvent event) {
        CompletableFuture<SendResult<String, ResourceEvent>> future =
                kafkaTemplate.send(KafkaTopics.RESOURCE_EVENTS, String.valueOf(event.resourceId()), event);
        future.whenComplete((result, ex) -> {
            if (ex != null) {
                log.error("资源事件发送失败 id={} type={}", event.resourceId(), event.eventType(), ex);
                return;
            }
            var meta = result.getRecordMetadata();
            log.info("资源事件已发送 id={} type={} partition={} offset={}",
                    event.resourceId(), event.eventType(), meta.partition(), meta.offset());
        });
        return future;
    }
}
```

两个容易被忽略的地方。

**第一个：key 用 `resourceId`，是为了换顺序。** Kafka 只用 key 的哈希决定分区，**分区内部严格有序，分区之间不保证**。把 `resourceId` 当 key，同一个资源的“创建 → 修改 → 删除”就必然落到同一分区，消费端看到的就是这个顺序。不指定 key 时消息轮询着往各分区撒，顺序就没了。

这一点可以直接验证。连着发三条 `resourceId` 都是 7 的事件：

```
@@@KAFKA-分区@@@ partitions=[0, 0, 0] offsets=[2, 3, 4]
```

三条全落在分区 0，偏移量 2、3、4 递增。换了 key 是不是一定换分区，**不能断言**——哈希碰撞本来就允许两个不同的 key 落到同一分区，所以测试里只断言“同一个 key 必然同分区”，不要断言“不同 key 必然不同分区”，那种测试迟早会因为数据变化而随机失败。

**第二个：`send()` 返回的 `CompletableFuture` 默认并不等 broker 确认。** 只调 `send()` 不看返回值，消息丢了也没有任何人知道——这是 Kafka 生产者最常见的静默故障。要感知失败必须挂回调（上面那样），或者像测试里那样 `get(timeout, unit)`。
