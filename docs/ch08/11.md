# 8.11 测试这三条链路

这一节是本篇最有实操价值的部分，因为消息相关的代码“本地跑不起来”是常态。三个测试总共 7 个用例，不需要本机装任何中间件，整个 `mvn test` 跑完约 10 秒。

### Kafka：`@EmbeddedKafka` 起一个真 broker

```java
@SpringBootTest
@EmbeddedKafka(partitions = 3,
        topics = {KafkaTopics.RESOURCE_EVENTS, KafkaTopics.RESOURCE_EVENTS_DLT},
        bootstrapServersProperty = "spring.kafka.bootstrap-servers")
class KafkaEventFlowTest {
    // ...
}
```

`@EmbeddedKafka` 在**同一个 JVM** 里起一个真的 Kafka broker（4.x 是 KRaft 模式，不需要 ZooKeeper），所以这不是打桩：分区、偏移量、消费者组、重试、死信走的全是真的那套逻辑。起停各几秒，比 Testcontainers 省一个 Docker，代价是不能跨 JVM 共享。

**`bootstrapServersProperty` 是最关键的一行**。内嵌 broker 监听的端口是随机分配的，只有把地址回填进 `spring.kafka.bootstrap-servers`，Boot 的自动配置才会连到它，而不是去连配置文件里写死的 `localhost:9092`。漏了这行，表现是测试一直等不到消息然后超时。

顺带一个版本细节：`spring-kafka-test` 4.1.1 的依赖里已经是 `kafka-server` 这个模块，不再是老的 `kafka_2.13`——Kafka 4.x 把 broker 拆成了独立的纯 Java 模块。

读死信主题要用原生消费者，`KafkaTestUtils` 提供了便利方法：

```java
Map<String, Object> props = KafkaTestUtils.consumerProps("dlt-check", "true", broker);
props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");
var consumerFactory = new DefaultKafkaConsumerFactory<>(props,
        new StringDeserializer(), new StringDeserializer());

try (Consumer<String, String> consumer = consumerFactory.createConsumer()) {
    broker.consumeFromAnEmbeddedTopic(consumer, KafkaTopics.RESOURCE_EVENTS_DLT);
    ConsumerRecord<String, String> dead = KafkaTestUtils.getSingleRecord(
            consumer, KafkaTopics.RESOURCE_EVENTS_DLT, Duration.ofSeconds(30));
    assertThat(dead.key()).isEqualTo("99");
    assertThat(dead.value()).contains("boom 触发失败");
}
```

三个用例实测结果：

```
@@@KAFKA-收发@@@  topic=activity-server.activity-events partition=0 offset=0
@@@KAFKA-分区@@@  partitions=[0, 0, 0] offsets=[2, 3, 4]
@@@KAFKA-DLT@@@   死信 key=99 originalTopic=activity-server.activity-events
```

### RabbitMQ：`TestRabbitTemplate` 不连 broker

`TestRabbitTemplate` 的 `convertAndSend` 不往 broker 发，而是在已注册的监听器容器里找匹配的、同步调用监听方法。这样在没有 RabbitMQ 的机器上也能测出“队列名写错”“消息转换器对不上”“监听方法签名不对”这三类最常见的接线问题。

**但它有三处必须自己动手，一处不满足就失败。** 这三个坑我全部实际踩过一遍：

**第一，它不会自动出现。** `@RabbitListenerTest` 只注册了一个 `RabbitListenerTestHarness`（负责捕获调用），并**不提供** `TestRabbitTemplate`。反编译 `RabbitListenerTestBootstrap.registerBeanDefinitions` 可以确认，它只注册了 `internalRabbitListenerAnnotationProcessor` 这一个 Bean。所以要自己声明：

```java
@TestConfiguration(proxyBeanMethods = false)
static class RabbitTestSupport {

    @Bean
    TestRabbitTemplate testRabbitTemplate(MessageConverter messageConverter) {
        var template = new TestRabbitTemplate(mockConnectionFactory());
        template.setMessageConverter(messageConverter);
        return template;
    }

    static ConnectionFactory mockConnectionFactory() {
        ConnectionFactory factory = mock(ConnectionFactory.class);
        Connection connection = mock(Connection.class);
        Channel channel = mock(Channel.class);

        given(factory.createConnection()).willReturn(connection);
        given(connection.createChannel(anyBoolean())).willReturn(channel);
        given(channel.isOpen()).willReturn(true);
        return factory;
    }
}
```

**第二，必须配 mock 的连接工厂。** `sendToRabbit` 虽然被重写了，但外层 `execute(...)` 仍然会走“建连接 → 建 channel”这两步。传真实的 `CachingConnectionFactory` 进来，测试直接报 `ConnectException: Connection refused`——它不会优雅地跳过网络。

这里还有一个类型陷阱：**`mock()` 的目标要是 Spring AMQP 自己的 `Connection` 接口**，不是 `com.rabbitmq.client.Connection`。`ConnectionFactory.createConnection()` 返回的是 `org.springframework.amqp.rabbit.connection.Connection`，两者同名不同包，import 错了编译器会给出很奇怪的提示（“boolean 无法转换为 int”，因为选中的是 AMQP 客户端那个 `createChannel(int)`）。

**第三，它必须当 Bean，而且要在测试前把连接工厂换回 mock。** 为什么必须当 Bean：它内部有一个 `@Autowired RabbitListenerEndpointRegistry`，靠它才能找到监听器容器；手工 `new` 出来的这个字段是 `null`，调用时直接 NPE。而一旦当了 Bean，容器里的后处理又会把真实的连接工厂塞回去——所以 `@BeforeEach` 里要再 `setConnectionFactory` 一次：

```java
@BeforeEach
void setUp() {
    inbox.clear();
    template.setConnectionFactory(RabbitTestSupport.mockConnectionFactory());
}
```

**最后是一条边界**：`TestRabbitTemplate` **不解析交换机和绑定关系**，它把第二个 `String` 参数（平时是 routing key 的位置）直接当**队列名**去查找监听器。所以这个测试证明的是“监听器接得上”，证明不了“绑定配得对”——后者要连真 broker 才验得了。

三个用例里有一个专门验证这个边界：

```java
@Test
@DisplayName("队列名写错时立刻报错，而不是静默丢弃")
void unknownQueueNameFailsFast() {
    assertThatThrownBy(() -> template.convertAndSend(RabbitConfig.EXCHANGE, "不存在的队列",
            ActivityEvent.created(44L, "无处投递", "tester")))
            // 原始异常同样被包装：RabbitAccessor 会把 IllegalArgumentException
            // 转成 UncategorizedAmqpException，根因里才留着 "No listener for ..."
            .isInstanceOf(org.springframework.amqp.UncategorizedAmqpException.class)
            .hasRootCauseMessage("No listener for 不存在的队列");
}
```

**顺带学到的一件事：异常在链路上会被包一层。** 监听器抛出的 `IllegalStateException` 会被容器包成 `ListenerExecutionFailedException`，`IllegalArgumentException` 会被 `RabbitAccessor` 转成 `UncategorizedAmqpException`。断言如果只看最外层消息，会看到一句什么也说明不了的 `Listener method ... threw exception`。**断言要落到根因上**（`hasRootCauseMessage`），否则这个测试等于没断言。

```
@@@RABBIT@@@ [RABBIT | 42:CREATED]
```

### WebSocket：真实客户端连真实端口

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class WebSocketStompTest {

    @LocalServerPort
    private int port;

    @Test
    void sendAndReceive() throws Exception {
        var client = new WebSocketStompClient(new StandardWebSocketClient());
        client.setMessageConverter(new JacksonJsonMessageConverter());
        // ...
        var session = client.connectAsync("ws://localhost:" + port + "/ws",
                new StompSessionHandlerAdapter() {}).get(10, TimeUnit.SECONDS);
        session.subscribe("/topic/notices", frameHandler);
        // ...
    }
}
```

WebSocket 的测试**不要退化成“直接调 controller 方法看返回值”**。那样前缀配错（把 `/app` 写成 `/api`）、broker 没启用、消息转换器对不上，一个都测不出来。用真客户端连真端口，一次覆盖整条链路：握手 → STOMP 帧 → `@MessageMapping` → broker → 订阅端。

**客户端需要一个 `TaskScheduler`**，缺了在长连接场景下会被 broker 判为掉线：

```java
var scheduler = new ThreadPoolTaskScheduler();
scheduler.setPoolSize(1);
scheduler.setThreadNamePrefix("stomp-");
scheduler.afterPropertiesSet();
client.setTaskScheduler(scheduler);
client.start();
```

### 一个“本该用回执却用不了”的地方

订阅是异步的：`subscribe()` 返回时，服务端可能还没登记好这个订阅，紧接着发消息就会偶发收不到。标准解法是打开 STOMP 回执——`setAutoReceipt(true)` 之后，服务端确认处理完 SUBSCRIBE 帧才回调，之后才发消息，既快又不会偶发失败。

**但这条路在 Spring 内置的简单 broker 上走不通。** 我试过，订阅回执一直不回来，10 秒超时：

```
[服务端未确认订阅] Expecting value to be true but was false
```

翻源码可以确认原因：`StompSubProtocolHandler` 里只有一处生成 RECEIPT 帧的逻辑，方法名叫 `getDisconnectReceipt`——**只给 DISCONNECT 回执**；`SimpleBrokerMessageHandler` 里则完全搜不到 `receipt` 这个词。想用回执得换成真正的 STOMP broker。

所以测试里退回到“发一次没收到就再发”的写法：

```java
await().atMost(Duration.ofSeconds(20)).untilAsserted(() -> {
    session.send("/app/notice", ActivityNotice.info("第八篇联调"));
    ActivityNotice notice = received.poll(2, TimeUnit.SECONDS);
    assertThat(notice).as("未收到广播").isNotNull();
    lastNotice.set(notice);
});
```

实测通过，整个用例 2.2 秒：

```
@@@WS@@@ 收到 INFO / 第八篇联调
```

**顺带一个提醒**：如果不用回执，`WebSocketStompClient` 也就不是必须配 `TaskScheduler`。但只要用到回执，缺了调度器会直接抛 `To track receipts, a TaskScheduler must be configured`——这个报错信息很明确，照着配就行。
