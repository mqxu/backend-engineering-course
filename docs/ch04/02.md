# 二、统一响应体

接口返回格式不统一，是前端最头疼的事。本项目所有接口都返回同一个外壳：

`common/ApiResponse.java`

```java
package com.example.activity.common;

/**
 * 统一响应体。
 *
 * <p>用 record 而不是普通类：字段不可变，Jackson 3 能直接序列化，
 * 不需要写 getter、equals、hashCode。
 *
 * @param code    业务状态码，0 表示成功
 * @param message 提示信息
 * @param data    业务数据，失败时为 null
 */
public record ApiResponse<T>(int code, String message, T data) {

    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<>(0, "success", data);
    }

    public static ApiResponse<Void> ok() {
        return new ApiResponse<>(0, "success", null);
    }

    public static <T> ApiResponse<T> fail(int code, String message) {
        return new ApiResponse<>(code, message, null);
    }
}
```

### 2.1 为什么要包一层，而不是直接返回业务对象

| 做法 | 问题 |
| --- | --- |
| 成功直接返回对象，失败返回 `{"error": "..."}` | 前端必须靠 HTTP 状态码或字段存在性判断是哪种结构，代码里到处是 `if (res.error)` |
| 成功返回 `{code, message, data}` | 所有响应同一种形状，前端写一个拦截器统一处理即可 |

HTTP 状态码与业务码是两套东西，都要用：

| 层 | 作用 | 例子 |
| --- | --- | --- |
| HTTP 状态码 | 给网络中间层看（网关、监控、浏览器） | 201 创建成功、404 活动不存在、413 请求体过大 |
| 业务码 `code` | 给自己的前端看，粒度更细 | `40001` 参数校验失败、`40900` 同名冲突 |

### 2.2 分页结果

不要直接把 Spring Data 的 `Page` 序列化返回。`Page` 的 JSON 结构在框架版本之间变动过，直接暴露等于把接口契约绑死在框架上。

`common/PageResult.java`

```java
public record PageResult<T>(List<T> list, long total, int page, int pageSize) {

    /** 把 Page<实体> 转成 PageResult<DTO>，映射函数由调用方提供；对外页码从 1 开始 */
    public static <E, T> PageResult<T> of(Page<E> page, Function<E, T> mapper) {
        return new PageResult<>(
                page.getContent().stream().map(mapper).toList(),
                page.getTotalElements(),
                page.getNumber() + 1,
                page.getSize()
        );
    }
}
```

> **页码从 0 开始还是从 1 开始？**
>
> Spring Data JPA 的 `Pageable` **从 0 开始**，MyBatis-Plus 的 `Page` **从 1 开始**。同一个项目里混用两种技术时，这里是高频出错点。本项目的做法是：对内跟随框架（JPA 从 0，MyBatis-Plus 从 1），**对外一律从 1 开始**，转换在 `PageResult.of` 里一次做完。前端只认一个规则，第 6 篇讲 MyBatis-Plus 时不再需要额外说明差异。
