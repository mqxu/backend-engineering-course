# 三、REST 接口设计

`web/ActivityController.java`

```java
@RestController
@RequestMapping("/api/activities")
@Validated
public class ActivityController {

    private final ActivityService activityService;

    public ActivityController(ActivityService activityService) {
        this.activityService = activityService;
    }

    @GetMapping
    public ApiResponse<PageResult<ActivityResponse>> list(
            @RequestParam(required = false) Long venueId,
            @RequestParam(required = false) ActivityType type,
            @RequestParam(required = false) String keyword,
            @RequestParam(defaultValue = "0")
            @Min(value = 0, message = "页码不能小于 0") int page,
            @RequestParam(defaultValue = "10")
            @Min(value = 1, message = "每页条数不能小于 1")
            @Max(value = 100, message = "每页条数不能大于 100") int size) {

        return ApiResponse.ok(activityService.search(venueId, type, keyword, page, size));
    }

    @GetMapping("/{id}")
    public ApiResponse<ActivityResponse> detail(@PathVariable Long id) {
        return ApiResponse.ok(activityService.getById(id));
    }

    @PostMapping
    public ApiResponse<Long> create(@Valid @RequestBody ActivityCreateRequest request) {
        return ApiResponse.ok(activityService.create(request));
    }

    @PutMapping("/{id}")
    public ApiResponse<Void> update(@PathVariable Long id,
                                    @Valid @RequestBody ActivityUpdateRequest request) {
        activityService.update(id, request);
        return ApiResponse.ok();
    }

    /** 发布。用 PATCH 是因为只改 status 一个字段，不是替换整个对象 */
    @PatchMapping("/{id}/status")
    public ApiResponse<Void> changeStatus(@PathVariable Long id,
                                          @Valid @RequestBody StatusUpdateRequest request) {
        activityService.publish(id, request.status());
        return ApiResponse.ok();
    }

    @PatchMapping("/{id}/offshelf")
    public ApiResponse<Void> changeOffShelf(@PathVariable Long id,
                                            @Valid @RequestBody OffShelfRequest request) {
        activityService.changeOffShelf(id, request.offShelf());
        return ApiResponse.ok();
    }

    @DeleteMapping("/{id}")
    public ApiResponse<Void> delete(@PathVariable Long id) {
        activityService.delete(id);
        return ApiResponse.ok();
    }
}
```

### 3.1 接口清单

| 方法 | 路径 | 说明 | 成功状态码 |
| --- | --- | --- | --- |
| GET | `/api/activities` | 分页 + 多条件查询 | 200 |
| GET | `/api/activities/{id}` | 查询详情 | 200 |
| POST | `/api/activities` | 新增 | 200 |
| PUT | `/api/activities/{id}` | 整体修改 | 200 |
| PATCH | `/api/activities/{id}/status` | 发布 / 结束活动 | 200 |
| PATCH | `/api/activities/{id}/offshelf` | 上架 / 下架 | 200 |
| DELETE | `/api/activities/{id}` | 删除（逻辑删除） | 200 |
| GET | `/api/activities/{id}/signup-stats` | 报名统计 | 200 |
| PATCH | `/api/signups/{id}/approve` | 审核通过一条报名，报名通过数 +1 | 200 |
| GET | `/api/venues` | 场地列表 | 200 |
| POST | `/api/files/covers` | 上传活动封面图 | 200 |
| GET | `/api/files/covers/{filename}` | 读取封面图 | 200 |

### 3.2 三个设计决策

**一、通过报名为什么用 PATCH 而不是 GET。**
通过报名要改两处数据：报名记录的状态从待审核变成已通过，活动的报名通过数同时 +1。做成 `GET /api/signups/1/approve` 的话，浏览器预取、爬虫抓取、用户刷新都会意外通过一条报名。

**二、删除为什么返回 200 而不是 204。**
严格按 REST 规范删除成功应返回 `204 No Content`，但那样响应体是空的，前端得分两种情况解析。本项目选择统一返回 `200 + ApiResponse`，契约更简单。规范与实用之间的取舍，团队内部统一即可。

**三、单字段修改为什么用 PATCH 而不是 PUT。**
发布活动只改 `status` 一个字段，下架只改 `offShelf` 一个字段。用 PUT 意味着请求体要带齐整个对象的字段，前端少传一个就会把它清空。PATCH 只描述要改的部分，意图也更清楚。

> **`@Validated` 与 `@Valid` 是两套机制**
>
> - 类上的 `@Validated`（Spring 的）开启**方法级校验**，让 `@RequestParam`、`@PathVariable` 上的 `@Min`/`@Max`/`@Pattern` 生效，失败抛 `ConstraintViolationException`。
> - 参数上的 `@Valid`（Jakarta 的）触发**请求体 DTO 校验**，失败抛 `MethodArgumentNotValidException`。
>
> 两者异常类型不同，全局异常处理器要分别处理。
