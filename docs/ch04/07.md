# 七、文件上传与读取

这一章要解决的是活动封面图：上传后拿到一个可以直接塞进 `<img src>` 的地址，读的时候浏览器能当图片渲染。

### 7.1 上传封面图

`web/FileController.java`

```java
@RestController
@RequestMapping("/api/files")
public class FileController {

    private final CoverStorageService coverStorageService;

    public FileController(CoverStorageService coverStorageService) {
        this.coverStorageService = coverStorageService;
    }

    /** 上传封面图，返回可访问的相对路径 */
    @PreAuthorize("hasRole('ORGANIZER') or hasRole('AUDITOR')")
    @PostMapping(value = "/covers", consumes = MediaType.MULTIPART_FORM_DATA_VALUE)
    public ApiResponse<String> uploadCover(@RequestParam("file") MultipartFile file) {
        return ApiResponse.ok(coverStorageService.store(file));
    }
}
```

只收封面图这一种文件，返回的是拼好的访问路径，前端拿到后直接写进活动的 `coverUrl`。返回路径而不是返回一个含存储名的对象，是因为存储名对前端没有意义——把它暴露出去，等于把服务端内部的命名规则变成了接口的兼容责任。

`service/CoverStorageService.java` 里的保存逻辑：

```java
public String store(MultipartFile file) {
    if (file == null || file.isEmpty()) {
        throw BusinessException.of(ErrorCode.VALIDATION_FAILED, "上传文件不能为空");
    }
    String extension = extensionOf(file.getOriginalFilename());
    if (!ALLOWED_EXTENSIONS.contains(extension)) {
        throw BusinessException.of(ErrorCode.VALIDATION_FAILED,
                "只支持 jpg / png / webp 格式的封面图");
    }

    // 文件名自己生成，不沿用原始名 —— 原始名是外部输入，不能进路径
    String filename = UUID.randomUUID().toString().replace("-", "") + "." + extension;
    Path dir = Path.of(properties.storagePath(), "covers").toAbsolutePath().normalize();

    try {
        Files.createDirectories(dir);
        Path target = dir.resolve(filename).normalize();
        // 双重保险：拼出来的路径必须仍在 covers 目录下
        if (!target.startsWith(dir)) {
            throw BusinessException.of(ErrorCode.VALIDATION_FAILED, "非法的上传路径");
        }
        file.transferTo(target);
    } catch (IOException ex) {
        log.error("封面图保存失败", ex);
        throw BusinessException.of(ErrorCode.INTERNAL_ERROR, "封面图保存失败");
    }
    return "/api/files/covers/" + filename;
}
```

存储名用 UUID 重新生成有两个理由。一是用户可能上传同名文件，沿用原名会互相覆盖；二是原始文件名是外部输入，可能带路径分隔符或特殊字符（`../../x.png`、`a:b.png`），直接拿它拼路径就等于把“往哪儿写”的决定权交给了调用方。后缀单独取出来，并且必须在 `jpg` / `jpeg` / `png` / `webp` 白名单之内。

只看后缀不足以确认文件类型，生产环境还应校验文件头的魔数（magic number）。教学项目到白名单这一步就够了，这一点写在注释里，比假装已经做全更诚实。

### 7.2 读取封面图

```java
@GetMapping("/covers/{filename}")
public ResponseEntity<Resource> readCover(@PathVariable String filename) {
    Path path = coverStorageService.resolve(filename);
    return ResponseEntity.ok()
            .contentType(mediaTypeOf(filename))
            .body(new FileSystemResource(path));
}
```

三个要点：

1. **返回 `ResponseEntity<Resource>` 而不是 `ApiResponse`**。响应体是字节流，不是 JSON。`FileSystemResource` 把文件交给 Spring 以流的方式写出，不必把整张图读进内存再转发。
2. **`Content-Type` 按后缀给出**。少了它浏览器会按 `application/octet-stream` 处理，图片不会直接显示，用户看到的是“下载了一个叫 xxx.png 的文件”。所以 `mediaTypeOf` 里对 `png`、`webp` 单独判断，其余归到 `image/jpeg`。
3. **路径穿越防护**——这是文件读取最容易被忽视的安全问题：

```java
public Path resolve(String filename) {
    Path dir = Path.of(properties.storagePath(), "covers").toAbsolutePath().normalize();
    Path target = dir.resolve(filename).normalize();
    if (!target.startsWith(dir) || !Files.isRegularFile(target)) {
        throw BusinessException.of(ErrorCode.NOT_FOUND, "封面图不存在");
    }
    return target;
}
```

`normalize()` 会把 `../` 折叠掉，`startsWith(dir)` 再确认折叠后的路径仍在存储目录内。少了这两行，`GET /api/files/covers/../../etc/passwd` 就能读到目录之外的文件。`Files.isRegularFile` 顺带挡掉目录、设备文件和管道。

这个接口在 `SecurityConfig` 里是 `permitAll` 的。封面图要被 `<img>` 直接引用，而 `<img>` 带不上 `Authorization` 头，所以它必须在 URL 层面放开。放开之后，防护只能靠上门的路径校验，不能指望鉴权——这是“按路径放开”之后必须补上的一步。

### 7.3 上传大小限制

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 5MB
      max-request-size: 10MB
      file-size-threshold: 1MB
```

| 配置 | 含义 |
| --- | --- |
| `max-file-size` | 单个文件上限 |
| `max-request-size` | 整个请求上限（多文件时是总和） |
| `file-size-threshold` | 超过此大小则写入临时文件，否则放内存 |

超限时抛 `MaxUploadSizeExceededException`，被全局异常处理器转成 413。

> **默认值是 1MB**
>
> Spring Boot 的默认单文件上限是 1MB，不是无限。很多“本地能传、线上传不了”的问题都是这个原因。默认不处理 `MaxUploadSizeExceededException` 时返回 500，客户端会误以为是服务端故障。

### 7.4 上传读取实测

以下全部是本机真实输出。

**上传**：

```
curl -X POST -H "Authorization: Bearer <token>" \
     -F "file=@/tmp/cover.png" http://127.0.0.1:8080/api/files/covers
```

```json
{"code":0,"message":"success","data":"/api/files/covers/e84f256633c248e4ad3bed922ec8ce26.png"}
```

**读取**（响应头）：

```
HTTP/1.1 200
Accept-Ranges: bytes
Content-Type: image/png
Content-Length: 69
```

返回的 69 字节与上传的源文件逐字节一致（用 `cmp` 校验通过）。`Content-Type: image/png` 让浏览器直接渲染，`Accept-Ranges: bytes` 是 `<img>` 加载和断点续传的基础。

**未登录上传**：

```
HTTP 401
{"code":1001,"message":"未登录或登录已过期，请重新登录","data":null}
```

**后缀不在白名单**（传一个 `.txt`）：

```
HTTP 200
{"code":1003,"message":"只支持 jpg / png / webp 格式的封面图","data":null}
```

业务失败返回 200 是本项目的统一约定，前端拦截器只看 `code`。更细的区分交给错误码：这里用 `1003`（参数校验失败），不是笼统的 5000。

**超过 5MB 上限**（传 6MB）：

```
HTTP 413
{"code":5002,"message":"上传文件超过大小限制","data":null}
```

**路径穿越尝试**：

```
curl "http://127.0.0.1:8080/api/files/covers/..%2F..%2F..%2Fetc%2Fpasswd"
→ HTTP 400
```

这里被 **Tomcat 挡在了容器层**，返回的是 Tomcat 自己的 HTML 错误页，请求根本没进到应用代码——Tomcat 8.5 起默认拒绝含编码路径分隔符 `%2F` 的请求（`ALLOW_ENCODED_SLASH` 默认 `false`）。但不能因此省掉应用层的 `normalize()` 校验：容器配置可能被人改掉、应用可能部署在别的容器上、内部调用也不一定经过 HTTP。

**封面图不存在**：

```
HTTP 404
{"code":1004,"message":"封面图不存在","data":null}
```

**存储目录实际内容**：

```
-rw-r--r--  1 moqi  staff  69 Sep 16 06:26 e84f256633c248e4ad3bed922ec8ce26.png
```

目录里只有 UUID 文件，看不到原始文件名。原始名只在前端展示时用，不落盘，也就不存在“用户把文件名改成怪字符”这类问题。
