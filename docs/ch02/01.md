# 一、代码结构：官方建议与背后的机制

### 1.1 为什么禁止使用“默认包”

官方文档在这一节用了相当重的措辞：“The use of the default package is generally discouraged and should be avoided.”（默认包通常不推荐使用，应当避免）

所谓默认包，就是类文件里**没有 `package` 声明**。它的具体危害是：

| 注解 | 在默认包下会发生什么 |
| --- | --- |
| `@ComponentScan` | 扫描范围退化成“全部”，classpath 上每个 jar 里的类都会被读一遍 |
| `@ConfigurationPropertiesScan` | 同上，配置类的扫描失去边界 |
| `@EntityScan` | 实体扫描范围失控，可能把依赖里的类当成实体 |
| `@SpringBootApplication` | 以上三者的组合效果同时出现 |

后果不只是启动变慢 —— 更麻烦的是**行为不可预期**：某个第三方 jar 里的类被误扫成组件，会导致莫名其妙的 Bean 冲突。

### 1.2 主类为什么必须放在根包

官方建议把主类放在“其他类之上的根包”。原因在于 `@SpringBootApplication` 隐含地定义了一个**基准搜索包**，而这个基准包就是主类所在的包。以下三类扫描都以它为起点：

**组件扫描**

`@ComponentScan` 从基准包向下递归，收集 `@Component` / `@Service` / `@Repository` / `@Controller` 标注的类。

**实体扫描**

JPA 应用里，同一路径用于查找 `@Entity`。主类在根包，所有实体才会被扫到。

**仓库扫描**

Spring Data 的仓库接口也从这里往下找。启动日志里那行 “Found N JPA repository interfaces” 就是在报告这一步的结果。

官方给出的典型布局是**按领域分包**：

**官方示例结构**

```bash
com
 +- example
     +- myapplication
         +- MyApplication.java      主类在根包
         |
         +- customer                 按业务领域组织
         |   +- Customer.java
         |   +- CustomerController.java
         |   +- CustomerService.java
         |   +- CustomerRepository.java
         |
         +- order
             +- Order.java
             +- OrderController.java
             +- OrderService.java
             +- OrderRepository.java
```

### 1.3 本教程采用按技术分层

官方还提到，如果想强制按领域划分结构，可以了解 Spring Modulith 项目。两种组织方式各有适用场景，本教程选择**按技术分层**（这是国内团队的主流做法，也和大多数院校课程的组织方式一致）：

**resource-hub 实际包结构**

```bash
com.example.resourcehub
├── ResourceHubApplication.java        主类，位于根包
│
├── common/                             跨层通用组件，不依赖任何业务包
│   ├── ApiResponse.java                    统一响应体
│   ├── PageResult.java                     分页结果
│   ├── BusinessException.java              业务异常
│   └── GlobalExceptionHandler.java         全局异常处理
│
├── config/                             基础设施配置
│   └── AppProperties.java                  自定义配置项绑定
│
├── domain/                             领域模型：只表达业务概念
│   ├── Category.java                       分类实体
│   ├── ResourceItem.java                   资源实体
│   └── ResourceType.java                   资源类型枚举
│
├── repository/                         数据访问：只和数据库打交道
│   ├── CategoryRepository.java
│   └── ResourceItemRepository.java
│
├── service/                            业务逻辑：事务边界在这一层
│   ├── CategoryService.java
│   └── ResourceService.java
│
├── dto/                                传输对象：对外契约，与实体解耦
│   ├── ResourceCreateRequest.java
│   ├── ResourceUpdateRequest.java
│   ├── ResourceResponse.java
│   └── CategoryResponse.java
│
└── web/                                控制器：只做协议转换
    ├── ResourceController.java
    └── CategoryController.java
```

两种方式的对照：

| 维度 | 按技术分层（本教程） | 按领域分包 |
| --- | --- | --- |
| 包的含义 | `web` / `service` / `repository` | `customer` / `order` |
| 找代码的方式 | 先想“这是哪一层”，再找具体文件 | 先想“这是哪个业务”，再看内部各层 |
| 适合 | 业务域较少、团队协作需要清晰分层约束 | 业务域多且相互独立、模块边界需要强约束 |
| 风险 | 业务变多后，同一层包会膨胀 | 跨领域的通用能力容易放得零散 |

> **一条实用的判断标准**
>
> 业务域在十个以内、团队成员对分层有共识 —— 用按技术分层，简单直接。业务域多、模块间需要强制隔离（比如多人同时开发不同模块），再考虑按领域分包或引入 Spring Modulith 做模块化约束。不要为了“架构先进”提前上复杂结构。
