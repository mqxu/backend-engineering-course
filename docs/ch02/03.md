# 三、自动配置是怎么工作的

### 3.1 机制：三个步骤

1. **登记** 每个 starter 或模块在自己的 jar 里放一个 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件，里面逐行列出自家的自动配置类全限定名。
2. **筛选** Spring Boot 启动时读取这些类，但对每个类都会先做**条件判断**（条件注解），条件不满足的直接跳过，满足的才生效。
3. **生效** 条件通过的自动配置类被当作普通配置类处理，里面定义的 `@Bean` 被注册到容器。此时如果用户自己定义了同类型的 Bean，自动配置通常会退让。

#### 五个最常用的条件注解

| 注解 | 含义 | 典型用法 |
| --- | --- | --- |
| `@ConditionalOnClass` | classpath 上有指定类才生效 | 有 H2 才配内存数据源 |
| `@ConditionalOnMissingBean` | 容器里**没有**指定 Bean 才生效 | 用户没自己配 DataSource 时给默认的 |
| `@ConditionalOnProperty` | 配置项满足条件才生效 | `spring.h2.console.enabled=true` 才开控制台 |
| `@ConditionalOnBooleanProperty` | 配置项为布尔真才生效（更严格的写法） | 4.x 中大量使用，见下面的实测输出 |
| `@ConditionalOnWebApplication` | 当前是 Web 应用才生效 | 只在 Servlet 环境注册过滤器 |

### 3.2 实测：用 --debug 看自动配置的决策过程

加了哪些自动配置、为什么加、为什么没加 —— 官方给的办法是加 `--debug` 参数启动：

```bash
java -jar target/activity-server-1.0.0.jar --debug
```

控制台会多出一份条件评估报告（本机运行时这份报告有 1222 行）。它的结构分四段，以下是真实输出片段：

**Positive matches（生效的自动配置）**

```bash
Positive matches:
-----------------

   AopAutoConfiguration matched:
      - @ConditionalOnBooleanProperty (spring.aop.auto=true) matched (OnPropertyCondition)

   AopAutoConfiguration.AspectJAutoProxyingConfiguration matched:
      - @ConditionalOnClass found required class 'org.aspectj.weaver.Advice' (OnClassCondition)

   ApplicationAvailabilityAutoConfiguration#applicationAvailability matched:
      - @ConditionalOnMissingBean (types: org.springframework.boot.availability.ApplicationAvailability;
        SearchStrategy: all) did not find any beans (OnBeanCondition)
```

`Exclusions / Unconditional classes`

```bash
Exclusions:
-----------

    None

Unconditional classes:
----------------------

    org.springframework.boot.health.autoconfigure.registry.HealthContributorRegistryAutoConfiguration

    org.springframework.boot.autoconfigure.context.ConfigurationPropertiesAutoConfiguration
```

这份报告怎么读：

| 段落 | 含义 | 什么时候看它 |
| --- | --- | --- |
| Positive matches | 条件满足、已生效的自动配置，后面跟着具体是哪个条件通过的 | 想确认“某个功能到底有没有被自动配上” |
| Negative matches | 条件不满足、被跳过的自动配置 | 配置没生效时，先在这里找原因 |
| Exclusions | 被主动排除的自动配置 | 确认 `spring.autoconfigure.exclude` 是否写对 |
| Unconditional classes | 无条件生效的类 | 排查“为什么有些配置关不掉” |

> **从这份真实报告里能看到两个 4.x 的细节**
>
> 一、新增了 `@ConditionalOnBooleanProperty` 条件，比早期的 `@ConditionalOnProperty(havingValue = "true")` 更严格（它只接受真正合法的布尔值）。
>
> 二、健康检查相关类的包名已经挪到了 `org.springframework.boot.health.autoconfigure.*`，3.x 时代是 `org.springframework.boot.actuate.autoconfigure.*`。这也解释了为什么照抄老代码时经常提示类找不到。

### 3.3 如何安全地覆盖自动配置

官方强调自动配置是“非侵入式”的：你可以在任何时候定义自己的配置来替换它的某一部分。规则很简单 —— **你定义了，它就退让**。以数据源为例：

**终端：查看当前生效的数据源**

```bash
# 启动日志里能看到连接池的实际来源
INFO --- com.zaxxer.hikari.HikariDataSource : HikariPool-1 - Starting...
INFO --- com.zaxxer.hikari.HikariPool      : HikariPool-1 - Added connection conn0: url=jdbc:h2:mem:activity user=SA
```

本案例工程没有配置任何数据源相关代码，日志里出现的 `HikariDataSource`、`jdbc:h2:mem:activity` 全部来自自动配置。如果哪天换成公司统一的数据源组件，只要自己声明一个 `DataSource` Bean，上面这些自动行为就会消失。

| 目标 | 做法 | 推荐程度 |
| --- | --- | --- |
| 替换某块自动配置 | 自己声明同类型的 Bean | 首选，改动最小 |
| 关闭某块自动配置 | `exclude` 或 `spring.autoconfigure.exclude` | 确定完全不需要时使用 |
| 调整行为参数 | 改配置项，不写代码 | 首选 |
| 改自动配置类的内部实现 | —— | 不要做，属于内部 API |
