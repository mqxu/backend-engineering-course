# 五、实战：把 activity-server 的分层落下来

这一节把上面的约定用到案例工程上。注意各层的依赖方向是**单向**的：`web` 依赖 `service`，`service` 依赖 `repository`，`repository` 依赖 `domain`，反向依赖一个都不能有。

### 5.1 domain：只表达业务概念

领域模型不掺入 Web 层的校验规则，也不负责序列化 —— 那些是 DTO 的事。以活动类型枚举为例：

`domain/ActivityType.java`

```java
package com.example.activity.domain;

/**
 * 活动类型。
 *
 * 存库时用字符串（@Enumerated(EnumType.STRING)），而不是默认的序号。
 * 用序号存库的风险：一旦枚举常量顺序调整，历史数据含义就全错了。
 */
public enum ActivityType {

    LECTURE("文档"),
    COMPETITION("视频"),
    CODE("代码"),
    LINK("活动详情页");

    private final String label;

    ActivityType(String label) {
        this.label = label;
    }

    public String getLabel() {
        return label;
    }
}
```

枚举带一个 `label` 字段用于前端展示 —— 接口返回 `"type": "LINK"` 与 `"typeLabel": "活动详情页"` 两个值，前端做筛选时用前者，直接展示时用后者。

实体类 `Activity` 的关键设计点（完整代码见第 6 篇）：

| 设计点 | 做法 | 原因 |
| --- | --- | --- |
| 关联抓取策略 | `@ManyToOne(fetch = FetchType.LAZY)` | 默认是 EAGER，列表接口上会顺带把场地查出来，产生多余查询 |
| 状态变更 | 暴露 `increaseApprovedCount()`、`disable()` 等业务方法，而不是给字段加 setter | 把“能做什么”收敛到实体内部，业务规则不会散落到 Service 的角落 |
| 时间字段 | `@PrePersist` / `@PreUpdate` 回调自动维护 | 避免每个 Service 方法都要手写 `setUpdatedAt` |
| 删除策略 | `enabled` 状态字段 + `disable()` 方法 | 下架而非物理删除，保留报名统计数据 |
| 无参构造器 | `protected Activity() {}` | JPA 规范要求；设为 protected 防止业务代码误用 |

### 5.2 repository：只和数据库打交道

`repository/ActivityRepository.java`

```java
package com.example.activity.repository;

import com.example.activity.domain.Activity;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.domain.Specification;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.JpaSpecificationExecutor;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.Optional;

/**
 * 继承 JpaSpecificationExecutor 后即可用 Specification 组装动态查询条件——
 * 这是官方支持的方案，比用大量 if 拼 JPQL 字符串安全。
 */
public interface ActivityRepository
        extends JpaRepository<Activity, Long>, JpaSpecificationExecutor<Activity> {

    /** 列表查询加实体图，把 N+1 压成 1 条 SQL（第 6 篇详解） */
    @Override
    @EntityGraph(attributePaths = {"venue"})
    Page<Activity> findAll(Specification<Activity> spec, Pageable pageable);

    /** 原子自增报名通过数：不能让数据库之外的代码参与读-改-写 */
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("""
            UPDATE Activity r
               SET r.approvedCount = r.approvedCount + 1
             WHERE r.id = :id
               AND r.enabled = true
            """)
    int incrementApprovedCount(@Param("id") Long id);

    /** 标题是否已存在（用于新增时的重名校验） */
    boolean existsByTitleAndEnabledTrue(String title);
}
```

> **仓库接口不需要实现类**
>
> 只声明接口、不写实现 —— Spring Data 在启动时用动态代理生成实现。启动日志里那行 `Found 2 JPA repository interfaces` 就是它在报告“我找到了两个接口，已经准备好实现”。`existsByTitleAndEnabledTrue` 这种由方法名推导查询的能力（派生查询）是 Spring Data 的核心便利之一，第 6 篇会系统讲它的命名规则。

### 5.3 service 与 web：依赖注入的完整链路

一次“分页查询活动列表”请求，穿过四层的样子：

**调用链**

```bash
HTTP GET /api/activities?keyword=spring&page=0&size=10
   │
   ▼
ActivityController           只做三件事：收参数、调 Service、包响应体
   │  构造器注入 ↓
   ▼
ActivityService              业务逻辑 + 事务边界
   │  构造器注入 ↓
   ▼
ActivityRepository       Spring Data 动态代理实现
   │  JPA ↓
   ▼
Hibernate 7  →  H2 / MySQL
```

控制器保持“薄”是关键。它不该出现 `if` 判断业务规则，也不该直接操作仓库：

`web/ActivityController.java（节选）`

```java
@RestController
@RequestMapping("/api/activities")
public class ActivityController {

    private final ActivityService activityService;

    public ActivityController(ActivityService activityService) {
        this.activityService = activityService;
    }

    @GetMapping
    public ApiResponse<PageResult<ActivityResponse>> list(
            @RequestParam(required = false) String keyword,
            @RequestParam(required = false) Long venueId,
            @RequestParam(defaultValue = "0") int page,
            @RequestParam(defaultValue = "10") int size) {

        return ApiResponse.ok(activityService.search(keyword, venueId, page, size));
    }
}
```

> **这段代码里有三个刻意的设计**
>
> 一、**返回 `ApiResponse` 而不是实体**：实体带着 JPA 的懒加载代理，直接序列化会踩坑（第 4 篇会演示具体报错），而且会泄露内部字段结构。
>
> 二、**分页参数用 `page` / `size` 而不是框架的 `Pageable`**：少了参数解析的隐式约定，前端一眼能看懂，也不用暴露 Spring Data 的排序语法。
>
> 三、**方法体只有一行**：控制器里出现第二行业务代码，通常说明逻辑放错了位置。

### 5.4 分层落地的自检清单

| 检查项 | 怎么判断 |
| --- | --- |
| 主类在根包 | 启动日志里 `Found N JPA repository interfaces` 的 N 与仓库接口数量一致 |
| 没有反向依赖 | `domain` 包里搜不到 `import ...service.` 或 `...web.` |
| 控制器够薄 | 每个方法体基本只有一行调用 |
| 实体不外泄 | 控制器签名里不出现 `Activity` 这类实体类型 |
| 依赖都是构造器注入 | 全工程搜 `@Autowired`，理想结果是零 |
