# 四、Bean 与依赖注入

### 4.1 优先用构造器注入

官方推荐构造器注入，理由有三个：**依赖可以声明为 final**（不可变）、**对象创建即完成装配**（不会出现半初始化状态）、**不依赖容器也能 new 出来测试**。第四点很少被提到但很实用：违反它往往意味着类设计有问题。

**✅ 构造器注入（本教程统一用法）**

```java
@Service
public class ActivityService {

    private final ActivityRepository activityRepository;
    private final VenueRepository venueRepository;

    // 只有一个构造器时可以省略 @Autowired，Spring 4.3+ 起自动识别
    public ActivityService(ActivityRepository activityRepository,
                           VenueRepository venueRepository) {
        this.activityRepository = activityRepository;
        this.venueRepository = venueRepository;
    }
}
```

**❌ 字段注入（不推荐）**

```java
@Service
public class ActivityService {

    @Autowired
    private ActivityRepository activityRepository;   // 无法声明为 final，测试时必须借助容器
}
```

> **字段注入为什么还在被广泛使用**
>
> 它写起来短，IDE 提示也好用。代价是：依赖关系藏在字段里（读代码看不出这个类需要什么）、无法用 final 保证不可变、单测必须启动 Spring 容器或用反射注入。**本教程所有生产代码统一用构造器注入**，你在后续章节看到的 Service 都是这个形态。

### 4.2 构造型注解的区别

这几个注解在“被扫描成 Bean”这件事上完全等价，差别只在于语义表达：

| 注解 | 语义 | 额外行为 |
| --- | --- | --- |
| `@Component` | 通用组件 | 无 |
| `@Service` | 业务服务 | 无（纯语义） |
| `@Repository` | 数据访问 | 会把底层抛出的持久化异常翻译成 Spring 的 `DataAccessException` 体系 |
| `@Controller` / `@RestController` | Web 控制器 | 被 MVC 基础设施识别为处理器 |
| `@Configuration` | 配置类 | 类内的 `@Bean` 方法默认被代理，保证单例语义 |

只有 `@Repository` 有真正的额外行为，其余都是语义标注。但语义标注本身有价值 —— 它让“这个类属于哪一层”一眼可辨。

### 4.3 同一类型有多个 Bean 怎么办

这是实际开发中一定会遇到的问题。三种解法，按使用频率排列：

**方案一：@Primary 指定默认实现**

```java
@Configuration
public class StorageConfig {

    // 默认用本地存储
    @Bean
    @Primary
    public FileStorage localStorage() {
        return new LocalFileStorage();
    }

    @Bean
    public FileStorage ossStorage() {
        return new OssFileStorage();
    }
}
```

**方案二：@Qualifier 精确指定（注入方决定）**

```java
@Service
public class ActivityService {

    private final FileStorage storage;

    public ActivityService(@Qualifier("ossStorage") FileStorage storage) {
        this.storage = storage;
    }
}
```

**方案三：按参数名匹配**

```java
// Bean 名称与参数名一致时，Spring 会自动消歧
public ActivityService(FileStorage ossStorage) {
    this.storage = ossStorage;   // 匹配名为 ossStorage 的 Bean
}
```

> **没有消歧手段时的报错长什么样**
>
> **启动失败**
>
> ```bash
> Parameter 0 of constructor in com.example.ActivityService required a single bean,
> but 2 were found:
> 	- localStorage: defined by method 'localStorage' in class path resource [...]
> 	- ossStorage: defined by method 'ossStorage' in class path resource [...]
> ```
>
> 看到 `required a single bean, but N were found`，就是这个问题。别急着加 `@Primary` 掩盖 —— 先想清楚“这两个实现是不是本来就不该同类型”。

### 4.4 Bean 生命周期

常用钩子只有三个，其余很少需要：

| 时机 | 用法 | 典型场景 |
| --- | --- | --- |
| 依赖注入完成后 | `@PostConstruct`（或实现 `InitializingBean`） | 加载本地缓存字典、校验配置项 |
| 容器关闭前 | `@PreDestroy` | 关闭线程池、释放外部连接 |
| 由 Spring 管理活动 | 实现 `DisposableBean` / `AutoCloseable` | 第三方客户端的优雅关闭 |

**示例**

```java
@Component
public class DictionaryCache {

    private Map<String, String> dict;

    @PostConstruct
    void load() {
        this.dict = loadFromDatabase();   // 容器启动时加载一次
    }

    @PreDestroy
    void clear() {
        this.dict.clear();                // 关停时释放
    }
}
```

> **Bean 默认是单例，Service 必须无状态**
>
> Spring 容器里的 Bean 默认单例 —— 全局只有一个实例，被所有线程共享。这意味着**绝对不要在 Service 里用可变字段保存请求相关的数据**：
>
> **❌ 危险的写法**
>
> ```java
> @Service
> public class ActivityService {
>     private String currentUser;      // 两个请求并发进来会互相覆盖
>
>     public void doSomething(String user) {
>         this.currentUser = user;     // 别这样写
>     }
> }
> ```
>
> 正确做法是把这类数据放在方法参数、局部变量，或者用 `ThreadLocal` / `RequestScope` Bean。第 5 篇讲安全认证时会用 `SecurityContextHolder` 演示线程隔离的当前用户获取方式。
