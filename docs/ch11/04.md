# 11.4 JVM 上的 AOT：把 Bean 定义在构建期算好

提到 AOT（Ahead-of-Time，提前处理），多数人第一反应是 GraalVM 原生镜像。但 AOT 本身是独立的一件事，**在普通 JVM 上也能用，而且不需要装 GraalVM**。

原理是 Spring 的启动流程里有一段开销很大的工作：解析 `@Configuration` 类、扫描注解、生成 Bean 定义。这部分结果是确定的——同样的代码，每次启动算出来的 Bean 定义都一样。AOT 就是把这个计算从运行期挪到构建期，生成等价的 Java 代码编译进产物。

官方文档给出两个入口：JVM 场景用 `-Pnative package` 加 `-Dspring.aot.enabled=true`（见 [Ahead-of-Time Processing With the JVM](https://docs.spring.io/spring-boot/reference/packaging/aot.html)），原生镜像场景则整条链路都走 AOT。

### 怎么开启

Spring Boot 的父 POM 里预置了一个 `native` profile，其中给 `spring-boot-maven-plugin` 绑了 `process-aot` 目标：

```xml
<profile>
  <id>native</id>
  <build>
    <pluginManagement>
      <plugins>
        <plugin>
          <groupId>org.springframework.boot</groupId>
          <artifactId>spring-boot-maven-plugin</artifactId>
          <executions>
            <execution>
              <id>process-aot</id>
              <goals><goal>process-aot</goal></goals>
            </execution>
          </executions>
        </plugin>
        ...
```

因为这些配置写在 `pluginManagement` 里，**只有工程自己也声明了这个插件，目标才会真正绑定上去**。本工程的 `pom.xml` 里本来就有 `spring-boot-maven-plugin`，所以直接构建即可：

```shell
$ mvn -Pnative -DskipTests package
```

```text
[INFO] --- spring-boot:4.1.1:process-aot (process-aot) @ resource-hub ---
[INFO] Replacing main artifact ... with repackaged archive ...
[INFO] BUILD SUCCESS
[INFO] Total time:  9.012 s
```

比普通构建多了约 6 秒，这是 AOT 处理本身的代价。

### 生成了什么

产物在 `target/spring-aot/main/` 下，三类东西：

```text
sources/    219 个 .java 文件
classes/    291 个 .class 文件
resources/    5 个文件
```

源码文件都是 `__BeanDefinitions` 这样的名字，内容是把配置类翻译成直接可执行的形式。随便挑一个看，原本要靠反射调用的 `@Bean` 方法变成了显式的实例供应器：

```java
public class MyConfiguration__BeanDefinitions {
    public static BeanDefinition getMyBeanBeanDefinition() {
        Class<?> beanType = MyBean.class;
        RootBeanDefinition beanDefinition = new RootBeanDefinition(beanType);
        beanDefinition.setInstanceSupplier(getMyBeanInstanceSupplier());
        return beanDefinition;
    }
}
```

`classes/` 下是运行期本来要动态生成的代理类字节码（cglib 那部分）。`resources/` 下是给 GraalVM 的提示文件。

另外，manifest 里多了一个字段：

```text
Spring-Boot-Native-Processed: true
```

### 运行时的开关

AOT 代码编译进 jar 之后，默认**不会**自动启用——因为同一份 jar 里的普通路径也还在。要显式打开：

```shell
$ java -Dspring.aot.enabled=true -jar resource-hub-1.0.0.jar
```

启动横幅会变，这是判断 AOT 是否生效最直接的方法：

```text
Starting AOT-processed ResourceHubApplication v1.0.0 using Java 21.0.12.1 with PID ...
```

实测三次：

| 形态 | 三次耗时（秒） | 中位数 |
| --- | --- | --- |
| 普通 jar | 4.643 / 4.799 / 4.825 | 4.80 |
| AOT jar，未启用 | 4.710 / 4.877 / 5.054 | 4.88 |
| AOT jar + `spring.aot.enabled=true` | 3.810 / 3.865 / 3.878 | 3.87 |

有用信息在两个地方。一是**光把 AOT 代码打进 jar 不会变快**（4.88 与 4.80 基本一致），必须有 `spring.aot.enabled=true`。二是启用之后快了约 0.9 秒，约 19%。

### AOT 带来的限制

用了 AOT，等于向框架承诺“Bean 定义在构建期就定下来，运行期不会再变”。这个承诺换来的是启动速度，代价是下面这些用法不再成立：

- **classpath 必须在构建期完全确定**，运行期不能改
- **`@Profile` 与 profile 专属配置有限制**，因为不同 profile 对应不同 Bean 定义，构建期只能算一套
- **`@ConditionalOnProperty` 与各种 `.enabled` 开关不支持**，它们同样会让 Bean 定义随配置变化

第二条和第三条是实际项目里最容易踩的。本工程里就有 `@ConditionalOnProperty` 的用法（第 7 篇的外部服务开关、第 8 篇的下行链路开关），AOT 处理时框架会怎样对待它们，取决于条件求值发生在哪个阶段。稳妥的判断标准是：**如果一个 Bean 的创建与否由配置决定，它就不适合放进 AOT 路径**。

这也是为什么 `-Dspring.aot.enabled=true` 是个开关而不是默认行为：它需要你对自己的代码有把握。

### 一个和文档不一致的地方

官方文档在介绍 Spring AOT 生成的提示文件时，列的是 GraalVM 传统的五个 JSON：

```text
resource-config.json
reflect-config.json
serialization-config.json
proxy-config.json
jni-config.json
```

但 4.1.1 实际生成的不是这些。`target/spring-aot/main/resources/` 下只有五个文件：

```text
META-INF/native-image/com.example/resource-hub/native-image.properties
META-INF/native-image/com.example/resource-hub/reachability-metadata.json
com/example/resourcehub/repository/AppUserRepository.json
com/example/resourcehub/repository/CategoryRepository.json
com/example/resourcehub/repository/ResourceItemRepository.json
```

`reflect-config.json`、`resource-config.json` 这些一个都没有。打开那个 339KB 的 `reachability-metadata.json`，开头是这样的：

```json
{
  "comment": "Spring Framework 7.0.9",
  "reflection": [
    { "type": "byte[]" },
    { "type": "ch.qos.logback.classic.LoggerContext" },
    {
      "type": "ch.qos.logback.classic.pattern.SyslogStartConverter",
      "allPublicConstructors": true
    },
    ...
```

这是 GraalVM 的**统一可达性元数据格式**（unified reachability metadata），把原本分散在五个文件里的内容合并成一份。Spring Framework 7 已经切到这个格式上，而文档里那一节的表述还停留在旧格式。

`native-image.properties` 里写的是原生镜像的构建参数：

```text
Args = -H:Class=com.example.resourcehub.ResourceHubApplication \
--no-fallback
```

`--no-fallback` 的含义是“如果静态分析发现缺少必要的反射配置，直接构建失败，不要退化成带回退的镜像”。对教学项目来说这个设置很有用——问题暴露在构建期而不是运行期。
