# 11.3 四层是按“变化频率”切的

`BOOT-INF/layers.idx` 的内容：

```yaml
- "dependencies":
  - "BOOT-INF/lib/"
- "spring-boot-loader":
  - "org/"
- "snapshot-dependencies":
- "application":
  - "BOOT-INF/classes/"
  - "BOOT-INF/classpath.idx"
  - "BOOT-INF/layers.idx"
  - "META-INF/"
```

划分依据只有一条：**这份内容有多久会变一次**。

| 层 | 装什么 | 变化频率 |
| --- | --- | --- |
| `dependencies` | 正式版本的依赖 jar | 改 `pom.xml` 才变，几周一次 |
| `spring-boot-loader` | 启动器代码 | 升级 Boot 版本才变 |
| `snapshot-dependencies` | SNAPSHOT 依赖 | 每次都能变，所以单独隔离 |
| `application` | 你的类和资源 | 每次提交都变 |

文件顺序也是有意义的：`layers.idx` 里的顺序就是往镜像里添加层的顺序，底下的层越稳定。这样 Docker 只要重建上面那几层，下面的能从缓存里拿。

SNAPSHOT 单独成层是个细节处理。SNAPSHOT 依赖按定义就是“内容可能随时变”，如果和正式依赖混在一层，每次构建都会让整个依赖层失效；隔出来之后，正式依赖层的缓存就稳了。

### 启动耗时实测

在同一台机器上，每种形态启动三次，记录日志里 `Started ResourceHubApplication in X seconds`：

| 形态 | 三次耗时（秒） | 中位数 | 相对基线 |
| --- | --- | --- | --- |
| 可执行 jar | 4.643 / 4.799 / 4.825 | 4.80 | — |
| 解压布局 | 3.765 / 3.767 / 3.897 | 3.77 | −21% |

只做解压这一步，启动快了约 1 秒。官方文档里说“解压后在生产环境推荐”，理由是嵌套 jar 的加载有额外开销；实测下来这个开销确实存在，同一个应用、同一个 JVM，差别就是这 1 秒。

需要注意这是**本机、无负载、热缓存**条件下的数字。应用的启动时间受机器、磁盘、容器限制影响很大，这里的三次运行只是说明“解压确实更快”这个方向成立，具体数字不要照搬。
