# 11.7 Buildpacks：不写 Dockerfile 的路线

前面那条路线需要自己维护 Dockerfile、自己处理基础镜像更新。另一条路线是 Cloud Native Buildpacks（CNB）：给插件一条命令，它自己分析项目、选 JDK、分层、生成镜像。

```shell
$ mvn spring-boot:build-image
```

4.1.1 的默认 builder 是：

```text
paketobuildpacks/builder-noble-java-tiny:latest
```

生成的镜像名由项目坐标推导，默认是 `docker.io/library/${artifactId}:${version}`，对应本工程就是 `docker.io/library/activity-server:1.0.0`。

这一节的命令与默认值来自 4.1.1 的插件文档。构建时插件要按 builder 元数据拉取 builder 与 run image（本机实测 builder 镜像 858MB），这一步依赖镜像仓库的可达性，在配置好仓库代理的环境里可以直接跑通。

### 几个默认值

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `builder` | `paketobuildpacks/builder-noble-java-tiny:latest` | 可选 `jammy-base`、`jammy-full` 等 |
| `name` | `docker.io/library/${artifactId}:${version}` | 用 `spring-boot.build-image.imageName` 覆盖 |
| `pullPolicy` | `ALWAYS` | 每次构建都拉 builder，`NEVER` 可跳过 |
| `createdDate` | 固定日期 | 固定的时间戳，让镜像可复现 |
| `trustBuilder` | 视 builder 而定 | 只有官方列出的那几个 builder 默认为可信 |

绑定到 `package` 阶段时要换成 `build-image-no-fork`：

```xml
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <executions>
    <execution>
      <goals><goal>build-image-no-fork</goal></goals>
    </execution>
  </executions>
</plugin>
```

`build-image` 会 fork 一次生命周期来确保 `package` 先跑完，适合命令行调用；在构建配置里绑定执行时应该用 `build-image-no-fork`，否则会多跑一轮。

### 和 Dockerfile 路线的取舍

Buildpacks 的优点是省事：不写 Dockerfile，基础镜像的安全更新由 builder 负责，分层规则由 Paketo 的 buildpack 决定。JVM 参数、内存比例、`layers.idx` 这些它都认识。

代价是控制力弱一些。想调整基础镜像里的系统包、想精确控制层的划分、想在构建阶段做点别的事（比如生成 CDS 归档），Buildpacks 给的余地比 Dockerfile 小。构建过程也更慢——它要拉 builder 镜像、跑完整的 buildpack 生命周期。

还有一点：**buildpacks 会改写应用产物的元数据**（比如文件的最后修改时间），用来做可复现构建和缓存。官方文档提醒，如果你的代码在运行期依赖这些元数据，行为会变。静态资源的缓存就是一处，必要时用 `spring.web.resources.cache.use-last-modified` 关掉。

选择上可以这样看：**镜像构建流程统一走 CNB 的平台**（比如团队已经有 CNB 的 CI 集成）就用 Buildpacks；需要精细控制镜像内容、或者构建阶段有自定义步骤，就用 Dockerfile。
