# 11.8 GraalVM 原生镜像

前面所有优化都在 JVM 的框架内做——JVM 还是要启动、还是要加载类。原生镜像（Native Image）走的是另一条路：**把应用编译成一个平台相关的可执行文件，里面不再有 JVM。**

好处很直接：启动时间从秒级降到毫秒级，内存占用显著下降。代价同样直接：构建要几分钟、产物要几十分钟的静态分析、部分动态特性不再可用。

### 构建前提

| 项目 | 要求 |
| --- | --- |
| GraalVM | 25 及以上（本次实测 25.0.4） |
| Maven 插件 | `native-maven-plugin`，版本 1.1.8（由父 POM 管理） |
| 内存 | 编译过程比较吃内存，建议 8GB 以上 |

`native-maven-plugin` 必须由工程显式声明，父 POM 里只在 `pluginManagement` 中提供了配置：

```xml
<plugin>
    <groupId>org.graalvm.buildtools</groupId>
    <artifactId>native-maven-plugin</artifactId>
</plugin>
```

不写 `<version>`，版本从父 POM 的 `native-build-tools-plugin.version` 继承。

### 编译命令与实测结果

`native:compile` 不在 `package` 阶段里，要显式调用：

```shell
$ JAVA_HOME=/path/to/graalvm mvn -Pnative -DskipTests package native:compile
```

这里有个容易踩的地方：**`mvn -Pnative package` 不会编译原生镜像**。父 POM 的 `native` profile 里给 `spring-boot-maven-plugin` 绑了 `process-aot`，给 `native-maven-plugin` 绑了 `add-reachability-metadata`，但没有绑定 `compile`。只跑 `package` 的话，得到的还是一个带 AOT 代码的普通 jar——日志里能看到 `process-aot` 执行了，`native:compile` 却不见了。

### 构建代价

编译输出很简洁：

```text
GraalVM Native Image: Generating 'resource-hub' (executable)...
Build artifacts:
Finished generating 'resource-hub' in 4m 37s.
[INFO] BUILD SUCCESS
[INFO] Total time:  04:55 min
```

本工程 52 个 Java 文件、约 100 个依赖，编译花了 **4 分 37 秒**（连上 Maven 前置阶段共 4 分 55 秒）。这个过程包含几步：

- **静态分析**：从 `main` 入口出发，把能到达的代码全找出来，构建期不可达的代码会被直接删掉
- **可达性元数据应用**：把 Spring AOT 生成的提示文件和 `graalvm-reachability-metadata` 仓库里的元数据合进来
- **编译与链接**：生成目标平台的可执行文件

编译时长与项目规模、依赖数量强相关。Spring Boot 官方对构建环境的要求是至少 8GB 内存，依赖更多、反射更重的项目时间会更长，给到 16GB 更稳妥。所以原生镜像适合放在 CI 里做，不适合开发时反复跑。

### 运行时的收益

产物是一个平台相关的可执行文件：

```text
$ file target/resource-hub
target/resource-hub: Mach-O 64-bit executable arm64
```

两种形态放在一起对比：

| 运行形态 | 产物 | 启动耗时（中位数） | 常驻内存 |
| --- | --- | --- | --- |
| JVM 可执行 jar | 62 MB | 4.80 秒 | 546 MB |
| GraalVM 原生镜像 | 191 MB | 0.268 秒 | 167 MB |

原生镜像启动三次：0.357 / 0.268 / 0.266 秒。内存数字是应用就绪后静置 4 秒读数，JVM 侧用的是默认堆参数。

启动快了约 18 倍，内存降到约三分之一。接口行为完全一致——两种形态下健康检查与 `/api/resources` 都返回 200，说明这不是一个“跑不起来但很快”的产物。

要正确理解这里的体积对比。191MB 看起来比 62MB 的 jar 大，但两者不可比：**jar 需要外部 JRE 才能运行**，而原生可执行文件自带运行时。放到镜像里看就反过来了——JVM 路线的基础镜像是 366MB 的 JRE 镜像加应用，原生路线理论上只需要一个近乎空的运行时基础镜像加这 191MB。

### 封闭世界假设

原生镜像最大的限制来自 GraalVM 的封闭世界假设：**能到达的代码在构建期就定死，运行期不再有新的类加载。**

GraalVM 本身不认识反射、动态代理、资源加载这些动态行为，需要靠提示文件告诉它。Spring 的 AOT 处理会自动生成这些提示，所以大多数框架层面的问题已经被处理好了。真正需要你注意的是那些会让 **Bean 定义随运行期条件变化**的写法：

- `@Profile` 与 profile 专属配置
- `@ConditionalOnProperty` 与各种 `.enabled` 开关

这和 11.4 里 JVM AOT 的限制是同一批——因为原生镜像整条链路都走 AOT，JVM AOT 的限制在这里是加强版：不只是“不生效”，而是**构建期就按某一种条件算死了 Bean 定义**。

实际判断方法很简单：如果你的应用启动时依赖环境变量、命令行参数来决定“装配哪些 Bean”，那它就不适合原生镜像。反过来，如果装配过程是固定的，只是配置值在变（数据库地址、超时时间这类），原生镜像完全没有问题。

### 什么时候值得用

| 场景 | 是否适合 |
| --- | --- |
| Serverless / FaaS，按请求计费 | 适合，启动时间是主要成本 |
| 需要快速扩缩容的容器服务 | 适合，扩容时的冷启动显著缩短 |
| 常驻服务、实例数固定 | 收益有限，JVM 的启动成本只在部署时付一次 |
| 构建环境受限的 CI | 需要评估，编译对内存和时间的消耗不小 |
| 大量使用运行期条件装配 | 不适合，需要先改代码结构 |
| 依赖不支持原生镜像的第三方库 | 不适合，除非能补齐可达性元数据 |
| 依赖 JVM 生态的动态能力（字节码增强、运行时代理、JMX 动态管理） | 不适合，这些能力在封闭世界里不存在 |

还有一点值得知道：**原生镜像和平台绑定得更紧**。可执行文件是平台相关产物，一份构建只能在同架构同系统的机器上跑。
