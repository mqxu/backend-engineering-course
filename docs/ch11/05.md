# 11.5 CDS：把类加载的结果存下来

AOT 解决的是“Spring 怎么算 Bean 定义”，CDS（Class Data Sharing）解决的是另一个问题：**JVM 每次启动都要读一遍几千个 class 文件、解析、验证、塞进元空间。**

CDS 的思路很直白：事先跑一次应用，把启动过程中加载过的类在内存里的形态存成一个归档文件，之后启动直接映射这个文件，跳过解析和验证。

### Java 21 上用什么

Java 24 引入的 AOT cache（`-XX:AOTCacheOutput`）是 CDS 的继任者，但那个需要 Java 25 及以上。本教程的基线是 Java 21 LTS，所以用的是 CDS：

```shell
# 训练运行：启动一次应用，把加载过的类归档下来
$ java -XX:ArchiveClassesAtExit=application.jsa \
       -Dspring.context.exit=onRefresh \
       -jar activity-server-1.0.0.jar

# 正式运行：挂上归档
$ java -XX:SharedArchiveFile=application.jsa -jar activity-server-1.0.0.jar
```

两个参数值得解释：

`-XX:ArchiveClassesAtExit=application.jsa` 是 JDK 的动态归档开关，进程退出时把这次加载的类写成归档。

`-Dspring.context.exit=onRefresh` 是 Spring Boot 提供的属性，让应用在容器 refresh 完成之后直接退出。训练运行的目的只是“让类被加载”，不需要真的把服务跑起来，这个属性避免训练运行卡在常驻状态。官方文档里 Dockerfile 的写法用的也是它。

还有一个前置条件容易漏：**归档必须在解压形态下生成，也必须用在解压形态上**。对可执行 jar 做训练运行，归档挂上去是没有效果的——因为可执行 jar 里的类是嵌套 jar，进不了归档。官方文档明确写了这一点：

> You have to use the cache file with the extracted form of the application, otherwise it has no effect.

### 归档里有什么、缺什么

训练运行会打印大量这样的警告：

```text
[warning][cds] Skipping jdk/proxy2/$Proxy120: Unsupported location
[warning][cds] Skipping jdk/proxy2/$Proxy161: Unsupported location
[warning][cds] Skipping org/hibernate/type/format/jakartajson/JsonBJsonFormatMapper: Failed verification
```

统计一下被跳过的类：

```text
235 条 Skipping 记录

158  jdk/proxy2/            JDK 动态代理
  8  jdk/proxy1/            JDK 动态代理
  6  net/bytebuddy/         ByteBuddy 生成的类
  6  com/example/activity/domain/    Hibernate 增强后的实体
  5  jdk/internal/reflect/
```

这里能看出 CDS 的能力边界：**运行期生成的类比构建期固定的类更吃亏**。动态代理的字节码在生成时才知道，没法进归档；Hibernate 增强过的实体类也是同理，`Failed verification` 说明字节码校验没过。

这些警告不影响使用，但如果归档后启动加速不明显，可以先看跳过了多少——跳得越多，归档的收益越小。

### 效果

| 形态 | 三次耗时（秒） | 中位数 | 相对基线 |
| --- | --- | --- | --- |
| 可执行 jar | 4.643 / 4.799 / 4.825 | 4.80 | — |
| 解压布局 | 3.765 / 3.767 / 3.897 | 3.77 | −21% |
| 解压 + CDS | 2.209 / 2.284 / 2.396 | 2.28 | −52% |

CDS 单独带来约 1.5 秒的提升，比解压更明显。

再看 AOT 和 CDS 叠加：

| 形态 | 三次耗时（秒） | 中位数 | 相对基线 |
| --- | --- | --- | --- |
| AOT jar | 3.810 / 3.865 / 3.878 | 3.87 | −19% |
| AOT + 解压 | 2.982 / 3.052 / 3.224 | 3.05 | −36% |
| AOT + 解压 + CDS | 1.624 / 1.647 / 1.760 | 1.65 | −66% |

**1.65 秒**。从 4.8 秒压到这个数字，全程没有改一行业务代码，也没有引入任何外部依赖——只是换了打包形态，让 JVM 少做了两次重复劳动。

### 归档的三个约束

CDS 不是随时都能用的，有三条硬约束：

**归档与平台绑定。** 归档里存的是内存映像，包含平台相关的结构。在 macOS 上生成的 `.jsa` 拿到 Linux 容器里用会直接失败。所以容器场景下，训练运行必须在容器构建阶段完成（11.6 的做法）。

**归档与 JDK 版本绑定。** 换了 JDK 小版本要重新生成，否则可能加载失败。

**应用一变，归档就作废。** 类名、方法签名变了，归档里的内容就对不上。所以生成归档是**构建流程的一部分**，不是一次性操作——每次发布新版本都要重新做训练运行。

**归档的体积也要算进去。** 实测这个应用的 `.jsa` 是 111 MB，比整个 jar（62MB）还大。如果只是为了让启动快 1.5 秒，就要在镜像里多塞 111MB，这笔账要自己算。11.6 会看到它对镜像大小的实际影响。
