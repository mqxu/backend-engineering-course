# 11.2 jarmode 从 layertools 换成了 tools

要在容器里做分层，需要把 jar 按层解开。这一步靠 jar 自身的一个特殊启动模式完成——`-Djarmode`。

4.x 的命令是：

```shell
$ java -Djarmode=tools -jar resource-hub-1.0.0.jar
```

不带子命令时它会打印可用命令：

```text
Usage:
  java -Djarmode=tools -jar resource-hub-1.0.0.jar

Available commands:
  extract      Extract the contents from the jar
  list-layers  List layers from the jar that can be extracted
  help         Help about any command
```

`list-layers` 的输出就是四层的名字：

```text
dependencies
spring-boot-loader
snapshot-dependencies
application
```

### 和旧写法的差别

Boot 3.2 之前用的是另一个模式名：

```shell
$ java -Djarmode=layertools -jar my-app.jar extract   # 3.1 及更早
$ java -Djarmode=tools    -jar my-app.jar extract     # 3.3 及以后
```

`layertools` 这个模式名在 4.x 里已经不存在。很多现有的 Dockerfile 模板还写着 `layertools`，拿到 4.x 项目上会直接报错——报错信息只是说 jarmode 不认识，不会提示你该换成什么。

`extract` 的完整选项：

```text
Options:
  --launcher                     Whether to extract the Spring Boot launcher
  --layers string list           Layers to extract
  --destination string           Directory to extract files to.
  --libraries string             Name of the libraries directory. Defaults to lib/
  --application-filename string  Name of the application JAR file.
  --force                        Whether to ignore non-empty directories, extract anyway
```

### `--layers` 默认不带启动器

执行官方 Dockerfile 里那条命令：

```shell
$ java -Djarmode=tools -jar resource-hub-1.0.0.jar extract --layers --destination extracted
```

产出四个目录，但其中两个是空的：

```text
extracted/application/             88 KB
extracted/dependencies/            62 MB
extracted/snapshot-dependencies/    0 B
extracted/spring-boot-loader/       0 B
```

`snapshot-dependencies` 为空好理解——工程里没有 SNAPSHOT 依赖。但 `spring-boot-loader` 为空值得说明：**不加 `--launcher` 时，`extract` 不复制启动器代码**。

原因是默认的提取方式换了一种启动思路。看 `extracted/application/` 里那个 87KB 的 jar 的 MANIFEST：

```text
Main-Class: com.example.resourcehub.ResourceHubApplication
Class-Path: lib/logback-classic-1.5.38.jar lib/logback-core-1.5.38.jar
 lib/log4j-to-slf4j-2.25.5.jar lib/spring-boot-autoconfigure-4.1.1.jar
 ...（约 100 个依赖，全部相对路径）
```

对比一下：

| | 可执行 jar | `extract` 后的薄 jar |
| --- | --- | --- |
| `Main-Class` | `...loader.launch.JarLauncher` | 应用主类 |
| 依赖位置 | 嵌套在 `BOOT-INF/lib/` | 同级 `lib/` 目录 |
| 靠什么找到类 | 启动器自建类加载器 | JDK 原生的 `Class-Path` |
| 需要启动器吗 | 需要 | 不需要 |

薄 jar 用的是 **JDK 从 1.0 就支持的 `Class-Path` 机制**，加载路径完全由标准类加载器处理。少了嵌套 jar 的展开和自定义类加载，这正是解压后启动更快的原因。

### 拼装与验证

`Class-Path` 里写的是相对路径（`lib/xxx.jar`），相对于薄 jar 自己所在的目录。所以各层不能就地放着跑，要按官方 Dockerfile 那样拷到同一个工作目录：

```shell
$ mkdir flat
$ cp -R extracted/dependencies/.       flat/
$ cp -R extracted/spring-boot-loader/. flat/
$ cp -R extracted/snapshot-dependencies/. flat/
$ cp -R extracted/application/.        flat/
```

拼出来就是 `lib/` 加一个 jar 的简单结构：

```text
flat/lib/                          96 个依赖 jar
flat/resource-hub-1.0.0.jar        87 KB
```

启动验证：

```shell
$ cd flat && java -jar resource-hub-1.0.0.jar --server.port=18081
```

```text
Tomcat started on port 18081 (http) with context path '/'
Started ResourceHubApplication in 4.138 seconds (process running for 4.347)
```

健康检查与接口都正常：

```json
{"components":{"db":{...},"diskSpace":{...},"livenessState":{"status":"UP"},
 "ping":{"status":"UP"},"readinessState":{"status":"UP"},"ssl":{...}},"status":"UP"}
```

```text
GET /api/resources -> 200
```

到这里可以确认一件事：**解压布局跑的是同一个应用，行为没有任何差别。**
