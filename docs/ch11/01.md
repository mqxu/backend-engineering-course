# 11.1 可执行 jar 里装了什么

`mvn package` 之后，`target/` 下会出现两个文件：

```text
target/activity-server-1.0.0.jar           64635306 字节
target/activity-server-1.0.0.jar.original     51 KB
```

构建日志里写明了这两个文件的关系：

```text
[INFO] --- spring-boot:4.1.1:repackage (repackage) @ activity-server ---
[INFO] Replacing main artifact .../activity-server-1.0.0.jar with repackaged archive,
       adding nested dependencies in BOOT-INF/.
[INFO] The original artifact has been renamed to .../activity-server-1.0.0.jar.original
```

`maven-jar-plugin` 先打出普通的 jar（只有编译产物，51KB），随后 `spring-boot-maven-plugin` 的 `repackage` 目标把它重新打包成可执行 jar，原始产物改名为 `.jar.original` 留在旁边。这个 `.original` 文件没什么用，但它解释了“为什么我的 jar 突然从 51KB 变成 62MB”——依赖被塞进来了。

### 目录骨架

解开可执行 jar，顶层只有四个目录：

```text
BOOT-INF/classes/     应用自己的类和活动（application.yml、data.sql 都在这）
BOOT-INF/lib/         所有依赖 jar，一个不落地以嵌套形式放在这
META-INF/             MANIFEST.MF、maven 元数据、services 声明
org/springframework/boot/loader/   启动器代码
```

体积分布很能说明问题：

| 目录 | 大小 | 占比 |
| --- | --- | --- |
| `BOOT-INF/lib` | 62 MB | 99.6% |
| `BOOT-INF/classes` | 272 KB | 0.4% |
| `org/springframework/boot/loader` | 604 KB | 1% |
| `META-INF` | 20 KB | — |

单个依赖占前几名的：

```text
hibernate-core-7.4.5.Final.jar        15 MB
byte-buddy-1.18.11.jar               4.4 MB
tomcat-embed-core-11.0.24.jar        3.5 MB
h2-2.4.240.jar                       2.6 MB
spring-web-7.0.9.jar                 2.1 MB
aspectjweaver-1.9.25.1.jar           2.1 MB
```

记住这个比例：**你自己的代码不到千分之五，其余全是依赖**。后面讲分层和镜像构建缓存时，所有优化都建立在这个事实上。

### MANIFEST.MF 里的六个字段

`META-INF/MANIFEST.MF` 是理解可执行 jar 的钥匙：

```text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.activity.ActivityServerApplication
Spring-Boot-Version: 4.1.1
Spring-Boot-Classes: BOOT-INF/classes/
Spring-Boot-Lib: BOOT-INF/lib/
Spring-Boot-Classpath-Index: BOOT-INF/classpath.idx
Spring-Boot-Layers-Index: BOOT-INF/layers.idx
```

三件事值得说：

**`Main-Class` 指向框架的类，不是你的主类。** 这是最容易让人困惑的一点。`java -jar` 只会调用 `Main-Class` 的 `main` 方法，而它指向 `JarLauncher`——框架的启动器。你的主类写在 `Start-Class` 里，由 `JarLauncher` 读出来再反射调用。

为什么绕这一圈？因为 **JDK 不认识嵌套 jar**。`BOOT-INF/lib/hibernate-core-7.4.5.Final.jar` 是 jar 里的 jar，标准类加载器打不开它。`JarLauncher` 做的工作就是自建一套类加载机制，把这些嵌套 jar 展开成可加载的 classpath，然后再启动你的应用。

**`Spring-Boot-Classes` 与 `Spring-Boot-Lib` 声明了这两类内容的相对路径。** `JarLauncher` 靠这两个字段定位，所以你手动改目录结构会直接启动失败。

**`Spring-Boot-Layers-Index` 有一定就有。** 只要用 `spring-boot-maven-plugin` 打包，`BOOT-INF/layers.idx` 就会生成，不需要额外配置——这一点和很多文章说的“要手动开分层”不一样。

### 4.x 换了 loader 的包名

`org/springframework/boot/loader/` 下的子包分布：

```text
31  net/      网络协议相关（jar:、nested: 的 URL 处理）
28  zip/      ZIP 解析
19  launch/   启动器，JarLauncher、WarLauncher、PropertiesLauncher 在这里
15  jar/      嵌套 jar 的文件系统抽象
 9  nio/
 4  log/
 3  ref/
 3  jarmode/  命令行模式，就是后面 jarmode=tools 的入口
```

`launch` 这个包名是 Boot 3.2 之后启用的，2.x 与 3.0/3.1 里启动器直接在 `loader` 包下（`org.springframework.boot.loader.JarLauncher`）。如果你维护的老项目里写过自定义启动器、或者有代码 `import org.springframework.boot.loader.JarLauncher`，升级时会遇到“找不到符号”，原因就在这里。
