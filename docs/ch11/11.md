# 11.11 小结与下一步

这一篇从 `mvn package` 的产物一路走到原生可执行文件：

- **可执行 jar 的结构**：`BOOT-INF/lib` 塞了 99.6% 的体积，`Main-Class` 指向 `loader.launch.JarLauncher` 而不是你的主类，原因是 JDK 不认识嵌套 jar；`loader` 下的 `launch` 包名是 Boot 3.2 之后才有的
- **4.x 的 jarmode 换成了 `tools`**：`layertools` 已不存在；`extract --layers` 默认不带启动器，产出的是靠 `Class-Path` 启动的薄 jar，必须把四层拼到同一目录才能跑
- **分层按变化频率切**：`dependencies` / `spring-boot-loader` / `snapshot-dependencies` / `application`，顺序就是往镜像里添加的顺序
- **解压能提速**：实测启动从 4.80 秒降到 3.77 秒，省掉的是嵌套 jar 的展开与自定义类加载
- **JVM 上的 AOT**：`-Pnative package` 触发 `process-aot`，219 个 Bean 定义源文件编译进产物；必须加 `-Dspring.aot.enabled=true` 才生效（实测 4.80 → 3.87 秒）；限制是 Bean 定义不能在运行期变
- **4.x 的提示文件换了格式**：不再生成 `reflect-config.json` 等五个文件，而是统一的 `reachability-metadata.json`，这一点和官方文档现有表述不一致
- **CDS**：训练运行 + 归档，实测 3.77 → 2.28 秒；与 AOT 叠加是 1.65 秒，比基线快 66%；代价是 111MB 的归档和“必须在目标平台生成”的约束
- **容器化的两个细节**：`COPY --chown` 与 `COPY` + `RUN chown` 差 64MB（CDS 场景下差 180MB）；分层不减小镜像体积，减少的是改动后的重建量
- **容器内实测**：单层 4.81 秒、分层 3.98 秒、分层加 CDS 2.29 秒，非 root 用户 10001 运行正常
- **Buildpacks**：`mvn spring-boot:build-image` 一条命令出镜像，默认 builder 是 `paketobuildpacks/builder-noble-java-tiny`；省事但控制力弱
- **GraalVM 原生镜像**：本机实测编译 4 分 37 秒，产出 191MB 可执行文件，启动 0.268 秒（JVM 是 4.80 秒），内存 167MB（JVM 是 546MB）；限制来自封闭世界假设
- **上线前的一批配置**：配置走环境变量而不是烤进镜像、容器内存感知与 `JAVA_TOOL_OPTIONS`、优雅停机、日志走标准输出、密钥不进镜像

到这里，后端从写代码到交付的整条链路走通了。可下一次打开浏览器，还是只有 `curl` 能用——**用户看到的界面还不存在**。

下一篇开始全端实战。前端部分会从零搭一个 Vue 3 + Element Plus 的管理端，把这一路写下来的 REST 接口接上去：活动列表与分页、文件上传、登录与令牌续期、路由守卫。接口的形态在前 11 篇里已经固定了（统一响应体 `ApiResponse`、分页 `PageResult`、JWT 在 `Authorization` 头），前端要做的就是把它们串起来。
