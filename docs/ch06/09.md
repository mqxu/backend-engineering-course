# 九、并发写入：不要读-改-写

### 9.1 有并发漏洞的写法

下载量自增最容易写错：

```java
// 错误写法
ResourceItem item = repository.findById(id).orElseThrow();
item.setDownloadCount(item.getDownloadCount() + 1);
repository.save(item);
```

两个请求同时进来，都读到 5，各自加 1 后写回 6。期望的 7 丢了。这就是**丢失更新**（lost update）。

顺带说明：被 `@Transactional` 包住也不会变对。事务保证了原子性（要么全做要么全不做），但两个事务都成功提交了，只是结果错了——这是隔离级别的问题，不是原子性的问题。

### 9.2 交给数据库做原子更新

```java
/**
 * 原子自增下载量。
 *
 * <p>不要写成"查出来 → setDownloadCount(n+1) → save"，那是有并发漏洞的读-改-写：
 * 两个请求同时读到 5，各自加 1 后写回，最终是 6 而不是期望的 7。
 * 交给数据库执行 UPDATE ... SET x = x + 1 才能保证正确。
 */
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("""
        UPDATE ResourceItem r
           SET r.downloadCount = r.downloadCount + 1
         WHERE r.id = :id
           AND r.enabled = true
        """)
int incrementDownloadCount(@Param("id") Long id);
```

调用处：

```java
@Transactional
public ResourceResponse download(Long id) {
    // 直接发原子 UPDATE，由数据库保证并发正确性
    int affected = resourceRepository.incrementDownloadCount(id);
    if (affected == 0) {
        throw BusinessException.notFound("资源不存在或已下架：id=" + id);
    }
    return ResourceResponse.from(requireEnabledResource(id));
}
```

三个细节值得注意：

- **`@Modifying` 是必须的**。不加它，Spring Data 会以为这是个查询，执行时报 `Expecting a SELECT query`。
- **返回 `int` 拿到影响行数**。这是判断“资源是否存在或已下架”的免费信息，不用再多查一次。
- **`clearAutomatically = true` 的含义**：批量 UPDATE 绕过了持久化上下文，上下文里缓存的实体还是旧值。加上它会自动清空上下文，避免后续读到过期数据。`flushAutomatically = true` 则在执行前先把待写入的变更刷出去。这两个参数配错会出现“更新完了查出来还是旧值”的怪现象。

### 9.3 @Version 乐观锁

上面的下载量是“自增”语义，天然适合原子 UPDATE。但“读取-计算-写回”的业务（比如库存扣减、状态机流转）没法用自增表达，这时用乐观锁：

```java
@Version
private Long version;
```

加了它之后，Hibernate 的 UPDATE 会自动带上版本条件：

```sql
UPDATE resource_item SET title=?, version=version+1 WHERE id=? AND version=?
```

如果有另一个事务先改了这条记录，`version` 对不上，受影响行数为 0，Hibernate 抛 `OptimisticLockException`。捕获后给用户返回“数据已被他人修改，请刷新重试”是标准做法。
