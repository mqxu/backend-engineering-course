# 二、数据源：从自动配置到连接池

### 2.1 嵌入式数据库是自动配好的

Spring Boot 的默认行为是：**类路径上检测到嵌入式数据库驱动，就自动配一个内存数据源**，不需要写任何 `url`。官方明确支持 H2、HSQL，Derby 已标记为废弃（`datasource-embedded-database-connection` 相关文档里标了 deprecated）。

本项目的 `application.yml` 只写了最必要的东西：

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:resourcehub;DB_CLOSE_DELAY=-1;MODE=MySQL
    driver-class-name: org.h2.Driver
    username: sa
    password: ""
```

三个参数里有两个是为了教学方便：

| 参数 | 作用 |
| --- | --- |
| `DB_CLOSE_DELAY=-1` | 最后一个连接关闭后不销毁数据库。不加的话，连接池空闲回收时数据库会被清空 |
| `MODE=MySQL` | 让 H2 按 MySQL 的语法规则解析，SQL 写法可以平移 |

有几个容易忽略的点：

- **驱动类名通常可以省略**。Spring Boot 能从 `url` 的 `jdbc:h2:` 前缀推断出驱动，写出来只是为了让初学者看清对应关系。
- **多个嵌入式数据库并存时要显式指定**。同时引了 H2 和 HSQL 时，用 `spring.datasource.embedded-database-connection=h2` 选一个；设为 `none` 则关闭嵌入式数据源自动配置。
- **测试时希望每个上下文用独立库**，加 `spring.datasource.generate-unique-name=true`，否则多个测试类共用同一个内存库，数据会互相干扰。

### 2.2 连接生产数据库

换到 MySQL 或 PostgreSQL 时，改动只有依赖和三项配置：

```yaml
spring:
  datasource:
    url: jdbc:mysql://localhost:3306/resourcehub?useSSL=false&serverTimezone=Asia/Shanghai
    username: resourcehub
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
```

密码不要写在 yml 里，用环境变量占位（第 3 篇讲过外部化配置的优先级）。

### 2.3 连接池是按固定顺序挑的

官方文档给出的选择算法是一个优先级队列，命中即用：

| 顺序 | 实现 | 触发条件 |
| --- | --- | --- |
| 1 | **HikariCP** | 类路径上存在，就总是选它 |
| 2 | Tomcat JDBC Pool | 没有 HikariCP，但有 `tomcat-jdbc` |
| 3 | Commons DBCP2 | 没有前两个，但有 `commons-dbcp2` |
| 4 | Oracle UCP | 以上都没有，但有 `ucp` |

引入 `spring-boot-starter-jdbc` 或 `spring-boot-starter-data-jpa` 就会带上 HikariCP，所以实际上绝大多数项目用的都是它。想绕开这个顺序、强行指定，用 `spring.datasource.type` 写全限定类名。

**注意 `spring-boot-starter-web` 不含 JDBC**。只引 Web 依赖的项目不会有连接池，这一点在排查“为什么 `DataSource` 注入不进来”时经常是根因。

### 2.4 HikariCP 实际生效的参数

网上讲连接池调参的文章常把默认值写得含糊。下面这份是实测读出来的——在案例工程里注入 `HikariDataSource` 后直接调用它的 getter（HikariCP 7.0.2）：

```
池名 poolName                = HikariPool-1
jdbcUrl                      = jdbc:h2:mem:resourcehub;DB_CLOSE_DELAY=-1;MODE=MySQL
maximumPoolSize              = 10
minimumIdle                  = 10
connectionTimeout(ms)        = 30000
idleTimeout(ms)              = 600000
maxLifetime(ms)              = 1800000
leakDetectionThreshold(ms)   = 0
validationTimeout(ms)        = 5000
keepaliveTime(ms)            = 120000
autoCommit                   = true
```

启动日志里也能看到它的生命周期：

```
HikariDataSource : HikariPool-1 - Starting...
HikariPool       : HikariPool-1 - Added connection conn0: url=jdbc:h2:mem:resourcehub user=SA
HikariDataSource : HikariPool-1 - Start completed.
```

### 2.5 该动哪几个参数

默认值对教学项目和中小系统足够用。真正需要调的是下面这几个：

| 参数 | 默认 | 什么时候要改 |
| --- | --- | --- |
| `maximum-pool-size` | 10 | 并发高且 SQL 快时上调；**不是越大越好**，池子超过数据库的连接上限反而会让请求排队 |
| `minimum-idle` | 与最大值相同 | 想让闲置时释放连接（省数据库内存）就调小，代价是突发流量要等新建连接 |
| `connection-timeout` | 30000 | 拿不到连接时的等待上限。**不要设成 0**（无限等待），那会让线程永久挂住 |
| `max-lifetime` | 1800000 | 必须**小于**数据库侧的连接空闲超时（MySQL 默认 8 小时，但中间件常设更短），否则会拿到已被服务端断开的连接 |
| `leak-detection-threshold` | 0（关闭） | 排查“连接不够用”时临时设为 10000（10 秒），日志会打印出借出超过阈值却没归还的调用栈 |
| `keepalive-time` | 120000 | 走防火墙或云数据库时保留，用于探活 |

对应到 yml 的写法：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 3000
      max-lifetime: 1200000
      leak-detection-threshold: 10000
      pool-name: resource-hub-pool
```

> **连接池耗尽不是加池子能解决的**
>
> 出现“连接池满了”时，先分清是 SQL 慢占着连接不放，还是代码借了连接没还。前者要优化 SQL 或加索引，后者要看有没有在事务里调用外部 HTTP 接口——那类操作会把数据库连接白白占住几百毫秒到几秒。把池子从 10 加到 100，只是把问题推后。

### 2.6 延迟获取连接

Spring Boot 4 新增了一个开关：

```yaml
spring:
  datasource:
    connection-fetch: lazy
```

默认情况下，一次事务开始就立刻从池里取一个连接。设为 `lazy` 后，直到真正执行第一条 SQL 才取连接。好处是“开了事务但没发 SQL”的场景（比如只做校验、构造响应的只读事务）不再占用连接。

代价是事务的隔离性边界会变得微妙——连接是延迟绑定的，事务开始到取连接之间发生的事不受事务保护。**只在确认业务逻辑不需要这个边界时使用**。

### 2.7 JNDI 数据源

部署到传统应用服务器（Tomcat、WebLogic）且连接池由容器管理时，用 `spring.datasource.jndi-name` 替代 url / username / password 三项。容器化的 Spring Boot 应用基本用不到。
