# 七、事务：边界、脏检查与失效场景

### 7.1 事务边界画在 Service 层

```java
@Service
public class ActivityService {

    @Transactional(readOnly = true)
    public PageResult<ActivityResponse> search(...) { /* ... */ }

    @Transactional
    public ActivityResponse create(ActivityCreateRequest request) { /* ... */ }
}
```

三条原则：

- **Controller 不加事务**。它只做协议转换，加事务会把事务范围扩大到参数绑定、JSON 序列化，白占连接。
- **Repository 不加事务**。`JpaRepository` 的方法自带事务，再包一层没必要。
- **一次业务操作一个事务**。“创建活动时要同时校验场地存在 + 查重 + 插入”是一个整体，要么全成功要么全回滚，这个边界只能在 Service 上。

### 7.2 readOnly = true 不只是语义标注

```java
@Transactional(readOnly = true)
public PageResult<ActivityResponse> search(...) { /* ... */ }
```

它的实际效果分几层：

| 层面 | 效果 |
| --- | --- |
| Hibernate | 跳过脏检查快照，不维护实体的原始状态副本，省内存和 CPU |
| Hibernate | 不执行 `FlushMode` 的自动刷新，避免意外 UPDATE |
| JDBC / 连接池 | 提示驱动和连接池这是只读连接（部分实现会把连接路由到只读副本） |

还有一层作用常被忽略：**它是代码意图的声明**。一个查询方法上标了 `readOnly = true`，就没人会在里面写更新逻辑——写了也会因为 FlushMode 而不生效，在测试阶段就能发现。

### 7.3 脏检查：update 里为什么没有 save

```java
@Transactional
public ActivityResponse update(Long id, ActivityUpdateRequest request) {
    Activity item = requireEnabledActivity(id);
    Venue venue = requireVenue(request.venueId());

    item.updateBasicInfo(request.title(), request.description(), venue,
            request.type(), request.url(), request.fileSize(), request.tags());

    // 注意这里没有调用 save()
    return ActivityResponse.from(item);
}
```

事务内查出来的实体处于**托管状态**（managed）。修改它的字段后，Hibernate 在事务提交时会把当前状态与加载时的快照逐一比对，发现差异就自动发 UPDATE。这就是脏检查（dirty checking）。

推导出两个实践结论：

1. **不需要 `save()`**，调了也不报错，只是多余（`save()` 对托管实体走的是 merge，会多一次内部处理）。
2. **不需要的字段变更也会被写库**。如果只是想读出来用一下，结果顺手改了某个字段，提交时就发出 UPDATE 了。在只读方法上不加 `readOnly = true`，这类意外更新很难查。

### 7.4 事务失效的六种场景

`@Transactional` 失效是排查成本最高的 Spring 问题之一——它不报错，只是回滚不生效或者事务根本没开。六种场景，命中过一种就建议把这一节贴到墙上：

**一、同类内部自调用。** 这是最常见的：

```java
@Service
public class OrderService {

    public void submit(Long id) {
        // 直接调本类的 createOrder，@Transactional 不生效
        createOrder(id);
    }

    @Transactional
    public void createOrder(Long id) { /* ... */ }
}
```

原因在于实现机制：Spring 的事务是通过**代理对象**加进去的。外部调用先进入代理，代理再调真实对象。而 `submit()` 内部调 `createOrder()` 用的是 `this`，绕过了代理。

三种解法，按推荐程度排序：

| 解法 | 做法 | 代价 |
| --- | --- | --- |
| 拆到另一个 Bean | 把 `createOrder` 移到一个独立 Service | 最干净，推荐 |
| 注入自身 | `@Autowired private OrderService self;` 然后 `self.createOrder(id)` | 有一点点别扭，但简单有效 |
| `AopContext.currentProxy()` | 需要 `@EnableAspectJAutoProxy(exposeProxy = true)` | 引入了对 AOP 细节的依赖，不推荐 |

**二、方法是 private 或 final。** Spring 用 CGLIB 生成子类来实现代理，private 方法不能被覆盖，final 方法不能被子类重写，两者都加不上事务。同理，**类本身是 final 的也不行**。

**三、异常类型不对。** `@Transactional` 默认只在遇到 `RuntimeException` 和 `Error` 时回滚，**受检异常（checked exception）不回滚**：

```java
@Transactional
public void importData() throws IOException {
    saveA();
    throw new IOException("文件读取失败");   // 事务不会回滚！
}
```

两种修正方式：

```java
// 方式一：指定回滚的异常类型
@Transactional(rollbackFor = Exception.class)

// 方式二：捕获受检异常后转成运行时异常抛出（本项目用 BusinessException）
catch (IOException e) {
    throw BusinessException.badRequest("文件读取失败：" + e.getMessage());
}
```

推荐第二种：业务异常本来就是运行时异常，还能被全局异常处理器翻译成规范的响应。

**四、方法不是 public。** 同第二点，代理拦不到。

**五、多线程。** 事务上下文绑定在线程上（`ThreadLocal`）。在 `@Transactional` 方法里起一个新线程去写库，新线程不在事务里，主线程回滚它也回滚不了。

**六、数据库引擎不支持。** MySQL 的 MyISAM 引擎不支持事务，建表时的 `ENGINE=MyISAM` 会让所有 `@Transactional` 变成摆设。用 InnoDB。

### 7.5 传播行为

多个事务方法互相调用时，用哪个事务？这就是传播行为。默认的 `REQUIRED` 覆盖了 95% 的场景：

| 传播行为 | 行为 | 典型场景 |
| --- | --- | --- |
| `REQUIRED`（默认） | 有事务就加入，没有就新建 | 绝大多数业务方法 |
| `REQUIRES_NEW` | **总是新建**，挂起外层事务 | 记审计日志——主业务回滚了，日志也要留下 |
| `NESTED` | 在当前事务里开保存点 | 批量导入，单条失败只回滚单条 |
| `SUPPORTS` | 有就用，没有就算了 | 既能被事务调用也能被非事务调用的查询方法 |
| `NOT_SUPPORTED` | 挂起当前事务，非事务执行 | 事务内的耗时外部调用 |
| `MANDATORY` | 必须已有事务，否则抛异常 | 强制某个方法只能被事务方法调用 |
| `NEVER` | 必须没有事务，否则抛异常 | 明确禁止在事务中执行的方法 |

`REQUIRES_NEW` 有个容易踩的地方：它会占用**第二条数据库连接**。外层事务的连接还没释放，新事务又要一条，连接池小时容易死锁。用它之前先确认池子够用。
