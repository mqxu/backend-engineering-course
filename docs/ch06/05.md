# 五、实体映射：把案例项目的实体讲透

### 5.1 不需要 persistence.xml

JPA 传统做法要写 `META-INF/persistence.xml` 声明实体，Spring Boot 取消了这一步，改成**实体扫描**：

- 扫描的起点是**主类所在的包**（`com.example.activity`）；
- 识别 `@Entity`、`@Embeddable`、`@MappedSuperclass`；
- 要扫描包外的实体，加 `@EntityScan("其他包")`。

这就是第 2 篇反复强调“主类必须放在根包”的原因之一——放错位置，实体扫不到，启动时报 `Not a managed type`。

### 5.2 逐行看 Activity

`domain/Activity.java` 的字段声明部分：

```java
@Entity
@Table(name = "activity")
public class Activity {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 128)
    private String title;

    @Column(length = 512)
    private String description;

    /**
     * 多对一关联。抓取策略显式声明为 LAZY：
     * 默认值是 EAGER，只要查活动就顺带把场地查出来，在列表接口上会造成多余的查询。
     */
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "venue_id", nullable = false)
    private Venue venue;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 16)
    private ActivityType type;
    // ... 其余字段
}
```

四个决策值得展开：

**一、`@ManyToOne` 显式写成 LAZY。** JPA 规范里 `@ManyToOne` 的默认抓取策略是 `EAGER`——这是规范设计上的历史包袱。不显式声明，每查一条活动都会自动关联查出场地，列表接口会退化成 N+1。声明成 LAZY 之后，关联数据只在真正访问时才加载（第八节会看到两种策略的 SQL 差异）。

**二、`@JoinColumn` 指明外键列名。** 不写的话 Hibernate 会自己拼一个（`venue_id` 恰好是默认猜测结果，但列名稍有不同就会猜错）。

**三、枚举用 `@Enumerated(EnumType.STRING)`。** 默认是 `ORDINAL`（存序号 0、1、2、3）。用序号的隐患是：将来在枚举中间插入一个新值，历史数据的含义就整体错位了——原来存 2 是 `CODE`，插入一个常量后 2 变成了别的类型，而且**不会报任何错**。

**四、`nullable` / `length` 与建表 DDL 联动。** 这些约束会体现在 Hibernate 生成的建表语句里。注意它们只对 `ddl-auto` 建表生效，如果表由 Flyway 管理，这些声明只是给 `validate` 校验用的，真正的约束以迁移脚本为准。

### 5.3 主键生成策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `IDENTITY` | 交给数据库自增（MySQL / H2 的 AUTO_INCREMENT） | 本项目使用 |
| `SEQUENCE` | 用数据库序列（PostgreSQL / Oracle） | 支持序列的库 |
| `TABLE` | 用一张表模拟序列 | 不推荐，性能和并发都差 |
| `AUTO` | 由框架按方言挑 | 省事但不可控，跨库迁移时容易出意外 |
| `UUID` | 应用侧生成 UUID 主键 | 分布式、需要提前知道 id 的场景 |

`IDENTITY` 有一个隐蔽的副作用：**插入时无法批量**。因为要拿到自增主键，Hibernate 必须逐条执行 INSERT 并等待返回，`hibernate.jdbc.batch_size` 对它无效。需要批量写入时改用 `SEQUENCE` 或 UUID。

### 5.4 时间字段与生命周期回调

```java
@Column(name = "created_at", nullable = false, updatable = false)
private LocalDateTime createdAt;

@Column(name = "updated_at", nullable = false)
private LocalDateTime updatedAt;

/** 插入前回调：创建时间和更新时间都取当前时刻 */
@PrePersist
void onCreate() {
    LocalDateTime now = LocalDateTime.now();
    this.createdAt = now;
    this.updatedAt = now;
    if (this.approvedCount == null) {
        this.approvedCount = 0;
    }
    if (this.enabled == null) {
        this.enabled = true;
    }
}

/** 更新前回调：只刷新更新时间 */
@PreUpdate
void onUpdate() {
    this.updatedAt = LocalDateTime.now();
}
```

`updatable = false` 是个保险：即使代码里不小心改了 `createdAt`，Hibernate 也不会把它写进 UPDATE 语句。

用回调而不是在每个 Service 方法里手工 `setCreatedAt(now())`，好处是**不可能漏**——新增路径、批量导入路径、测试代码路径全都覆盖，因为它是实体自身的生命周期事件。

> **`@PrePersist` 与数据库默认值的分工**
>
> 生产环境通常还会在表上给时间字段加 `DEFAULT CURRENT_TIMESTAMP`。两者不冲突：回调负责 Java 侧赋值，数据库默认值负责“绕过应用直接写库”的场景（比如运维手工修数据）。

### 5.5 领域行为收进实体

实体里除了 getter，还有三个方法：

```java
/** 被报名通过一次。报名通过数是热点字段，后续可以用原子 UPDATE 替换以应对并发 */
public void increaseApprovedCount() {
    this.approvedCount = (this.approvedCount == null ? 0 : this.approvedCount) + 1;
}

public void updateBasicInfo(String title, String description, Venue venue, ActivityType type,
                            String url, Long fileSize, String tags) { /* ... */ }

/** 下架。不物理删除，保留数据用于统计 */
public void disable() {
    this.enabled = false;
}
```

这叫“富领域模型”的写法：把“下架”这个动作定义在实体上，调用方写 `item.disable()` 而不是 `item.setEnabled(false)`。区别在于语义——`disable()` 表达的是业务动作，将来下架需要附带别的处理（记录下架时间、发通知、状态机流转），改一个方法就够了；而满世界散落的 `setEnabled(false)` 得一处一处找。

### 5.6 equals 与 hashCode 只按 id

```java
@Override
public boolean equals(Object o) {
    if (this == o) {
        return true;
    }
    if (!(o instanceof Activity other)) {
        return false;
    }
    return id != null && id.equals(other.id);
}

@Override
public int hashCode() {
    return Objects.hashCode(id);
}
```

几个要点：

- **只用 id 判断**。实体在 `persist()` 前后 id 从 null 变成具体值，拿业务字段（比如 title）参与 equals 会导致“同一个对象放进 `Set` 后取不出来”。
- **`id != null` 这个前提很重要**：两个都还没入库的对象（id 都是 null）不应被视为相等，否则会把两个不同的新活动当成同一个。
- 用 `instanceof Activity other` 这种模式匹配写法（Java 16+），比先判断再强转干净。

### 5.7 ddl-auto 的取值与默认规则

| 取值 | 行为 | 用在哪 |
| --- | --- | --- |
| `none` | 什么都不做 | 生产（配合 Flyway） |
| `validate` | 只校验实体与表是否一致，不一致就启动失败 | 生产推荐 |
| `update` | 缺的表和列自动补上 | **不推荐**，改列类型、删列它都不管，容易积累不一致 |
| `create` | 启动时建表，**不删旧表** | 测试 |
| `create-drop` | 启动建表，关闭删表 | 本项目（内存库） |

默认值的判定规则是：

- 嵌入式数据库（H2 / HSQL / Derby）+ **没有** Flyway 或 Liquibase → 默认 `create-drop`；
- 其他所有情况 → 默认 `none`。

所以“连了 MySQL 却没建表”不是 bug，是默认值在起作用——生产库上必须自己用迁移工具建表。

> **`update` 是最容易埋雷的选项**
>
> 它看起来最省事，实际上只会加、不会改也不会删。某次把一个字段从 `varchar(64)` 改成 `varchar(128)`，`update` 模式下什么都不会发生，代码里却以为改完了；某次删掉一个字段，数据库里的列还在，且带着 NOT NULL 约束，插入立刻失败。用 `validate` 让不一致在启动时就暴露出来。
