# 六、Repository：从派生查询到 Specification

### 6.1 派生查询靠方法名

`repository/VenueRepository.java` 里一行实现都没有，方法却能用：

```java
public interface VenueRepository extends JpaRepository<Venue, Long> {

    /** 按排序值升序、其次按 id 升序 */
    List<Venue> findAllByOrderByNameAsc();

    Optional<Venue> findByName(String name);

    boolean existsByName(String name);
}
```

Spring Data 在启动时解析方法名生成实现。构词规则是固定的几段：

```
findBy / readBy / queryBy / getBy / countBy / existsBy / deleteBy
  + 条件（属性名 + 关键字）
  + OrderBy + 排序属性 + Asc/Desc
```

条件的常用关键字：

| 关键字 | 生成的 SQL 片段 | 例子 |
| --- | --- | --- |
| `And` / `Or` | `AND` / `OR` | `findByTitleAndType` |
| `IsNull` / `IsNotNull` | `IS NULL` / `IS NOT NULL` | `findByUrlIsNull` |
| `Like` / `Containing` | `LIKE` | `findByTitleContaining` |
| `GreaterThan` / `LessThan` | `>` / `<` | `findByFileSizeGreaterThan` |
| `Between` | `BETWEEN` | `findByCreatedAtBetween` |
| `In` / `NotIn` | `IN` | `findByIdIn` |
| `IgnoreCase` | 大小写不敏感 | `findByTitleIgnoreCase` |
| `Top` / `First` | 限制条数 | `findTop5ByOrderByDownloadCountDesc` |
| `True` / `False` | 布尔字段 | `findByEnabledTrue` |

**方法名写错会在启动时报错**，不会静默失效——这是派生查询的一个优点。但方法名一长就可读性急剧下降，超过两三个条件时改用 `@Query` 或 Specification。

### 6.2 @Query 与 JPQL

```java
@EntityGraph(attributePaths = {"venue"})
@Query("SELECT r FROM Activity r WHERE r.id = :id")
Optional<Activity> findDetailById(@Param("id") Long id);
```

注意三点：

- JPQL 里写的是**实体名和属性名**（`Activity`、`r.id`），不是表名和列名。这是 JPQL 与原生 SQL 的关键区别——换数据库时不用改。
- 参数用 `:name` 命名形式，配合 `@Param` 绑定（编译时保留参数名需要 `-parameters` 编译参数，Spring Boot 的 Maven 插件默认开启，但写上 `@Param` 更稳妥）。
- 需要原生 SQL 时加 `nativeQuery = true`，代价是失去跨数据库能力。

### 6.3 Specification：动态条件查询

列表接口有“按场地筛、按类型筛、按关键字搜”三个条件，每个都可以不传。用派生查询要写 2³ = 8 个方法，用 JPQL 拼字符串则有拼接错误和注入风险。官方的方案是 `Specification`：

```java
/** 组装动态查询条件 */
private Specification<Activity> buildSpecification(Long venueId, ActivityType type, String keyword) {
    return (root, query, cb) -> {
        List<Predicate> predicates = new ArrayList<>();

        // 只查上架中的活动
        predicates.add(cb.isTrue(root.get("enabled")));

        if (venueId != null) {
            predicates.add(cb.equal(root.get("venue").get("id"), venueId));
        }
        if (type != null) {
            predicates.add(cb.equal(root.get("type"), type));
        }
        if (StringUtils.hasText(keyword)) {
            // 转小写后模糊匹配，避免大小写差异导致搜不到
            String pattern = "%" + keyword.trim().toLowerCase() + "%";
            predicates.add(cb.or(
                    cb.like(cb.lower(root.get("title")), pattern),
                    cb.like(cb.lower(root.get("description")), pattern),
                    cb.like(cb.lower(root.get("tags")), pattern)
            ));
        }

        return cb.and(predicates.toArray(new Predicate[0]));
    };
}
```

这段代码的价值在于它**拼的是 Predicate 对象而不是字符串**：

- 参数走绑定变量，`keyword` 里带引号或 `--` 都不会出问题；
- `cb.isTrue(...)` 生成的是 `enabled = true`，不是手写的字符串片段，字段改名时编译期就能发现；
- `cb.or(...)` 自动加括号，不会因为运算符优先级写出“本该是 `A AND (B OR C)` 却成了 `A AND B OR C`”的隐式 bug。

要使用 `Specification`，Repository 必须多继承一个接口：

```java
public interface ActivityRepository
        extends JpaRepository<Activity, Long>, JpaSpecificationExecutor<Activity> {
```

### 6.4 分页与排序

```java
Sort sort = Sort.by(Sort.Direction.DESC, "createdAt")
        .and(Sort.by(Sort.Direction.DESC, "id"));
Pageable pageable = PageRequest.of(safePage, safeSize, sort);

Page<Activity> result = activityRepository.findAll(
        buildSpecification(venueId, type, keyword), pageable);
```

三个细节：

**一、页码从 0 开始。** `PageRequest.of(0, 10)` 是第一页。这是 Spring Data 的约定，和 MyBatis-Plus 相反（第十一节）。

**二、排序字段写属性名不写列名。** 写 `"createdAt"` 而不是 `"created_at"`——它走的是实体属性，能防止把列名拼错。

**三、`Pageable` 的 size 要防御性收敛。** 案例代码里做了这件事：

```java
// 防御性收敛：即使有人传 size=100000，也不会把数据库拖垮
int safeSize = Math.min(Math.max(size, 1), appProperties.maxPageSize());
int safePage = Math.max(page, 0);
```

`size=100000` 这种请求不是只有恶意用户才会发——前端分页组件出 bug、脚本循环调用都可能造成。在 Service 层做上限收敛，比只靠 Controller 的参数校验更可靠（校验注解可以被绕过，比如内部调用）。

**四、分页会额外发一条 count 查询。** 实测中（第八节的场景 B），一次分页查询发出的是两条 SQL：

```sql
select count(a1_0.id) from activity a1_0 where a1_0.enabled=true
select ... from activity a1_0 join venue c1_0 on ... order by ... offset ? rows fetch first ? rows only
```

不想要 count 时有两个选择：返回 `Slice`（只判断有没有下一页，不查总数），或者用 `@Query` 配合自定义 `countQuery`。

### 6.5 不要把 Page 直接返回给前端

第 4 篇讲过这一点，这里补充原因。`Page` 的 JSON 结构由 Spring Data 决定，历史上变动过（字段名、是否包含 `pageable` 大对象）。把它序列化出去，等于把接口契约绑在框架版本上。本项目的做法是转成自己的 `PageResult`：

```java
public record PageResult<T>(List<T> items, int page, int size, long total, int totalPages) {
    /** 把 Page<实体> 转成 PageResult<DTO>，映射函数由调用方提供 */
    public static <E, T> PageResult<T> of(Page<E> page, Function<E, T> mapper) {
        return new PageResult<>(
                page.getContent().stream().map(mapper).toList(),
                page.getNumber(),
                page.getSize(),
                page.getTotalElements(),
                page.getTotalPages()
        );
    }
}
```

调用处一行：

```java
return PageResult.of(result, ActivityResponse::from);
```
