# 八、N+1 问题：实测对比

### 8.1 问题是什么

“N+1”指的是：发出 1 条查询拿到 N 条主记录，然后为了取每条记录的关联数据，又发了 N 条查询。总数变成 N+1 条。

案例项目的列表接口正好暴露这个问题。为此我写了一个探测测试（**不属于交付工程**，仅用于取数），在同一份数据上跑两种写法：

**场景 A：分页查询 + 逐条访问 LAZY 关联**（模拟“忘了加 `@EntityGraph` 的列表接口”）

```java
List<ResourceItem> items = entityManager
        .createQuery("select r from ResourceItem r where r.enabled = true "
                + "order by r.createdAt desc, r.id desc", ResourceItem.class)
        .setFirstResult(0)
        .setMaxResults(5)
        .getResultList();
Long total = entityManager
        .createQuery("select count(r) from ResourceItem r where r.enabled = true", Long.class)
        .getSingleResult();
items.forEach(item -> item.getCategory().getName());   // 模拟 DTO 转换
```

**场景 B：走 `@EntityGraph` 的 `findAll`**

```java
Page<ResourceItem> page = repository.findAll(
        (root, query, cb) -> cb.isTrue(root.get("enabled")),
        PageRequest.of(0, 5, Sort.by(Sort.Direction.DESC, "createdAt")));
page.getContent().forEach(item -> item.getCategory().getName());
```

### 8.2 实测结果

开启 `logging.level.org.hibernate.SQL=debug` 后数 SQL 条数：

**场景 A：7 条 SQL**

```text
 1. select ri1_0.id,ri1_0.category_id,ri1_0.created_at,ri1_0.description, ... 
    from resource_item ri1_0 where ri1_0.enabled=true 
    order by ri1_0.created_at desc,ri1_0.id desc offset ? rows fetch first ? rows only
 2. select count(ri1_0.id) from resource_item ri1_0 where ri1_0.enabled=true
 3. select c1_0.id,c1_0.code,c1_0.name,c1_0.sort_order from category c1_0 where c1_0.id=?
 4. select c1_0.id,c1_0.code,c1_0.name,c1_0.sort_order from category c1_0 where c1_0.id=?
 5. select c1_0.id,c1_0.code,c1_0.name,c1_0.sort_order from category c1_0 where c1_0.id=?
 6. select c1_0.id,c1_0.code,c1_0.name,c1_0.sort_order from category c1_0 where c1_0.id=?
 7. select c1_0.id,c1_0.code,c1_0.name,c1_0.sort_order from category c1_0 where c1_0.id=?
```

第 3 到第 7 条就是 N——5 条资源，5 次单条查询分类。

**场景 B：2 条 SQL**

```text
 1. select ri1_0.id,ri1_0.category_id,c1_0.id,c1_0.code,c1_0.name,c1_0.sort_order,
           ri1_0.created_at,ri1_0.description, ... 
    from resource_item ri1_0 join category c1_0 on c1_0.id=ri1_0.category_id 
    where ri1_0.enabled=true 
    order by ri1_0.created_at desc offset ? rows fetch first ? rows only
 2. select count(ri1_0.id) from resource_item ri1_0 where ri1_0.enabled=true
```

分类数据被 `join` 一次带出来了。

**对比：7 条 → 2 条。** 每页 10 条时是 12 条 → 2 条，每页 100 条时是 102 条 → 2 条。这就是 N+1 的危害量级：**SQL 条数随页大小线性增长**。

### 8.3 解法一：@EntityGraph

```java
/**
 * 覆盖父接口方法并加上 @EntityGraph。
 *
 * <p>列表查询每页 10 条，若不做处理，取每条的分类名都会单独发一条 SQL，
 * 一共 1 + 10 = 11 条（这就是 N+1 问题）。加上 @EntityGraph 后压成 1 条。
 */
@Override
@EntityGraph(attributePaths = {"category"})
Page<ResourceItem> findAll(Specification<ResourceItem> spec, Pageable pageable);
```

`@EntityGraph` 描述的是“这次查询要顺带把哪些关联取回来”。它比改实体上的 `fetch` 更精确——**只影响这一个方法**，其他查询仍然是 LAZY。

一个要注意的点：`@EntityGraph` 与分页一起用时，如果关联的是一对多集合，Hibernate 会在内存里分页（先查出所有再截断），日志里会出现 `HHH000104: firstResult/maxResults specified with collection fetch; applying in memory` 的警告。一对多场景改用 `@BatchSize`（解法三）。

### 8.4 解法二：JOIN FETCH

```java
@Query("SELECT r FROM ResourceItem r JOIN FETCH r.category WHERE r.enabled = true")
List<ResourceItem> findAllWithCategory();
```

`JOIN FETCH` 写起来更直观，但它有两个限制：

- **不能和分页共存**（对集合关联而言，同样是内存分页的问题）；
- 多个 `JOIN FETCH` 会笛卡尔积放大结果集。

对于本例这种“多对一”的关联，`JOIN FETCH` 和 `@EntityGraph` 效果一样。**多对一优先用 `@EntityGraph`**，因为它不改 JPQL，能在 `JpaRepository` 已有的方法上覆盖。

### 8.5 解法三：@BatchSize

当关联是集合（一对多、多对多）时，上面两招都不适合分页。这时用 `@BatchSize`：

```java
@BatchSize(size = 20)
private List<Comment> comments;
```

或者全局配置：

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 20
```

效果是：需要加载 N 个集合时，Hibernate 把它们的 id 收集起来，用 `IN (...)` 一次查 20 个。SQL 条数从 N+1 降到 N/20 + 1。

它不改变查询本身，只改变加载策略，所以**和分页兼容**，也适合“不是每次都需要关联数据”的场景。

### 8.6 为什么必须关掉 open-in-view

```yaml
spring:
  jpa:
    open-in-view: false
```

`open-in-view` 默认是 `true`，效果是：为每个请求注册一个 `OpenEntityManagerInViewInterceptor`，让 Hibernate 的 Session 一直保持到 JSON 渲染完成。

它“解决”的问题是：Service 方法结束后、Controller 渲染响应时，代码还能访问 LAZY 关联而不报 `LazyInitializationException`。

它真正做的事是**掩盖问题**：

| 开着 open-in-view | 关掉之后 |
| --- | --- |
| Session 跨越整条请求链路 | Session 在 Service 方法结束时关闭 |
| 渲染响应时的每次懒加载都发 SQL | 在 Service 内就该把数据取全，否则抛异常 |
| 连接被长时间占用（直到响应写完） | 连接在事务结束时归还 |
| N+1 问题被藏起来，只在压测时表现为慢 | 问题在开发期直接暴露成异常 |

关掉之后，`ResourceResponse.from(item)` 里访问 `item.getCategory()` 必须在事务内完成——本项目的 `search` / `getById` 都标了 `@Transactional`，所以没问题。这是一条健康的约束。

> **文档里怎么描述这条建议**
>
> 官方文档对 `open-in-view` 的描述是中立的（它是 JPA 规范的一个特性）。而“生产环境应当关闭”是社区共识，理由如上。教程里把它写成“本项目强制关闭”，而不是“官方要求关闭”。

### 8.7 怎么发现 N+1

| 手段 | 做法 | 特点 |
| --- | --- | --- |
| SQL 日志 | `logging.level.org.hibernate.SQL=debug` | 最简单，适合开发期 |
| 绑定参数日志 | 加 `logging.level.org.hibernate.orm.jdbc.bind=trace` | 能看到 `?` 的实际值 |
| Hibernate 统计 | `spring.jpa.properties.hibernate.generate_statistics=true` | 启动时打印语句数、执行时间汇总 |
| 连接池监控 | Actuator 的 `metrics` 端点看 `hikaricp.connections` | 生产环境看趋势 |
| APM / 慢查询日志 | 数据库侧的 slow query log | 线上排查的兜底 |

其中 `hibernate.generate_statistics=true` 的启动日志会直接给出结论性数字，形如：

```text
Session Metrics {
    12345 nanoseconds spent acquiring 1 JDBC connections;
    89012 nanoseconds spent releasing 1 JDBC connections;
    156789 nanoseconds spent preparing 12 JDBC statements;
    234567 nanoseconds spent executing 12 JDBC statements;
    ...
}
```

**“preparing 12 JDBC statements”对一次列表请求来说就是明确的报警**。
