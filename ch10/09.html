10.9 运行时改日志级别 ​

loggers 端点是 Actuator 里少数几个写操作之一，也是排查线上问题时最常被用到的一个：某个接口行为不对，想开 DEBUG 看细节，又不想重启服务。

响应的三个部分 ​

实测 /actuator/loggers 的顶层结构：

text
顶层键: ['levels', 'loggers', 'groups']
可调级别: ['OFF', 'ERROR', 'WARN', 'INFO', 'DEBUG', 'TRACE']
logger 条目数: 686

loggers 里每个条目的结构，以及 configuredLevel 什么时候出现：

text
ROOT                                              -> {"configuredLevel": "INFO", "effectiveLevel": "INFO"}
com.example.activity                           -> {"configuredLevel": "DEBUG", "effectiveLevel": "DEBUG"}
com.example.activity.service                   -> {"effectiveLevel": "DEBUG"}
org.apache.catalina.core.StandardEngine          -> {"effectiveLevel": "ERROR"}

686 条里只有 10 条带 configuredLevel，其余 676 条只有 effectiveLevel。这个差别正是排查“改了级别却没看到日志”的线索：

  • configuredLevel = 显式配过（配置属性或运行时 POST 设过）
  • effectiveLevel = 实际生效的，可能从父级继承而来

为什么恰好是 10 条？看一下这 10 条分别是谁，比记住数字有用：

text
ROOT                                                INFO   ← 你配的
com.example.activity                             INFO   ← 你配的
org.apache.catalina.startup.DigesterFactory         ERROR  ← Tomcat 自己设的
org.apache.catalina.util.LifecycleBase              ERROR  ← Tomcat 自己设的
org.apache.coyote.http11.Http11NioProtocol          WARN   ← Tomcat 自己设的
org.apache.tomcat.util.net.NioSelectorPool          WARN   ← Tomcat 自己设的
org.apache.sshd.common.util.SecurityUtils           WARN   ← 依赖自己设的
org.eclipse.jetty.util.component.AbstractLifeCycle  ERROR  ← 依赖自己设的
org.hibernate.validator.internal.util.Version       WARN   ← 依赖自己设的
org.springframework.boot.actuate.endpoint.jmx       WARN   ← Spring Boot 自己设的

只有 2 条是你写的，另外 8 条是框架和依赖为了不刷屏预先压下去的。 这个现象在排查时有两个用处：一是某个包明明是 WARN 级别，不必怀疑有人改过配置，它自己就是那么设的；二是想知道“平时哪些包在吵”—— 恰好就是这 8 个。

如果某个 logger 的 configuredLevel 是 DEBUG 但 effectiveLevel 是 INFO，说明父级把它压住了 —— 这时候要去改父级，或者直接改 root。

改级别与清除级别 ​

java
@Test
@DisplayName("POST 改级别后立刻生效，GET 能读到新值")
void changesLevelAtRuntime() {
    // 写操作返回 void，所以按端点规则是 204 而不是 200
    assertThat(mvc.post().uri("/actuator/loggers/" + LOGGER)
            .contentType(MediaType.APPLICATION_JSON)
            .content("""
                    {"configuredLevel":"DEBUG"}
                    """)
            .exchange())
            .hasStatus(204);

实测 POST 返回 204，读回是 {"configuredLevel": "DEBUG", "effectiveLevel": "DEBUG"}。

传 null 表示清除显式配置，回落到父级。这里有一个与直觉不符的细节，实测确认过：

java
@Test
@DisplayName("传 null 表示清除该 logger 的显式配置，回落到父级")
void nullResetsToInheritedLevel() {
    // ... 先设成 WARN，再传 null

    // 实测：configuredLevel 被置空之后，这个字段是<em>整个从响应里消失</em>的，
    // 而不是输出一个 null。所以这里断言的是"响应体里没有这个键"，
    // 用 JsonPath 去提取一个不存在的路径只会直接失败。
    assertThat(mvc.get().uri("/actuator/loggers/" + LOGGER).exchange())
            .hasStatusOk()
            .bodyText()
            .doesNotContain("configuredLevel")
            // effectiveLevel 回落到从 root 继承下来的 INFO
            .contains("\"effectiveLevel\":\"INFO\"");
}

configuredLevel 为 null 时整个键从响应里消失，而不是输出 "configuredLevel": null。Actuator 的 JSON 序列化配置了不输出 null 字段，所以用 JsonPath 提取一个不存在的路径会直接失败，得改成对响应体文本做断言。

分组：一次改一批 ​

yaml
logging:
  group:
    # 自定义日志分组：一条配置改一批包
    activity:
      - com.example.activity
      - org.springframework.boot.actuate.endpoint

实测分组出现在 groups 里：

json
{ "activity": { "members": ["com.example.activity", "org.springframework.boot.actuate.endpoint"] },
  "web": { "members": ["org.springframework.core.codec", "org.springframework.http", "org.springframework.web", "..."] },
  "sql": { "members": ["org.springframework.jdbc.core", "org.hibernate.SQL", "org.jooq.tools.LoggerListener"] } }

web 与 sql 是 Boot 内置的分组，不用自己配。POST 到组名就能给整组一次性调级 —— 排查某个技术栈的问题时，这一步省很多事：

bash
# 整组开 DEBUG，不用逐个包写
curl -X POST http://localhost:8080/actuator/loggers/web \
     -H 'Content-Type: application/json' -d '{"configuredLevel":"DEBUG"}'

注意组的条目里没有 effectiveLevel —— 组只是名字的集合，本身不生效。这一点从响应结构上就能看出来：组条目只有 members（和可能存在的 configuredLevel）。

隐藏 logger：名字带下划线前缀的那些 ​

686 条里有 6 条的名字以下划线开头，而且连成一串：

text
_org
_org.springframework
_org.springframework.web
_org.springframework.web.servlet
_org.springframework.web.servlet.HandlerMapping
_org.springframework.web.servlet.HandlerMapping.Mappings

它们不是端点编出来的，而是日志框架里真实存在的名字。 一开始我以为 _ 是 Actuator 给“没有显式配置的 logger”打的标记，于是做了个实验：分别 POST 到 /_org 和 /org。结果是两个互相独立的 logger —— 给 _org 设 WARN 之后，org 那条仍然是 {"effectiveLevel": "INFO"}；反过来也一样。所以下划线是名字的一部分。

源头在 Spring Framework 的 LogDelegateFactory：

java
/**
 * Create a "hidden" logger with a category name prefixed with "_", thus
 * precluding it from being enabled together with other log categories from
 * the same package. This is useful for specialized output that is either
 * too verbose or otherwise optional or unnecessary to see all the time.
 * @param category the log category to use
 * @return a Log with the category {@code "_" + category}
 * @since 5.3.5
 */
public static Log getHiddenLog(String category) {
    return LogFactory.getLog("_" + category);
}

Javadoc 说得很直白：加下划线是为了让这种 logger 不会跟着同包的其他 logger 一起被打开。用它的地方是 AbstractHandlerMapping：

java
/** Dedicated "hidden" logger for request mappings. */
protected final Log mappingsLogger =
        LogDelegateFactory.getHiddenLog(HandlerMapping.class.getName() + ".Mappings");

它用来输出“Mapped {GET /api/activities, produces [...]}”这类请求映射明细。输出又长又吵，不该在你把 org.springframework.web 调到 DEBUG 时一起涌出来 —— 这就是“隐藏”的含义。注意 @since 5.3.5：这不是 4.x 的新东西，只是以前不太会有人去读这个端点的原始响应。

那为什么是 6 条而不是 1 条？因为 Logback 的 getLogger(name) 是逐段建 logger 的：创建 _org.springframework.web.servlet.HandlerMapping.Mappings 会顺带建出它整条祖先链，每一段都成为一个独立的 logger 对象。这 6 条正是同一条链。

隐藏 logger 仍然可以按自己的名字单独调级 —— 名字里带下划线，路径变量照常接受：

java
@Test
@DisplayName("响应里会出现名字带下划线前缀的 logger —— 这是框架故意藏起来的")
void hiddenLoggersAppearVerbatim() {
    AbstractJsonContentAssert<?> json = assertThat(mvc.get().uri("/actuator/loggers").exchange())
            .hasStatusOk()
            .bodyJson();

    json.extractingPath("$.loggers['_org.springframework.web.servlet.HandlerMapping.Mappings']"
            + ".effectiveLevel").isEqualTo("INFO");
    // 隐藏 logger 仍可按自己的名字单独调级
    assertThat(mvc.post()
            .uri("/actuator/loggers/_org.springframework.web.servlet.HandlerMapping.Mappings")
            .contentType(MediaType.APPLICATION_JSON)
            .content("""
                    {"configuredLevel":"DEBUG"}
                    """)
            .exchange())
            .hasStatus(204);

排查“映射没注册上”这类问题时，这个 logger 就是最直接的线索 —— 平时它是隐藏的，需要时按上面这样单独打开。

名字里的特殊字符 ​

logger 名字就是日志框架里的原始名字，端点不做任何加工。所以里面会有各种不适合直接塞进 URL 或 JsonPath 的字符：

text
org.apache.catalina.core.ContainerBase.[Tomcat].[localhost].[/]
_org.springframework.web.servlet.HandlerMapping.Mappings

两条实用规则：

  1. JsonPath 里必须用 ['...'] 包起来，不能按点逐层找：$.loggers['com.example.activity'].configuredLevel。名字里的 [ ] 更是只能这样写。
  2. URL 里的方括号要转义。curl 里方括号会被当成 glob，加 -g 参数或者对 [ ] 做百分号编码才稳妥。

这个端点的安全边界 ​

loggers 能让任何人把任意包调到 TRACE，进而把日志刷满磁盘。日志量暴涨是比服务不可用更难排查的故障：磁盘写满之后数据库、容器运行时全部受影响，而现象只是“服务逐渐变慢”。

所以生产环境它要么不暴露，要么单独加权限。相关配置见 10.12。
