十一、MyBatis-Plus 接入 Spring Boot 4 ​

JPA 的定位是“以对象为中心”，MyBatis-Plus 的定位是“以 SQL 为中心但省掉重复的 CRUD”。教学项目里两者都值得讲，因为企业的技术选型分布很广。

activity-server-mybatisplus 工程用 MyBatis-Plus 3.5.17 实现了同一套接口，下面按接入顺序讲，全部内容都经过本机实测。

11.1 选对 starter ​

这是第一个坑。MyBatis-Plus 的 starter 坐标随 Spring Boot 大版本改名：

Spring Bootstarter 坐标
2.xmybatis-plus-boot-starter
3.xmybatis-plus-spring-boot3-starter
4.xmybatis-plus-spring-boot4-starter

用错的表现是启动时找不到自动配置类（AutoConfigureMybatisPlus 之类），或者 SqlSessionFactory 建不起来。三个坐标在中央仓库都存在，boot3 那个也能下载到——“能下载”不代表“能用”，必须按 Spring Boot 版本选。

xml
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-spring-boot4-starter</artifactId>
    <version>3.5.17</version>
</dependency>

这个 starter 传递带进来的关键依赖包括 mybatis-plus 3.5.17、mybatis-spring 4.0.0、spring-boot-starter-jdbc（所以 HikariCP 也就有了）。

11.2 还要单独引 SQL 解析器 ​

xml
<!--
  MyBatis-Plus 3.5.9 起把 SQL 解析器拆成了独立模块，
  分页插件 PaginationInnerInterceptor 依赖它，不引会报 ClassNotFoundException。
-->
<dependency>
    <groupId>com.baomidou</groupId>
    <artifactId>mybatis-plus-jsqlparser</artifactId>
    <version>3.5.17</version>
</dependency>

遗漏它的报错是运行时抛 ClassNotFoundException: net.sf.jsqlparser...——启动能过，一调分页接口就炸。

11.3 建表脚本要自己写 ​

MyBatis-Plus 不做对象到表的映射推导，也不会建表。所以必须提供 schema.sql：

sql
DROP TABLE IF EXISTS activity;
DROP TABLE IF EXISTS venue;

CREATE TABLE venue
(
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    name       VARCHAR(64)  NOT NULL,
    code       VARCHAR(32)  NOT NULL,
    sort_order INT          NOT NULL DEFAULT 0,
    CONSTRAINT uk_venue_name UNIQUE (name)
);

CREATE TABLE activity
(
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    title          VARCHAR(128) NOT NULL,
    -- 逻辑删除字段：0 表示已删除，1 表示正常
    enabled        TINYINT      NOT NULL DEFAULT 1,
    -- ...
);

并在 yml 里显式告诉 Spring Boot 去哪里找（因为默认位置只认类路径根目录，显式声明更清楚）：

yaml
spring:
  sql:
    init:
      mode: always
      schema-locations: classpath:schema.sql
      data-locations: classpath:data.sql

11.4 实体注解对照 ​

java
@TableName("activity")
public class Activity {

    /** AUTO 表示依赖数据库自增主键，插入后框架会把生成值回填到该字段 */
    @TableId(type = IdType.AUTO)
    private Long id;

    private String title;

    /** 驼峰转下划线已开启，venueId 会自动映射到 venue_id */
    private Long venueId;

    /**
     * 逻辑删除标记。加上 @TableLogic 后，框架会自动做两件事：
     * 所有查询自动追加 enabled = 1；调用 deleteById 时改成 UPDATE ... SET enabled = 0
     */
    @TableLogic
    private Integer enabled;

    /** 插入时自动填充 */
    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createdAt;

    /** 插入和更新时都自动填充 */
    @TableField(fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updatedAt;
}

与 JPA 的对应关系：

关注点JPAMyBatis-Plus
表名@Table(name = ...)@TableName(...)
主键@Id + @GeneratedValue@TableId(type = IdType.AUTO)
字段名@Column(name = ...)驼峰自动转下划线，@TableField 只在特殊时用
关联@ManyToOne 等，返回对象手工持 venueId，需要场地名要自己再查或写 JOIN
逻辑删除自己写方法改字段@TableLogic 由框架改写 SQL
时间填充@PrePersist / @PreUpdateMetaObjectHandler + fill
建表Hibernate 自动建必须自己写脚本

有一段注释里的表格值得单独说：MyBatis-Plus 没有对象关联。JPA 里 Activity 持有 Venue 对象，MyBatis-Plus 里只有 venueId。这不是缺陷，是设计取向——MyBatis-Plus 希望你用 SQL 的思维处理关联（写 JOIN，或者查两次）。

11.5 分页插件必须手工注册（本项目踩到的坑） ​

java
/**
 * 分页插件。
 *
 * <p>这是最容易踩的一个坑：MyBatis-Plus 的 selectPage 默认不会真的分页，
 * 它需要这个拦截器去改写 SQL 加上 LIMIT。
 * 忘了注册的话，返回的 total 会是 0、records 是全部数据，而且没有任何报错。
 */
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.H2));
    return interceptor;
}

为了给出确凿证据，我做了一次对照实验：注释掉这个 @Bean，跑同一套测试。

正常注册（LIMIT 出现在 SQL 里）：

sql
SELECT id,title,description,venue_id,type,... FROM activity 
WHERE enabled=1 ORDER BY created_at DESC,id DESC LIMIT ?
[INFO] Tests run: 6, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS

注释掉 @Bean 之后（SQL 里没有任何 LIMIT）：

=== 含 LIMIT 的 SQL 条数 ===
0

[ERROR] Tests run: 6, Failures: 2, Errors: 0, Skipped: 0
[ERROR]   MpActivityApiTest.pageQuery:42 JSON path "$.records.length()" expected:<2> but was:<5>
[ERROR]   MpActivityApiTest.keywordQuery:52 
[INFO] BUILD FAILURE

expected:<2> but was:<5> 就是“分页没生效，把全部 5 条都返回了”。

这个坑的可怕之处在于它不报错。如果当初没写分页相关的断言，测试依然全绿，问题会一直到数据量变大、接口返回几百条时才发现。

顺带说明 DbType.H2 参数：它告诉解析器按哪种数据库方言改写分页 SQL（MySQL 用 LIMIT，SQL Server 用 OFFSET ... FETCH，Oracle 12c 之前用嵌套 ROWNUM）。生产用 MySQL 时改成 DbType.MYSQL。

11.6 逻辑删除与自动填充的实测效果 ​

同一套测试的 SQL 日志里，能看到框架自动改写了 SQL：

逻辑删除：deleteById 变成了 UPDATE

text
==>  Preparing: UPDATE activity SET updated_at=?, enabled=0 WHERE id=? AND enabled=1
==> Parameters: 2026-09-13T17:45:41.130510(LocalDateTime), 1(Long)

数据行还在，只是 enabled 变成 0。后面所有查询都自动带上 enabled = 1：

text
==>  Preparing: SELECT id,title,description,... FROM activity WHERE id=? AND enabled=1

自动填充：INSERT 语句里没有手工赋值的时间字段

text
==>  Preparing: INSERT INTO activity ( title, venue_id, type, approved_count, organizer, enabled, created_at, updated_at ) VALUES ( ?, ?, ?, ?, ?, ?, ?, ? )
==> Parameters: 自动填充验证(String), 1(Long), LECTURE(String), 0(Integer), 测试员(String), 1(Integer), 2026-09-13T17:45:41.377273(LocalDateTime), 2026-09-13T17:45:41.377273(LocalDateTime)

Service 里只写了 item.setDownloadCount(0); item.setEnabled(1); mapper.insert(item);，两个时间字段是 MetaObjectHandler 填进去的。

11.7 页码从 1 开始 ​

java
@GetMapping
public Page<Activity> list(..., @RequestParam(defaultValue = "1") int page,
                               @RequestParam(defaultValue = "10") int size) {
    return activityService.search(venueId, type, keyword, page, size);
}

MyBatis-Plus 的 Page 从 1 开始，Spring Data 的 Pageable 从 0 开始。 这是两个工程并存时的高频错误来源，症状是“第一页少一条”或者“翻到最后一页报空”。

java
LambdaQueryWrapper<Activity> wrapper = Wrappers.lambdaQuery(Activity.class)
        // 三个参数的重载：条件为 false 时该条件不拼进 SQL，省掉了大量 if 判断
        .eq(venueId != null, Activity::getVenueId, venueId)
        .eq(StringUtils.hasText(type), Activity::getType, type)
        // and(...) 把一组条件用括号包起来，避免和前面的 eq 混淆优先级
        .and(StringUtils.hasText(keyword), w -> w
                .like(Activity::getTitle, keyword)
                .or()
                .like(Activity::getDescription, keyword))
        .orderByDesc(Activity::getCreatedAt)
        .orderByDesc(Activity::getId);

return activityMapper.selectPage(new Page<>(page, size), wrapper);

LambdaQueryWrapper 的两个好处：Activity::getTitle 是方法引用，字段改名时编译期报错（用字符串 "title" 就只能等运行时）；and(...) 保证一组 or 条件被括号包住，不会串味。

11.9 两套技术怎么选 ​

维度JPA（Hibernate）MyBatis-Plus
上手速度简单 CRUD 极快，注解一写就跑需要写建表脚本、配插件
复杂查询JPQL 表达力有限，复杂场景要退化成原生 SQLSQL 完全可控，多表 JOIN 很自然
表结构管理可自动建表（仅开发期）必须人工维护脚本
关联对象直接持有对象，配好抓取策略很方便需手工处理
团队心智要懂持久化上下文、脏检查、抓取策略要懂 SQL
典型场景领域模型清晰、以对象为中心的增删改查报表查询多、SQL 复杂、需要精细优化

一句话概括：数据访问逻辑简单、对象关系清晰时用 JPA；SQL 复杂、性能敏感、团队 SQL 功底强时用 MyBatis-Plus。两者在同一个项目里共存也完全可行（不同模块用不同技术），但要注意页码起点和事务管理方式的差异。
