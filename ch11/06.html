11.6 容器化：两个容易被忽略的细节 ​

把应用放进容器，最朴素的写法是三步：

dockerfile
FROM eclipse-temurin:21-jre
COPY target/activity-server-1.0.0.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]

这能跑起来，但有两个问题：每次构建都要把 62MB 整个重写一遍，而且容器里以 root 运行。

官方文档给出了分层写法（见 Dockerfiles）。它用的基础镜像是 bellsoft/liberica-openjre-debian:25-cds——选 25 是因为那一页的示例要顺带演示 AOT cache（需要 Java 25+）。本教程的基线是 Java 21，所以换成 eclipse-temurin:21-jre：

dockerfile
# 构建阶段：把可执行 jar 按层解压
FROM eclipse-temurin:21-jre AS builder
WORKDIR /builder

ARG JAR_FILE=target/activity-server-1.0.0.jar
COPY ${JAR_FILE} application.jar

RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

FROM eclipse-temurin:21-jre

# 运行账号先建好，后面的 COPY 才能用 --chown 直接指定属主
RUN useradd --uid 10001 --gid 0 --create-home appuser

WORKDIR /application

COPY --chown=appuser:0 --from=builder /builder/extracted/dependencies/ ./
COPY --chown=appuser:0 --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --chown=appuser:0 --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --chown=appuser:0 --from=builder /builder/extracted/application/ ./

RUN mkdir --parents storage && chown appuser:0 storage

USER appuser

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "application.jar"]

配一个 .dockerignore，别让 62MB 之外的东西也进上下文：

text
target/*
!target/activity-server-1.0.0.jar

storage
*.log

.git
.idea
.vscode

target/* 加 !target/activity-server-1.0.0.jar 这个写法是关键：先全部排除，再单独把 jar 放回来。

实测：四个镜像 ​

配套工程里放了四个 Dockerfile，分别构建后对比：

文件写法镜像大小
Dockerfile分层 + COPY --chown431 MB
Dockerfile.uber单层 + COPY --chown431 MB
Dockerfile.naive单层，先 COPY 再 RUN chown496 MB
Dockerfile.cds分层 + CDS 训练运行546 MB

基础镜像是 366MB。四个数字放在一起，能拆出两条容易搞混的结论。

细节一：chown 的位置，代价是 64MB ​

Dockerfile.uber 和 Dockerfile.naive 都打单层，唯一的差别是改属主的位置：

dockerfile
# Dockerfile.uber：COPY 时顺手改
COPY --chown=appuser:0 ${JAR_FILE} application.jar

# Dockerfile.naive：拷完再改
COPY ${JAR_FILE} application.jar
RUN useradd --uid 10001 --gid 0 --create-home appuser \
    && chown --recursive appuser:0 /application

用 docker history 看每一层的体量，差别一眼就能看出来：

text
# Dockerfile.uber（431 MB）
64.6MB   COPY --chown=appuser:0 target/activity-server-1.0.0.jar application.jar

# Dockerfile.naive（496 MB）
64.6MB   COPY target/activity-server-1.0.0.jar application.jar
64.6MB   RUN /bin/sh -c useradd ... && chown --recursive appuser:0 /application

原因是 Docker 的分层机制：每一层都是上一层的差异快照。chown 修改了所有文件的属主，对文件系统来说这些文件全都变了，于是这一层必须把它们整套重新存一遍。64MB 的文件被塞了两份，镜像凭空胖了 64MB。

这个坑在 CDS 镜像上更贵。Dockerfile.cds 最初的版本把训练运行放在 chown 前面，结果：

text
180MB   RUN ... chown --recursive appuser:0 /application
115MB   RUN ... java -XX:ArchiveClassesAtExit=application.jsa ...

依赖 64MB 加归档 115MB，一共 179MB 被复制了一份。改成 COPY --chown 之后，这一层直接消失，镜像从 726MB 降到 546MB。

规则很简单：改属主用 COPY --chown，不要用之后的 RUN chown。 如果确实需要对已有内容批量改属主（比如构建脚本产出的文件），把它和产出文件的那条命令合到一起，别单独成层。

细节二：分层不减小镜像，减少的是重建量 ​

Dockerfile 和 Dockerfile.uber 的大小完全一样，都是 431MB。这一点值得强调，因为“分层镜像更小”是个流传很广的说法。

分层的收益不在大小，在改动之后重建多少。改一处源码再构建，两次构建的执行步骤对比：

text
########## 分层（Dockerfile） ##########
#7  [builder 3/4] COPY target/activity-server-1.0.0.jar application.jar
#7  DONE 0.2s
#8  [builder 4/4] RUN java -Djarmode=tools ... extract --layers ...
#8  DONE 0.6s
#9  [stage-1 4/8] COPY --chown=appuser:0 .../dependencies/ ./          → CACHED
#10 [stage-1 5/8] COPY --chown=appuser:0 .../spring-boot-loader/ ./   → CACHED
#13 [stage-1 6/8] COPY --chown=appuser:0 .../snapshot-dependencies/ ./ → CACHED
#14 [stage-1 7/8] COPY --chown=appuser:0 .../application/ ./
#14 DONE 0.0s

########## 单层（Dockerfile.uber） ##########
#8  [4/5] COPY --chown=appuser:0 target/activity-server-1.0.0.jar application.jar
#8  DONE 0.1s

分层写法下，jar 明明变了（COPY 与 extract 两步都重跑），但依赖层的四步全部命中缓存——因为 extracted/dependencies/ 里的内容没有变化，Docker 按内容做校验，不关心它是怎么来的。只有 87KB 的应用层需要重建。

单层写法下，整个 64MB 的 jar 在一层里，只要 jar 有任何一个字节不同，这一层就要重写。

在这台本地机器上，两者的构建耗时都是零点几秒，看不出差距。真正的差别体现在两个场景：

往镜像仓库推的时候。 镜像推送是按层传的。依赖层在仓库里已经存在，只推变化的 87KB，而不是 64MB。

CI 里没有本地缓存的时候。 单层写法每次都要重新拉一遍完整基础层，分层写法可以让稳定的依赖层跨构建复用。

这也是为什么 layers.idx 的划分依据是变化频率——它优化的从来不是体积，是“变了多少”。

容器内运行验证 ​

三个镜像跑起来，各测三次启动：

镜像三次耗时（秒）中位数
单层 jar4.847 / 4.754 / 4.8124.81
分层4.062 / 3.911 / 3.9773.98
分层 + CDS2.327 / 2.342 / 2.1882.29

和宿主机上的数字（4.80 / 3.77 / 2.28）基本一致，容器本身的开销很小。分层与 CDS 带来的加速在容器里同样成立。

text
$ docker exec rh-m id
uid=10001(appuser) gid=0(root) groups=0(root)

健康检查与接口都正常：

text

CDS 镜像里的训练运行 ​

Dockerfile.cds 的关键一段是在镜像构建阶段做训练运行：

dockerfile
RUN java -XX:ArchiveClassesAtExit=application.jsa \
         -Dspring.context.exit=onRefresh \
         -jar application.jar

放在构建阶段而不是本地做，因为 11.5 提到的平台绑定：归档与操作系统、JDK 版本绑定，在 macOS 上生成的归档在 Linux 容器里用不了。构建容器和运行容器是同一个基础镜像、同一个架构，所以构建期产出的归档可以直接被运行阶段使用。

代价是镜像大了 115MB（431MB → 546MB）。启动从 3.98 秒降到 2.29 秒，换来的是 1.7 秒和 115MB 体积之间的交换。启动敏感、镜像体积不敏感的场景（比如需要快速扩缩容的服务）值得做；镜像要频繁分发、或者容器本来就常驻不重启的场景，不做更划算。

storage 目录要提前放开 ​

应用启动时会在工作目录下创建 storage/ 存放上传文件（第 4 篇的文件上传接口）。容器内工作目录是 /application，而这个目录在 COPY --chown=appuser:0 之后属于 appuser，所以新建子目录没问题。

但如果构建时做过一次训练运行，storage/ 会被 root 身份的进程先创建出来，运行时非 root 用户反而写不进去。两种处理：

dockerfile
# 训练运行之后补一条，或者干脆只在最后统一建
RUN mkdir --parents storage && chown appuser:0 storage

更彻底的做法是把可变数据移出镜像，挂载卷：

shell
$ docker run -v activity-server-data:/application/storage ...

镜像层是只读的，运行时写入的数据属于容器实例而不属于镜像，混在一起会让“这个镜像到底包含什么”变得说不清。上传文件、日志、临时文件都属于应该外置的内容。
